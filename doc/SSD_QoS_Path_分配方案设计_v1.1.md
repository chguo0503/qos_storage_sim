# PD 分离 Prefill 场景下 SSD QoS Path 分配方案设计

> 目标:在 layerwise 逐层预取的前提下,让每个 P 节点的 **NPU 永不因为等 KV 数据而空转**,即最大化 NPU 利用率。
>
> 软件面约定:客户端通过 **KV SQE 语义**(UCM kv client 格式)经 **华为 UB 网络**下发读请求,SQE 的 **DW2** 字段用于指定该请求进入哪条 QoS Path;请求中可另外携带 **带宽需求**声明。本文不涉及任何代码。

> **v1.1 修订说明**(相对初版的三处实质性更正):
>
> 1. **§7.3 方案 C 的否决理由被推翻重写**。初版称"盘框 CPU 要处理 800 GB/s 流量,不现实"——这是错的:800 GB/s 是**数据面**线速,而 CPU 若只做选路,它碰的是**命令面**的 SQE 描述符,单盘仅约 52 K SQE/s、0.067 GB/s。初版的"时延不允许"论据同样站不住(16 ms 预算下存转发的几微秒可忽略)。结论从"不可行"降级为"**能做但不划算**",真正的理由改为"CPU 无信息优势 + 需要新硬件特性"。
> 2. **§4.3 的 $\kappa$ 补上了蒙特卡洛校验**。渐近公式在小样本区间高估均值约 9%,已给出完整分位数,并说明 $\kappa=1.97$ 实际是 P75~P80 而非典型值。
> 3. **新增 §4.5:一致性哈希环的持久偏斜**。初版假设每块盘的命中概率恰为 $1/N_S$,忽略了虚拟节点数有限带来的**永不随时间平均掉**的结构性偏斜。这会让最热盘的有效超配系数从 1.2 塌缩到 1.04,每层失约概率从 0.13% 升到 23.7%。§3.4、§9.3、§12、§13 及附录已连带修正。

## 0. 结论速览(先看这一页)

| 问题 | 结论 |
|---|---|
| **数据面选 path 由谁做?** | **必须由客户端做**(DW2 直接填物理 path id)。盘框侧 CPU 只做**控制面**:采集统计 → 算参数 → 写 cir/pir/权重。理由见 §7.3。 |
| **P 节点 ↔ path 是 1:1 还是动态?** | **绑定关系静态**(初始化后不变),但**一个节点绑多条 path**,按"数据的紧急程度(deadline 剩余量)"分到不同组。即 **1 : k 静态分级映射**,k = 2~3。 |
| **主备 path 有用吗?** | 有用,但不是"主备",而是**逃生通道**:一条极高优先级、极小 cir、极大 pir 的 URGENT path,只在预取落后时使用。必须配准入限制。 |
| **cir/pir 固定时怎么配?** | `cir = 平均需求 × 1.15~1.25`,`pir = cir × 3~4`,桶深 `β ≥ 一层在该盘上的数据量`。**关键:cir 按均值配、pir 按峰值配**,靠统计复用省盘。见 §4.4。 |
| **cir/pir 可改时怎么用?** | 只用于**慢漂移**(命中率变化、chunk 大小变化),控制周期 20~50 ms,加 EWMA 平滑 + 死区,每周期只写少数几条 path。层内抖动交给令牌桶和预取深度,**不要**试图用闭环追层级抖动。 |
| **推荐哪两个方案?** | **方案 B**(全静态 deadline 分级,零运行时配置)和 **方案 E**(方案 B 的骨架 + 50 ms 级闭环调参)。见 §9、§10。 |
| **ring hash 本身的不均匀怎么办?** | 虚拟节点数 $V$ 有限会造成**永久性**的盘间偏斜(不是抖动,不会被时间平均掉)。必须做两件事:$V \ge 500$,且 **cir 按各盘实际环占比 $p_j$ 缩放**。见 §4.5——**这是最容易被忽略、后果最严重的一条**。 |

**四条最重要的公式**(详细推导见正文):

1. **SSD 数量下界**:$N_S \ge \dfrac{N_P \cdot B_{req} \cdot \kappa_{ring}}{\rho \cdot BW_{ssd}}$,其中 $\kappa_{ring} = N_S \cdot \max_j p_j$ 是环的结构性偏斜
2. **短期不均衡系数**:$\kappa \approx 1 + \sqrt{\dfrac{2\ln N_S}{\mu}}$,其中 $\mu$ = 每层每盘的平均请求个数
3. **环的持久偏斜**:$\kappa_{ring} \approx 1 + \dfrac{\sqrt{2\ln N_S}}{\sqrt{V}}$,$V$ = 每盘的虚拟节点数
4. **稳态积压(决定会不会失速)**:$E[Q] \approx \dfrac{\sigma_B^2}{2(c - \mu_B)}$,要求 $c > \mu_B$ **严格大于**

## 2. 目标函数:什么叫"NPU 利用率最大"

### 2.1 layerwise 的时序

layerwise 方案的核心是:**算第 k 层的同时,读第 k+1 层的数据**。画成时间轴:

```
NPU:  [ 算 L0 ][ 算 L1 ][ 算 L2 ][ 算 L3 ] ...
读盘: [ 读 L1 ][ 读 L2 ][ 读 L3 ][ 读 L4 ] ...
       ↑ 这两条必须"同步推进"
```

如果某一层的读比算慢,NPU 就得**停下来干等**,这段等待叫 **stall(失速)**:

$$
\text{stall}_k = \max\big(0,\; T_r(k+1) - T_c(k)\big)
$$

**逐字解释**:$T_r(k+1)$ 是读第 k+1 层数据花的时间,$T_c(k)$ 是算第 k 层花的时间。两者是**并行**的。如果读得比算得快($T_r < T_c$),NPU 一算完就有数据,不用等,stall = 0;如果读得慢,多出来的那部分时间 NPU 就在发呆,所以取 $T_r - T_c$。`max(0, ...)` 就是"负数按 0 算"的意思——读得再快也不会让 NPU 变负数。

### 2.2 NPU 利用率的定义

一次完整 prefill 走完 $L$ 层,总时间是"算的时间 + 干等的时间":

$$
U_{NPU} = \frac{\sum_{k=1}^{L} T_c(k)}{\sum_{k=1}^{L} T_c(k) + \sum_{k=1}^{L} \text{stall}_k}
$$

**逐字解释**:分子是 NPU **真正在干活**的总时间,分母是**墙上时钟走过的**总时间。两者相除就是"有效工作时间占比"。如果一次都没 stall,分母 = 分子,$U = 100\%$。

算例:$L = 80$,$T_c = 8$ ms,总计算时间 = 640 ms。如果总 stall 是 6.4 ms,那么

$$
U_{NPU} = \frac{640}{640 + 6.4} = 0.990 = 99.0\%
$$

**这就是我们要优化的目标**:让分母里的 stall 项尽可能小。

### 2.3 把目标翻译成 QoS 能听懂的话

$U_{NPU} \to 100\%$ 等价于:**对每一层 $k$、每一块盘 $j$,该层落在盘 $j$ 上的数据都必须在 deadline 之前送达**。

用预取深度 $d$ 表示:第 $k+d$ 层的请求在第 $k$ 层开始时发出,必须在第 $k+d$ 层开始前送到,所以每个请求的**时间预算**是:

$$
T_{budget} = d \cdot T_c
$$

算例:$d = 2$,$T_c = 8$ ms,预算 = 16 ms。也就是说,**一个 KV block 的读请求从发出到完成,允许用 16 ms**。这就是 QoS 要保证的 SLO。

> **重要**:预算随 $d$ 线性放大,而 $d$ 的代价只是客户端多缓存几层数据:
> $$\text{客户端缓冲区} = (d+1) \cdot D_L$$
> 算例:$d=2$ 时 = 3 × 64 MB = **192 MB**。这是极其便宜的代价,换来的是 deadline 预算翻倍。**加大预取深度是本场景性价比最高的一个旋钮**,后面反复用到。

## 3. 需求侧:一个 P 节点到底需要多少带宽

### 3.1 第一步:每 token 每层的 KV 有多少字节

$$
b = \underbrace{2}_{\text{K 和 V 两份}} \times\; n_{kv} \;\times\; d_h \;\times\; s
$$

**逐字解释**:注意力缓存要存 Key 和 Value 两份,所以乘 2。每一份是 $n_{kv}$ 个 head,每个 head 有 $d_h$ 个数,每个数占 $s$ 字节。

算例:$b = 2 \times 8 \times 128 \times 2 = 4096$ 字节 = **4 KB**。

### 3.2 第二步:每层要读多少

$$
D_L = H \times b
$$

**逐字解释**:命中 prefix cache 的 token 有 $H$ 个,每个 token 在这一层占 $b$ 字节,乘起来就是这一层要搬的总量。

算例:$D_L = 16384 \times 4\text{ KB} = 65536\text{ KB} = $ **64 MB**。

整个模型 80 层一共要搬:$80 \times 64\text{ MB} = 5120\text{ MB} = 5$ GB。

### 3.3 第三步:需要多大带宽

$$
B_{req} = \frac{D_L}{T_c}
$$

**逐字解释**:带宽 = 数据量 ÷ 时间。要在 $T_c$ 这么长的时间里把 $D_L$ 搬完,就需要这么大的带宽。

算例:$B_{req} = \dfrac{64\text{ MB}}{8\text{ ms}} = 8\text{ MB/ms} = $ **8 GB/s**。

> 直觉检查:8 GB/s 是单盘带宽的 20%。也就是说,**一个 P 节点就能吃掉五分之一块盘**。64 个节点合计 512 GB/s,这就是为什么需要一堆盘。

### 3.4 第四步:需要多少块盘

总需求 = $N_P \times B_{req}$。单盘只敢用到 $\rho \times BW_{ssd}$(留 30% 裕量给抖动和 URGENT 流量)。所以:

$$
N_S \;\ge\; \frac{N_P \cdot B_{req}}{\rho \cdot BW_{ssd}}
$$

算例:$N_S \ge \dfrac{64 \times 8}{0.7 \times 40} = \dfrac{512}{28} = 18.3$ → **暂取 20 块**。

验算:每块盘承担 $\dfrac{512}{20} = 25.6$ GB/s = 单盘的 **64%**。留了 14.4 GB/s 的余量。✓

> ⚠ **这个公式还不完整**。它假设每块盘恰好承担 $1/N_S$ 的负载,而一致性哈希做不到这一点。§4.5 会给出修正版:
> $$N_S \ge \frac{N_P \cdot B_{req} \cdot \kappa_{ring}}{\rho \cdot BW_{ssd}}$$
> 代入 $\kappa_{ring} = 1.15$(虚拟节点数 $V=160$ 时的典型值)后,算例的答案从 20 块变成 **21 块**。

### 3.5 第五步:每个"节点-盘"对的平均需求

因为 ring hash 把数据打散到所有盘,单个节点对**第 $j$ 块盘**的平均带宽需求是:

$$
\bar{d}_j = B_{req} \cdot p_j \;\xrightarrow{\;\text{理想均匀时}\;}\; \frac{B_{req}}{N_S}
$$

其中 $p_j$ 是盘 $j$ 在哈希环上占的份额(所有盘的 $p_j$ 加起来等于 1)。

算例(先按理想均匀算):$\bar{d} = \dfrac{8}{20} = $ **0.4 GB/s**。

**这个 0.4 GB/s 就是我们后面配 cir 的基准数字。** 但——先别急着照抄,§4 会告诉你为什么直接用均值会翻车,而且是**两种不同的翻车方式**:一种是每层随机抖动(§4.1~§4.4),另一种是环本身就不均匀(§4.5)。

## 4. 关键洞察:ring hash 带来的"短期不均衡"

### 4.1 为什么均值不够用

平均下来每块盘 0.4 GB/s,听起来很整齐。但 layerwise 的残酷之处在于:**deadline 是按层算的,一层只有 8~16 ms**。在这么短的窗口里,一个节点只发出了 128 个请求,要散到 20 块盘上——**平均每块盘只有 6.4 个请求**。

样本量只有 6.4,随机波动会非常大。可能某块盘这一层分到了 13 个请求(2 倍),另一块只分到 2 个。而**最慢的那块盘决定了这一层什么时候读完**——木桶效应。

> 这就是"平均带宽够用,但 NPU 还是会 stall"的根本原因。

### 4.2 用"扔球进桶"算出不均衡有多大

这是一个经典的概率问题,叫 **balls into bins(装箱问题)**:

> 把 $n$ 个球随机扔进 $m$ 个桶,**最满的那个桶**大概有几个球?

在我们的场景里:球 = 一个 KV block 读请求,桶 = 一块 SSD,$n$ = 一层的请求数,$m = N_S$。

**第一步:平均值**

$$
\mu = \frac{n}{m}
$$

每个球等概率进任一个桶,所以平均每桶 $n/m$ 个。算例:$\mu = 128/20 = 6.4$。

**第二步:最满的桶有多少**

概率论给出的近似结论(当 $\mu$ 不太小时):

$$
\text{MaxLoad} \approx \mu + \sqrt{2\,\mu \ln m}
$$

**逐字解释**:第一项是平均值,第二项是"运气最差能超出多少"。里面的 $\ln m$ 是**自然对数**——桶越多,你有越多次机会"抽到不幸",所以最大值越可能偏离均值;但它是对数增长,涨得很慢(桶从 20 增到 200,$\ln m$ 只从 3.0 涨到 5.3)。$\sqrt{\mu}$ 这一项来自二项分布的标准差(标准差 ≈ $\sqrt{\mu}$),说明**样本越多,相对波动越小**。

**第三步:定义不均衡系数**

把最大值除以平均值,得到一个无量纲的倍数:

$$
\kappa = \frac{\text{MaxLoad}}{\mu} = 1 + \sqrt{\frac{2 \ln m}{\mu}}
$$

**这个公式非常好用,请记住它的直觉:$\kappa$ 与 $\sqrt{\mu}$ 成反比——每层每盘的请求数翻 4 倍,超出均值的部分就减半。**

### 4.3 代入算例

**情况一:单个节点、预取深度 d=1**

- $n = 128$,$m = 20$,$\mu = 6.4$
- $\ln 20 = 2.996$
- $\kappa = 1 + \sqrt{\dfrac{2 \times 2.996}{6.4}} = 1 + \sqrt{0.936} = 1 + 0.968 = \mathbf{1.97}$

**运气最差的那块盘,要承担接近 2 倍的量。** 它需要的不是 0.4 GB/s,而是 **0.79 GB/s**。

**情况二:单个节点、预取深度 d=2**

预取深度加倍,意味着窗口内在途的请求也加倍,$n = 256$,$\mu = 12.8$:

- $\kappa = 1 + \sqrt{\dfrac{5.991}{12.8}} = 1 + 0.684 = \mathbf{1.68}$

**情况三:d=4**

$\mu = 25.6$,$\kappa = 1 + \sqrt{5.991/25.6} = 1 + 0.484 = \mathbf{1.48}$。

**情况四:全部 64 个节点在一层窗口内的聚合**

- $n_{agg} = 64 \times 128 = 8192$,$\mu_{agg} = 8192/20 = 409.6$
- $\kappa_{agg} = 1 + \sqrt{\dfrac{5.991}{409.6}} = 1 + 0.121 = \mathbf{1.12}$

### 4.3.1 公式准不准?蒙特卡洛校验

上面那个 $\mu + \sigma\sqrt{2\ln m}$ 是**渐近公式**,在 $\mu$ 只有 6.4 的小样本区间未必准。20 万次仿真(每次把 $n$ 个球随机扔进 20 个桶,记录最满桶的球数)结果如下:

| 场景 | $n$ | $\mu$ | 公式 $\kappa$ | 仿真 E[max]/μ | P50 | P95 | P99 |
|---|---|---|---|---|---|---|---|
| d=1, G=512 KB | 128 | 6.40 | 1.968 | **1.802** | 1.72 | 2.19 | 2.50 |
| d=2, G=512 KB | 256 | 12.80 | 1.684 | **1.555** | 1.56 | 1.80 | 2.03 |
| d=1, G=64 KB | 1024 | 51.20 | 1.342 | 1.270 | 1.27 | 1.41 | 1.48 |
| 64 节点聚合 | 8192 | 409.60 | 1.121 | 1.093 | 1.09 | 1.14 | 1.16 |

**三条读法**:

1. **公式在小 $\mu$ 时高估均值约 9%**(1.968 vs 1.802)。$\mu$ 越大越准,聚合那一行只差 2.6%。
2. **$\kappa = 1.97$ 不是"典型值",它大约落在 P75~P80 的位置。** 初版文字说"峰值是均值的 2 倍"不够严谨,准确说法是:**均值 1.80 倍,P95 2.19 倍,P99 2.50 倍**。
3. **好在我们用 $\kappa$ 是为了配 pir 和桶深,本来就该用高分位而不是均值**,所以 1.97 作为配置点是合理的——但要意识到它只覆盖到 P75 左右,§9.3 里把桶深从算出的 2.18 MB 向上取整到 4 MB,才真正盖住了 P99(2.03 → 3.3 MB)。**这一步取整不是可有可无的保守,是必需的。**

**块粒度 $G$ 是这条链上最敏感的输入**:$G$ 从 512 KB 降到 64 KB,$n$ 涨 8 倍,$\kappa$ 从 1.80 降到 1.27。代价是 IOPS 涨 8 倍。如果 UCM 的实际块粒度与本文假设的 512 KB 不同,**§4、§5、§9 的所有数字都要按新的 $n = D_L/G$ 重算**。

### 4.4 这四个数字告诉我们的事(全文最重要的一段)

把结果并排看:

| 视角 | $\mu$ | 公式 $\kappa$ | 仿真均值 | 仿真 P99 | 含义 |
|---|---|---|---|---|---|
| 单节点,d=1 | 6.4 | 1.97 | **1.80** | 2.50 | 单个节点在某块盘上,瞬时要 1.8~2.5× 均值 |
| 单节点,d=2 | 12.8 | 1.68 | **1.56** | 2.03 | 加深预取后降下来 |
| 单节点,d=4 | 25.6 | 1.48 | ~1.40 | ~1.75 | 继续降 |
| 全盘聚合 | 409.6 | 1.12 | **1.09** | 1.16 | **整块盘的总负载只波动 9~16%** |

**关键矛盾**:单个节点的峰值是均值的 2 倍,但整块盘的总负载峰值只比均值高 12%。为什么?因为**不同节点在 ring 上的哈希位置不同,它们"倒霉"的时刻互相错开了**——A 节点这一层在 3 号盘上超载时,B 节点大概率正好在 3 号盘上欠载。

**这直接决定了 cir/pir 的配法:**

- **如果按峰值配 cir**:每条 path 的 cir = $\kappa \bar{d}$ = 2.0 × 0.4 = 0.8 GB/s,64 条路合计 $\Sigma cir = 51.2$ GB/s > 40 GB/s。**硬件根本配不进去**,你得把盘数从 20 加到 40。
- **如果按均值配 cir、按峰值配 pir**:cir = 0.4~0.48 GB/s($\Sigma cir \approx 30$ GB/s ✓ 配得进去),pir = 1.6 GB/s。当某个节点这一层在这块盘上倒霉时,它用 pir 从**盘的空闲带宽**里多拿一点。而根据 $\kappa_{agg} = 1.12$,整盘同时超载的幅度只有 $0.12 \times 25.6 = 3.1$ GB/s,而我们留的余量是 $40 - 25.6 = 14.4$ GB/s——**绰绰有余**。

> **这就是本方案的经济性来源:统计复用(statistical multiplexing)。**
> 用一句话概括:**cir 是"我保证你能拿到的",pir 是"运气好时你能借到的"。因为大家不会同时倒霉,所以借得到。**
>
> 定量地说,$\Sigma pir$ 可以超配到 $2.5\times$ 线速而不出问题,超配比的安全上界近似为 $1/\kappa_{agg}$ 反推的余量条件:
> $$\Sigma cir + (\kappa_{agg} - 1)\,\Sigma cir \;\le\; BW_{ssd}$$
> 即 $\Sigma cir \le \dfrac{BW_{ssd}}{\kappa_{agg}} = \dfrac{40}{1.12} = 35.7$ GB/s。我们的 30 GB/s 满足。✓

### 4.5 第二种翻车方式:一致性哈希环的**持久**偏斜

前面 §4.1~§4.4 讲的是**随机抖动**——它有一个救赎性质:**时间会把它平均掉**。某块盘这一层倒霉,下一层大概率就轮到别人了。令牌桶正是靠这个"此消彼长"来工作的。

但一致性哈希还有第二种不均衡,**它永远不会被时间平均掉**。

#### 4.5.1 问题出在哪

一致性哈希的做法是:把每块盘复制成 $V$ 个**虚拟节点**,随机撒在一个环上;一个 key 哈希到环上某点,顺时针找到的第一个虚拟节点就是它的属主。

盘 $j$ 实际拿到的份额 $p_j$ = 它的 $V$ 个虚拟节点各自"管辖"的弧长之和。**这些弧长是随机的,加起来不会恰好等于 $1/N_S$。**

数学上,$mV$ 个均匀随机点把环切成 $mV$ 段,每段长度近似独立同分布;盘 $j$ 拿到其中 $V$ 段,其和服从 Gamma 分布:

$$
p_j \sim \frac{\text{Gamma}(V,\,1)}{N_S \cdot V}, \qquad E[p_j] = \frac{1}{N_S}, \qquad \frac{\text{std}(p_j)}{E[p_j]} = \frac{1}{\sqrt{V}}
$$

**逐字解释**:Gamma$(V,1)$ 是 $V$ 个独立指数分布之和。它的均值是 $V$、标准差是 $\sqrt{V}$,所以**相对标准差是 $\sqrt{V}/V = 1/\sqrt{V}$**。这就是全部结论:**虚拟节点数决定偏斜大小,而且是平方根律——想把偏斜减半,虚拟节点数要涨 4 倍。**

最热盘的偏斜倍数,同样用"$m$ 个随机量的最大值"公式:

$$
\kappa_{ring} = N_S \cdot \max_j p_j \;\approx\; 1 + \frac{\sqrt{2 \ln N_S}}{\sqrt{V}}
$$

#### 4.5.2 仿真:偏斜到底有多大

$N_S = 20$,每个 $V$ 跑 3000 次独立建环:

| $V$(每盘虚拟节点数) | 理论相对 std $=1/\sqrt V$ | 仿真 $E[\kappa_{ring}]$ | P95 |
|---|---|---|---|
| 50 | 0.141 | 1.281 | 1.424 |
| 100 | 0.100 | 1.198 | 1.299 |
| **160** | 0.079 | **1.152** | 1.227 |
| 500 | 0.045 | 1.085 | 1.125 |
| 1000 | 0.032 | 1.060 | 1.089 |

**关键点:环只抽一次,抽完就固定了。** 如果你的环恰好抽到最热盘 $\kappa_{ring} = 1.15$,那么**这块盘对所有节点、所有层、所有请求,永远比均值热 15%**,直到你重建环为止。

#### 4.5.3 为什么这会翻车——代入排队模型

回到 §5.3 的 Lindley 模型。初版文档把 cir 配成 $\gamma \times$ **名义均值** $\mu_B^{nom} = D_L/N_S = 3.2$ MB。但最热盘的**真实**均值是 $1.15 \times 3.2 = 3.68$ MB。于是:

| | 初版假设 | 实际($V=160$,最热盘) |
|---|---|---|
| 每层到达 $\mu_B$ | 3.2 MB | **3.68 MB** |
| 每层服务 $c = \gamma \mu_B^{nom}$ | 3.84 MB | 3.84 MB(cir 没变) |
| **有效富余** $c - \mu_B$ | 0.64 MB | **0.16 MB** |
| **有效超配系数** | $\gamma = 1.20$ | $\gamma_{eff} = 3.84/3.68 = \mathbf{1.043}$ |
| $\sigma_B$ | 1.233 MB | 1.322 MB |
| $E[Q]$ | 1.19 MB | **5.46 MB** |
| $W$ | 2.42 ms | **11.1 ms** |
| 每层失约概率 | 0.13% | **23.7%** |

**$\gamma = 1.2$ 的超配被环偏斜整个吃掉了。** 有效超配只剩 4.3%,系统正好退化成 §5.4"配法二:保守配法,系统性失速"的那一档。$W = 11.1$ ms 虽然还没超过 $d=2$ 的 16 ms 预算,但安全裕量从 6.6 倍塌到 1.44 倍;而尾概率 23.7% 意味着**这块盘平均每 4 层就拖一次后腿**,而它拖的是**所有 64 个节点**。

> 这是本文档初版最严重的一个疏漏。它的隐蔽之处在于:**平均带宽核算完全正确**(总需求 512 GB/s、总供给 800 GB/s),但系统仍然会被一块盘卡住。**做容量规划时只看总量,是看不出这个问题的。**

#### 4.5.4 修法:三条,都很便宜

**修法一(必做):cir 按盘缩放。**

$p_j$ **不需要测量**——初始化时把环枚举一遍就能精确算出来。所以把 §9.3 的配法从

$$
cir = \gamma \cdot \frac{B_{req}}{N_S} \quad\text{(所有盘用同一个值)}
$$

改成

$$
\boxed{\;cir_j = \gamma \cdot B_{req} \cdot p_j \quad\text{(每块盘一个值)}\;}
$$

这样每块盘上的有效超配系数都精确等于 $\gamma$,§5.4 的所有结论恢复成立。**代价:cir 配置表从"一个数"变成"$N_S$ 个数",仍然是初始化配一次、运行期零改动。**

**修法二(建议同时做):把 $V$ 提到 $\ge 500$。**

偏斜从 1.152 降到 1.085。这是纯客户端改动(ring 表大一点、查表慢一点),按本文的成本模型是最便宜的一档。$V = 1000$ 可以降到 1.06,但收益递减,500 是性价比拐点。

**修法三:盘数公式用 $\max_j p_j$。**

$$
N_S \;\ge\; \frac{N_P \cdot B_{req} \cdot \kappa_{ring}}{\rho \cdot BW_{ssd}}
$$

算例($\kappa_{ring} = 1.15$):$\dfrac{64 \times 8 \times 1.15}{0.7 \times 40} = \dfrac{588.8}{28} = 21.0$ → **21 块**(初版是 20 块)。

若同时做了修法二($V=500 \Rightarrow \kappa_{ring}=1.085$):$\dfrac{512 \times 1.085}{28} = 19.8$ → **20 块**,回到初版的数字。**这说明修法二不只是"锦上添花",它直接省了一块盘。**

#### 4.5.5 两种不均衡的对比总结

| | 随机抖动($\kappa$) | 环偏斜($\kappa_{ring}$) |
|---|---|---|
| 来源 | 每层只有 $n$ 个请求,样本量小 | 虚拟节点弧长不等 |
| 大小 | 1.56 ~ 2.5(d=2) | 1.06 ~ 1.28(取决于 $V$) |
| **会不会随时间平均掉** | **会** | **不会,永久固定** |
| 影响面 | 单个节点的某一层 | **所有节点的所有层** |
| 应对机制 | 令牌桶桶深 $\beta$ + 预取深度 $d$ + URGENT 通道 | **cir 按盘缩放** + 提高 $V$ |
| 配错的后果 | 偶发 stall | **系统性失速** |

**一句话**:$\kappa$ 决定你的**桶深和 pir** 怎么配,$\kappa_{ring}$ 决定你的 **cir 和盘数**怎么配。**两者用途不同,不能互相替代,初版把后者漏掉了。**

## 5. QoS 执行机构的数学模型

上一节说清了"需要什么",这一节说清"QoS 硬件能提供什么",以及两者怎么对上。

### 5.1 令牌桶:cir、pir、桶深 β 到底是什么

QoS Path 本质是一个**令牌桶(token bucket)**:

```
      cir 速率往桶里滴令牌
              │
              ▼
        ┌───────────┐
        │  ▓▓▓▓▓    │  ← 桶深 β(最多攒这么多令牌)
        │  ▓▓▓▓▓    │
        └─────┬─────┘
              │ 发 1 字节数据消耗 1 个令牌
              ▼
          数据出盘
```

- **cir(承诺速率)**:令牌的**滴入速率**。这是你的**长期保底带宽**——只要你不超过它,永远拿得到。
- **β(桶深)**:桶最多能攒多少令牌。你闲一会儿,桶就攒满;然后可以**瞬间**把攒的令牌一次花掉,这叫**突发**。
- **pir(峰值速率)**:突发时的**速度上限**。即使桶里有一大把令牌,也不能超过 pir 往外冲。

传输 $D$ 字节需要的时间近似为:

$$
T_r \approx \max\left(\frac{D}{pir},\; \frac{D - \beta}{cir}\right)
$$

**逐字解释**:如果 $D \le \beta$(要发的量比攒的令牌少),第二项是负的,取第一项——**以 pir 全速冲出去**。如果 $D > \beta$,超出桶深的那部分 $(D - \beta)$ 只能按 cir 的滴入速度慢慢发,所以取第二项。

**这告诉我们桶深该怎么配**:我们希望"某一层运气不好、多出来的那部分数据"能被桶吸收掉,即

$$
\beta \;\ge\; (\kappa - 1) \cdot \frac{D_L}{N_S}
$$

算例:$(1.97 - 1) \times \dfrac{64\text{ MB}}{20} = 0.97 \times 3.2 = $ **3.1 MB**。所以桶深配 4 MB 就够了。

> ⚠ **一个诚实的提醒**:令牌桶只能吸收"此消彼长"的抖动,**不能凭空创造带宽**。如果一个节点持续以超过 cir 的速率要数据,桶会被抽干,最终还是被 cir 限住。所以 cir **必须严格大于长期平均需求**,见 §5.3。

### 5.2 两级 WRR + RR:剩余带宽怎么分

硬件的调度是三层:**组内 WRR → 组间 WRR → 最后 RR**。

对于**超过 cir 的那部分**(即从盘的空闲带宽里"借"的部分),分配份额是:

$$
\text{share}_i = \underbrace{\frac{W_{g(i)}}{\sum_{g \in \mathcal{A}} W_g}}_{\text{组间}} \times \underbrace{\frac{w_i}{\sum_{j \in g(i),\, j \in \mathcal{A}} w_j}}_{\text{组内}} \times BW_{leftover}
$$

**逐字解释**:
- $W_g$ 是**组的权重**,$w_i$ 是**path 在组内的权重**。
- $\mathcal{A}$ 表示"当前有待发请求的"集合。**这一点非常关键**:WRR 轮转时会跳过空组/空 path,所以**给一个平时没流量的组配高权重,不会浪费带宽**。这正是我们敢给 URGENT 组配最高权重的原因。
- 两个分数相乘,是因为要先决定"这个组占多少",再决定"组里这条 path 占多少"。

数值例子:剩余带宽 6.8 GB/s,组权重 G0=8 / G1=4 / G2=2 / G3=1。若此刻只有 G1、G2 有流量:
- G1 得 $\frac{4}{4+2} = 66.7\%$ → 4.53 GB/s,64 条 path 平分 → 每条 0.071 GB/s
- G2 得 $\frac{2}{6} = 33.3\%$ → 2.27 GB/s

**权重的设定原则**:组内权重 $w_i \propto cir_i$。这样"保底大的,借得也多",比例公平。

### 5.3 排队模型:到底会不会 stall(这一节决定成败)

现在把需求和供给拼起来。定义**逐层递推**:

设第 $l$ 层落在某块盘上的数据量是随机变量 $A_l$,该盘这条 path 在一层时间内能服务的量是 $c = cir \cdot T_c$(固定)。那么积压(还没发完的数据)满足:

$$
Q_{l+1} = \max\big(0,\; Q_l + A_l - c\big)
$$

**逐字解释**:这叫 **Lindley 递推**。这一层结束时的积压 = 上一层剩下的积压 + 这一层新来的 − 这一层发走的。如果发得比来得多,积压清零(不能是负数),所以套一个 `max(0, ·)`。

**第一个结论(生死线)**:令 $\mu_B = E[A_l]$(平均每层每盘的数据量)。

$$
\boxed{\;c > \mu_B \;\text{(严格大于)}\;}
$$

如果 $c = \mu_B$ 或更小,积压会**无界增长**,NPU 必然越来越慢直至崩溃。这就是为什么 cir 必须**超配**,超配系数记为 $\gamma$:

$$
cir = \gamma \cdot \frac{\mu_B}{T_c}, \qquad \gamma > 1
$$

**第二个结论(平均积压)**:在重流量近似下,

$$
E[Q] \approx \frac{\sigma_B^2}{2\,(c - \mu_B)}
$$

**逐字解释**:$\sigma_B$ 是 $A_l$ 的标准差(波动幅度)。分子是波动的平方——**波动越大,积压越多,而且是平方关系,非常敏感**。分母是"每层的富余产能"——富余越多,积压越小。当富余趋近 0,积压趋于无穷,和上面的生死线一致。

平均等待时间:

$$
W = \frac{E[Q]}{cir}
$$

**要求**:$W \le T_{budget} = d \cdot T_c$。

**第三个结论(尾概率)**:排队论给出积压的尾巴近似是指数分布:

$$
P(Q > q) \approx \exp\left(-\frac{2\,(c - \mu_B)\,q}{\sigma_B^2}\right)
$$

**逐字解释**:积压超过 $q$ 的概率随 $q$ **指数衰减**。衰减快慢由 $\frac{2(c-\mu_B)}{\sigma_B^2}$ 决定——富余产能越多、波动越小,衰减越快,越不容易失约。

### 5.4 代入算例:三种配法的对比

先算参数:
- $\mu_B = \dfrac{D_L}{N_S} = \dfrac{64\text{ MB}}{20} = 3.2$ MB(每层每盘平均数据量)
- $\sigma_B = G \cdot \sqrt{\mu(1 - 1/N_S)} = 0.5\text{ MB} \times \sqrt{6.4 \times 0.95} = 0.5 \times 2.466 = 1.233$ MB

  (解释:请求数服从二项分布 $B(n, 1/m)$,标准差是 $\sqrt{n \cdot \frac 1m (1-\frac 1m)} = \sqrt{\mu(1-1/m)}$,再乘每个请求的字节数 $G$。)

**配法一(朴素):$\gamma = 1.00$,$d = 1$**

$c = \mu_B$ → 分母为 0 → $E[Q] \to \infty$。**系统崩溃**,NPU 利用率随时间趋于 0。

**配法二(保守):$\gamma = 1.05$,$d = 1$**

- $c = 1.05 \times 3.2 = 3.36$ MB,富余 $c - \mu_B = 0.16$ MB
- $E[Q] = \dfrac{1.233^2}{2 \times 0.16} = \dfrac{1.520}{0.32} = 4.75$ MB
- $cir = 1.05 \times 0.4 = 0.42$ GB/s = 430 MB/s
- $W = 4.75 / 430 = $ **11.05 ms**
- 预算 $= d \cdot T_c = 8$ ms → **11.05 > 8,系统性失速**
- 粗估 $U_{NPU} \approx \dfrac{8}{8 + 3.05} \approx \mathbf{72\%}$ ×

**配法三(推荐):$\gamma = 1.20$,$d = 2$**

- $c = 1.2 \times 3.2 = 3.84$ MB,富余 = 0.64 MB
- $E[Q] = \dfrac{1.520}{2 \times 0.64} = 1.19$ MB
- $cir = 1.2 \times 0.4 = 0.48$ GB/s = 491.5 MB/s
- $W = 1.19 / 491.5 = $ **2.42 ms**
- 预算 $= 2 \times 8 = 16$ ms → **2.42 ≪ 16,余量 6.6 倍** ✓
- 失约门限 $q = cir \times 16\text{ms} = 491.5 \times 0.016 = 7.86$ MB
- $P(Q > q) = \exp\left(-\dfrac{2 \times 0.64 \times 7.86}{1.520}\right) = e^{-6.62} = 1.33 \times 10^{-3}$
- 一层要跨 20 块盘,任一块失约的概率 = $1 - (1 - 0.00133)^{20} = 2.6\%$
- 80 层期望失约次数 = $80 \times 20 \times 0.00133 \approx 2.1$ 次,每次平均超时 ≈ $E[Q]/cir$ = 2.42 ms
- 总 stall ≈ $2.1 \times 2.42 = 5.1$ ms
- $U_{NPU} = \dfrac{640}{640 + 5.1} = \mathbf{99.2\%}$ ✓

**可行性验算**:$\Sigma cir = 64 \times 0.48 = 30.7$ GB/s ≤ $40 / \kappa_{agg} = 35.7$ GB/s ✓

**配法四(反例,必看):$\gamma = 1.20$、$d = 2$,但忽略环偏斜**

这是初版文档实际会配出来的东西。cir 仍是 0.48 GB/s,但最热盘的真实 $\mu_B = 3.68$ MB:

- 富余 $= 3.84 - 3.68 = 0.16$ MB(不是 0.64!)
- $E[Q] = \dfrac{1.322^2}{2 \times 0.16} = 5.46$ MB,$W = 11.1$ ms
- 尾概率 $= \exp\left(-\dfrac{2 \times 0.16 \times 7.86}{1.748}\right) = e^{-1.44} = \mathbf{23.7\%}$

**同一个 $\gamma$,只因为分母用错了均值,失约率从 0.13% 变成 23.7%,差了 180 倍。** 详见 §4.5。修法:$cir_j = \gamma B_{req} p_j$。

### 5.5 三个旋钮及其代价

| 旋钮 | 效果 | 代价 |
|---|---|---|
| $\gamma$ ↑(cir 超配) | 富余产能 ↑,积压平方级下降 | $\Sigma cir$ 上升,**要加盘**(最贵) |
| $d$ ↑(预取深度) | deadline 预算线性放大 + $\kappa$ 下降 | 客户端多 $(d+1)D_L$ 缓存(**最便宜**) |
| URGENT 逃生通道 | 把那 $10^{-3}$ 的尾部救回来 | 多占 1 组 + 少量 path(**便宜**) |

> **设计哲学**:先把 $d$ 拉满到内存能承受的程度(2~4 层),再用适度的 $\gamma$(1.15~1.25),最后用 URGENT 通道兜住尾巴。**不要靠堆 cir 硬扛**,那是在烧盘。

## 6. 设计空间:三个正交的轴

所有方案都是这三个轴的组合:

| 轴 | 选项 | 复杂度代价 |
|---|---|---|
| **X. 谁决定 SQE 进哪条 path** | X1 客户端填 DW2(静态查表)<br>X2 客户端填 DW2(按 slack 判断)<br>X3 盘框 CPU 在数据面改写 | X1 极低<br>X2 低<br>X3 **极高(不可行,见 §7.3)** |
| **Y. P 节点 ↔ path 的映射** | Y1 静态 1:1<br>Y2 静态 1:k(按 deadline 分级)<br>Y3 运行期动态重绑<br>Y4 主备 | Y1 极低<br>Y2 低<br>Y3 高<br>Y4 中 |
| **Z. cir/pir/权重** | Z1 初始化一次,永不改<br>Z2 控制面按 ms 级闭环调整 | Z1 零<br>Z2 中(盘框 CPU + 配置写) |

> **复杂度权重提醒**(按你的约束):给 SSD 下配置 = 高成本操作;客户端代码 = 低成本。所以我们**尽量把智能放在客户端的"选路"上,尽量少动 SSD 的配置**。

## 7. 候选方案 A ~ F

### 7.1 方案 A:静态 1:1 + 固定参数(X1 + Y1 + Z1)—— 基线

**结构**:初始化时给每个 P 节点分配一条固定的 path id。客户端在每个 KV SQE 的 DW2 里填这个常量,一辈子不变。SSD 上每条 path 配一次 cir/pir/桶深,之后不再触碰。

**参数配法**(直接用 §5.4 配法三):

$$
cir_i = \gamma \cdot \frac{B_{req,i}}{N_S},\quad pir_i = 3 \sim 4 \times cir_i,\quad \beta_i = (\kappa - 1)\frac{D_L}{N_S}
$$

算例:cir = 0.48 GB/s,pir = 1.6 GB/s,β = 4 MB。所有 64 条 path 参数相同,组内权重全为 1。

**优点**
- 复杂度地板级:SSD 只配一次;客户端只填一个常量;盘框 CPU 完全不参与。
- 隔离性天然完美:节点之间靠硬件 path 物理隔离,一个节点抖不影响别人。
- 估算 $U_{NPU} \approx 99.2\%$(见 §5.4)。

**缺点**
- **无法表达"同一个节点内部的轻重缓急"**。层 k+1 的数据(马上要用)和层 k+4 的推测性预取,走同一条 path、抢同一个令牌桶,**先进先出**。这意味着一个不着急的大块预取可能把令牌桶抽干,把着急的数据挡在后面(**队头阻塞**)。
- 命中率 $H$ 变化时($B_{req}$ 变化 2 倍很常见)完全靠 pir 硬扛,配不准。
- 那 $1.3\times10^{-3}$ 的失约尾巴没有任何补救手段。

**适用**:节点负载高度同质、命中率稳定、且你想要"绝对最简单"的场景。作为其他方案的对照基线。

---

### 7.2 方案 B:静态 1:k deadline 分级映射(X2 + Y2 + Z1)—— ★ 推荐一

**核心思想**:把方案 A 的缺点(无法表达轻重缓急)用**硬件已经给好的"8 个组"**解决掉。组间 WRR 天然就是一个优先级阶梯,**用它来编码 deadline 等级**。

**结构**:每个 P 节点绑 **3 条 path**,分别落在 3 个不同的组:

| 组 | 语义 | 装什么数据 | cir | pir | 组权重 $W_g$ |
|---|---|---|---|---|---|
| **G0 = URGENT** | 剩余 slack ≤ 1 层 | 层 k+1 尚未到齐的**残余** block | 极小 | 极大 | 8(最高) |
| **G1 = NORMAL** | slack = 2 ~ d 层 | 正常的 layerwise 预取主流量 | 主体 | 3~4× cir | 4 |
| **G2 = BULK** | slack > d 层 / 推测性 | 深度预取、整请求预热 | 0 | 中 | 2 |
| **G3 = WRITE** | 无 deadline | KV dump、迁移、GC | 0 | 小 | 1 |
| G4~G7 | 预留 | 多租户隔离 / 管理面 / 扩展 | — | — | — |

**客户端要做的事(这就是全部)**:

> 对每个待发的 KV block 请求,算一个 slack(还剩几层要用),按上表查出组号,DW2 = `组基址 + 本节点 path 序号`。
>
> slack 的计算就是"目标层号 − 当前层号"。层号是循环里的计数器,**一次减法 + 一次三分支比较 + 一次查表**。这是客户端侧成本的全部,量级 ~10 行逻辑,零状态、零通信。

**为什么这样能大幅降低 stall——定量说明**

方案 A 的问题是所有数据混在一个桶里。方案 B 把"来不及的那一小撮"单独拎出来走 G0,而 G0 的量有多小?

设 NORMAL 通道的服务速率是 $c = \gamma \mu_B$,则平均每层"没发完、要转 URGENT"的量是二项分布的**超均值期望**:

$$
E\big[(A - c)^+\big] \;\approx\; \sigma_B \cdot \phi(z) - (c - \mu_B) \cdot \big(1 - \Phi(z)\big),\quad z = \frac{c - \mu_B}{\sigma_B}
$$

其中 $\phi$ 是标准正态的**概率密度**,$\Phi$ 是**累积分布**。这个式子叫"正态分布的部分期望"。

**逐字解释**:$(A - c)^+$ 表示"超出服务能力的部分,不足则记 0"。$z$ 是把"富余产能"换算成"多少个标准差"。$z$ 越大,超出的期望越小。

代入 $z = \dfrac{0.64}{1.233} = 0.519$:$\phi(0.519) = 0.3477$,$1 - \Phi(0.519) = 0.3019$

$$
E[(A-c)^+] = 1.233 \times 0.3477 - 0.64 \times 0.3019 = 0.4287 - 0.1932 = 0.235 \text{ MB}
$$

占该盘每层数据量 $\mu_B = 3.2$ MB 的 **7.3%**。

所以 **URGENT 组只需要承担约 7% 的流量**,但它享有最高的组权重。给 G0 配:

- 每条 path:$cir = 0.06$ GB/s(≈ 12% 的 NORMAL cir),$pir = 4$ GB/s(几乎不限),$\beta = 1$ MB
- $\Sigma cir_{G0} = 64 \times 0.06 = 3.84$ GB/s(占盘的 9.6%,对 7% 的需求有 1.4× 裕量)

**效果**:原本会失约的那 $1.33\times10^{-3}$ 事件,现在会被 G0 以最高优先级抢救。G0 的排队时延上界(组权重 8,基本独占剩余带宽):

$$
T_{G0} \le \frac{Q_{G0}}{cir_{G0} + \text{share}_{G0} \cdot BW_{leftover}}
$$

代入:$Q_{G0} \approx 0.235$ MB,$cir_{G0} = 61.4$ MB/s,leftover ≈ 6.8 GB/s 中 G0 占 8/15 → 3.6 GB/s = 3686 MB/s。

$$
T_{G0} \le \frac{0.235}{61.4 + 3686} = 0.063 \text{ ms}
$$

**0.063 ms,相对 8 ms 的层时间完全可以忽略。** 失约事件基本被完全抵消。

估算 $U_{NPU} \approx \mathbf{99.8\%}$。

**优点**
- SSD 侧仍然是**初始化配一次,运行期零配置写**,完全满足"不要动态实时设置"的约束。
- 客户端增量成本 ≈ 0。
- 彻底消除队头阻塞:着急的数据和不着急的数据物理分离在不同令牌桶。
- 8 个组的语义清晰,便于后续扩展(多租户、优先级 SLO)。
- **利用了硬件本来就有的能力**,没有引入任何新机制。

**缺点**
- path 消耗 3 倍。$N_P \le 85$ 时完全够用;更多节点要降级(见 §9.2 分档表)。
- 仍然不能自适应命中率漂移(这正是方案 E 要补的)。

### 7.3 方案 C:盘框 CPU 数据面重映射(X3)—— 能做,但不划算

**结构设想**:客户端在 DW2 里只填**语义标签**(如"带宽需求 = 0.5 GB/s,deadline 等级 = 紧急"),盘框侧 CPU 拿到 SQE 后,查全局负载表,把它**改写**成某条物理 path id,再送进 SSD。这就是"类 DRB"的集中式动态资源均衡思路。

#### 7.3.1 先纠正一个常见的误判:CPU 并不在数据面上

一个容易犯的错误(本文档初版就犯了)是这样算的:20 块盘 × 40 GB/s = 800 GB/s 聚合流量压在 CPU 上,除以 512 KB 得 164 万 IOPS,于是宣布"不现实"。

**这个算法是错的,而且错在概念上。** 如果 CPU 只负责**选路**,它碰的是 **SQE 描述符**(约 64 字节),数据仍然由 SSD 直接 DMA 回客户端内存,**CPU 一个字节的用户数据都不碰**。所以要算的是**命令面**的速率,不是数据面的带宽。而且基数应该用**实际负载 512 GB/s**,不是线速 800 GB/s。

正确的账:

| 块粒度 $G$ | 全系统 SQE/s | 单盘 SQE/s | 描述符带宽(64 B/SQE) |
|---|---|---|---|
| 512 KB | 1.05 M | 52 K | 0.067 GB/s |
| 256 KB | 2.10 M | 105 K | 0.134 GB/s |
| 128 KB | 4.19 M | 210 K | 0.268 GB/s |
| 64 KB | 8.39 M | 419 K | 0.537 GB/s |
| 16 KB | 33.6 M | 1.68 M | 2.147 GB/s |

**单盘 52 K SQE/s、67 MB/s 描述符流量,一个轮询核轻松吃下。** 只有当块粒度掉到 16 KB 量级时,速率才真的难看。

**同理,"时延预算不允许"也站不住**:$d=2$ 给了 16 ms 的 deadline 预算,存转发多加 2~5 μs 是预算的 0.03%,哪怕 200 μs 的长尾也只占 1.25%。

> **所以:方案 C 在工程上是做得出来的。** 否掉它的理由必须是别的。

#### 7.3.2 真正该否掉它的三个理由

**理由一(最根本):盘框 CPU 没有任何信息优势。**

问一个问题:**CPU 知道而客户端不知道的信息是什么?** 只有一样——"别的节点此刻压了多少"。

但这恰恰是 **QoS 硬件在纳秒粒度、零陈旧度上仲裁的事**。CPU 拿到的是微秒级的过期快照,而且它只能在**命令提交时刻**做一次性决策,之后就管不着了;硬件调度器则是在**每个传输周期**都在重新仲裁。**CPU 在自己最弱的维度上,去替代硬件最强的能力。**

反过来问:**决定这个 block 该走哪条路,最关键的信息是什么?** 是它的 **slack(还剩几层要用)**。而这个信息**只有客户端有**——它是客户端的循环计数器,CPU 无从得知,除非客户端显式告诉它(那还不如客户端自己直接填 path id)。

**结论:有用的信息本来就在正确的一侧。把决策搬到 CPU,是拿走了唯一有用的信息,换来了一份过期的、硬件已经在用的信息。这是净损失。**

**理由二:它需要的是新硬件特性,不是配置。**

要让这条路走通,SSD 必须:接受**第三方**提交的命令(不是发起 IO 的那个客户端)、决定 CQE 回给谁、并实现一层"语义标签 → 物理 path"的间接映射。这些都不在现有 QoS 硬件的能力范围内。

按本文的成本模型,**"给 SSD 下配置"已经算高成本操作,"给 SSD 加一个新的命令间接层"要比它高一个数量级**。

**理由三:单点与序列化点。**

所有命令过一个实体。它挂了,整个盘框停摆;它慢了,所有节点一起慢。而方案 B 里客户端各自填 DW2,故障域被天然隔离在单个节点内。

#### 7.3.3 结论

**数据面选路应当在客户端完成**,DW2 直接填物理 path id。盘框 CPU 定位为**观测者**(采集统计、算参数、写配置),而不是**转发者**。

注意这个结论比初版弱:不是"物理上做不到",而是"**做得到,但要付新硬件特性的代价,换来的是零收益甚至负收益**"。如果将来出现某种场景,客户端确实无法得知选路所需的信息(比如跨租户的全局公平性仲裁),这个方案值得重新评估。

### 7.4 方案 C′:盘框 CPU 控制面换绑(Y3 的轻量版)—— 可选增强

把 C 降级:CPU 不碰数据面,只在发现某条 path 长期过载/欠载时,通过**带外的控制通道**通知客户端"你的 NORMAL path 从 #37 换到 #52"。换绑频率是秒级或分钟级。

**评价**:在本场景中**收益很小**。因为 ring hash 已经把负载均匀打散了,不存在"某个节点固定压垮某条 path"的情况;而 path 是节点私有的,换到哪条都一样。**除非**出现:
- 某条 path 对应的硬件资源(如某个队列)出现故障;
- 引入了异构节点(不同模型/不同 SLO 的租户混跑)。

**结论**:作为**故障容错**手段保留(path 级故障切换),不作为性能手段。

---

### 7.5 方案 D:纯闭环调参(X1 + Y1 + Z2)

**结构**:绑定关系保持静态 1:1,盘框 CPU 每 $\Delta$ 毫秒:
1. 读取每条 path 的 IOPS/带宽统计;
2. 结合客户端在 KV SQE 里申报的带宽需求;
3. 跑一次分配算法,算出新的 cir/pir/权重;
4. 写回 SSD。

**优点**:能跟随命中率、chunk 大小、节点相位的变化,把利用率目标 $\rho$ 从 0.7 提到 0.85,等价于**省 18% 的盘**。

**缺点**
- **控制周期 $\Delta$(20~50 ms)比层时间 $T_c$(8 ms)慢 3~6 倍**。这意味着闭环**根本追不上层级抖动**,它只能处理慢漂移。如果你指望它解决 §4 的短期不均衡,会失望。
- 单独使用时,仍然存在方案 A 的队头阻塞问题(同一节点的紧急/非紧急数据混在一条 path)。
- 有振荡风险,需要阻尼设计。

**结论**:**不要单独用 D**。它应该叠在 B 的骨架上 → 方案 E。

---

### 7.6 方案 E:方案 B 的骨架 + 慢速闭环(X2 + Y2 + Z2)—— ★★ 推荐二

- **绑定关系**:完全沿用方案 B,静态 1:3,运行期不变 → 客户端代码与 B 完全相同,零增量。
- **参数**:NORMAL 组的 cir/pir/组内权重由盘框 CPU 每 50 ms 用 max-min fair 重算;URGENT / BULK / WRITE 组的参数**保持静态**(它们的量小且不敏感,不值得动)。
- **写配置预算**:加死区过滤后,实测通常每周期只需要写个位数条 path。

**分工是清晰的**:

| 时间尺度 | 谁负责 | 机制 |
|---|---|---|
| 微秒 ~ 层内(< 8 ms) | 硬件 | 令牌桶桶深 β 吸收突发 |
| 层级(8 ~ 16 ms) | 客户端 | 预取深度 d + URGENT 逃生通道 |
| 十层级(50 ms ~ 秒) | 盘框 CPU | 闭环调 cir/pir/权重,跟随需求漂移 |

**这个三层分工是方案 E 的精髓**:每一层只解决它这个时间尺度上的问题,不越界。

详见 §10。

---

### 7.7 方案 F:主备 / 逃生 path(Y4)—— 作为 B 和 E 的子机制

严格意义的"主备"(备用 path 平时闲置,主 path 故障才切)在本场景**没有性能价值**,因为 path 本身不会故障,且闲置一条 path 是纯浪费。

但把它改造成**逃生通道**就非常有价值——这正是方案 B 的 G0(URGENT)组在做的事。区别在于:

| | 传统主备 | 逃生通道(推荐) |
|---|---|---|
| 备用 path 平时 | 完全闲置 | 承载 ~7% 的紧急残余流量 |
| 触发条件 | 主路故障 | 层边界检查发现预取落后 |
| cir 配置 | 与主路相同(浪费) | 极小(0.06 GB/s) |
| pir 配置 | 与主路相同 | 极大(4 GB/s) |
| 风险 | 无 | **所有节点同时逃生 → 逃生通道自己拥塞** |

**必须配的准入限制**(否则逃生通道会被打爆):

1. **硬上限**:$\Sigma cir_{G0} \le 0.10 \times BW_{ssd}$。这是硬件配置,天然封顶。
2. **客户端自律**:一个节点在连续 $L$ 层中,走 URGENT 的层数占比不超过阈值 $\theta$(建议 15%)。超过说明是**系统性欠配**,不是偶发抖动——应该报警,让运维加 cir 或加盘,而不是继续逃生。
3. **单次限量**:一次逃生最多提交 $\beta_{G0}$ 字节(= 1 MB),超过的部分留在 NORMAL 通道。防止某个节点把整层数据都塞进 URGENT。

## 9. 推荐方案一:方案 B(静态 deadline 分级)详解

### 9.1 8 个组的语义划分

硬件给了"8 组、组内 WRR、组间 WRR、最后 RR"这样一个两级层次。**最自然的用法是把"组"当作 deadline 等级(SLO class),把"组内 path"当作租户/节点隔离。**

```
                    ┌─────────────────── SSD 出口 40 GB/s ───────────────────┐
                    │                                                        │
         组间 WRR   │  W=8      W=4        W=2       W=1     (空组自动跳过)  │
                    │   │        │          │         │                      │
              ┌─────┴──┐ ┌──────┴───┐ ┌────┴────┐ ┌──┴─────┐                 │
```

### 9.3 参数配置手册(手把手)

**第 1 步:测出 $T_c$**

离线 profiling,建一张表 `T_c(chunk_size, prefix_len)`。这是唯一必须实测的量,不能算。

**第 2 步:枚举哈希环,拿到每块盘的份额 $p_j$**

初始化时把 ring 上所有虚拟节点的弧长累加一遍,得到 $p_1 \dots p_{N_S}$(精确值,无需测量)。同时检查 $\kappa_{ring} = N_S \max_j p_j$:**若 $> 1.10$,先把虚拟节点数 $V$ 提到 500 再往下走**(见 §4.5)。

**第 3 步:算 NORMAL 组的 cir —— 按盘缩放**

$$
cir_{G1,j} = \gamma \cdot \frac{B_{req} \cdot p_j}{1},\qquad \gamma \in [1.15,\, 1.25]
$$

**注意分母不是 $N_S$ 而是用 $p_j$ 直接乘。** 这是 §4.5 的核心修正——用 $1/N_S$ 会让最热盘的有效超配塌缩到 1.04,失约率飙到 23.7%。

算例(理想均匀 $p_j = 0.05$):$1.2 \times 8 \times 0.05 = 1.2 \times 0.4 = \mathbf{0.48\ GB/s}$

算例(最热盘 $p_j = 0.0576$,即 $\kappa_{ring}=1.15$):$1.2 \times 8 \times 0.0576 = \mathbf{0.553\ GB/s}$

> 这意味着**每块盘有自己的一张 cir 表**。仍然是初始化下发一次、运行期零改动,只是配置量从 1 个数变成 $N_S$ 个数。

**第 4 步:算 NORMAL 组的 pir**

pir 要能覆盖 $\kappa$ 倍的峰值,再留点余量:

$$
pir_{G1} = \max\left(3 \cdot cir_{G1},\; \kappa \cdot \frac{D_L}{N_S \cdot T_c}\right)
$$

算例:$\max(3 \times 0.48,\; 1.68 \times 0.4) = \max(1.44,\, 0.67) = \mathbf{1.44\ GB/s}$,取整到 **1.6 GB/s**。

> 为什么可以配这么大?因为 $\Sigma pir = 64 \times 1.6 = 102$ GB/s,是线速的 2.5 倍。这个**超配是有意为之**——统计复用告诉我们大家不会同时冲顶(§4.4)。

**第 5 步:算桶深 β**

$$
\beta_{G1} \ge (\kappa - 1) \cdot \frac{D_L}{N_S}
$$

算例:$(1.68 - 1) \times \dfrac{64}{20} = 0.68 \times 3.2 = 2.18$ MB → 取 **4 MB**(向上取整到 2 的幂,留一倍余量)。

**第 6 步:配 URGENT 组**

$$
cir_{G0} = 0.12 \times cir_{G1} = 0.058 \to \mathbf{0.06\ GB/s},\quad pir_{G0} = \mathbf{4\ GB/s},\quad \beta_{G0} = \mathbf{1\ MB}
$$

校验硬上限:$\Sigma cir_{G0} = 64 \times 0.06 = 3.84$ GB/s $\le 0.10 \times 40 = 4$ GB/s ✓

**第 7 步:配 BULK / WRITE**

$cir = 0$(或极小值 0.02 GB/s 防饥饿),$pir = 0.5$ GB/s,$\beta = 1$ MB。它们只吃剩余带宽。

**第 8 步:配权重**

- 组间:$W_{G0} : W_{G1} : W_{G2} : W_{G3} = 8 : 4 : 2 : 1$
- 组内:同质节点全部为 1(均分)。异质场景下 $w_i \propto cir_i$。

**第 9 步:总校验(必须按最热盘算)**

校验必须落在 $p_j$ 最大的那块盘上,因为它的 $\Sigma cir$ 最大:

$$
\Sigma cir_{j^*} = \underbrace{64 \times 0.553}_{G1} + \underbrace{64 \times 0.069}_{G0} + \underbrace{\approx 0.7}_{G2,G3} = 35.4 + 4.4 + 0.7 = 40.5 \text{ GB/s}
$$

约束是 $\Sigma cir \le BW_{ssd} / \kappa_{agg} = 40/1.12 = 35.7$ GB/s。**40.5 > 35.7 × 不通过!**

**这就是 §4.5 修法三存在的原因**:$\kappa_{ring} = 1.15$ 时 20 块盘不够,必须加到 21 块。加到 21 块后 $p_{j^*} = 1.15/21 = 0.0548$:

$$
\Sigma cir_{j^*} = 64 \times (1.2 \times 8 \times 0.0548) + 64 \times 0.063 + 0.7 = 33.7 + 4.0 + 0.7 = 38.4 \text{ GB/s}
$$

仍然 $> 35.7$。**再把 $V$ 提到 500**($\kappa_{ring}=1.085$,$p_{j^*} = 1.085/20 = 0.0543$,回到 20 块盘):

$$
\Sigma cir_{j^*} = 64 \times (1.2 \times 8 \times 0.0543) + 64 \times 0.0625 + 0.7 = 33.4 + 4.0 + 0.7 = 38.1 \text{ GB/s}
$$

还是超。**最终收敛的配置是:$V = 500$ + $N_S = 21$ 块**,此时 $p_{j^*} = 1.085/21 = 0.05167$:

$$
\Sigma cir_{j^*} = 64 \times 0.496 + 64 \times 0.060 + 0.7 = 31.7 + 3.8 + 0.7 = \mathbf{36.2} \text{ GB/s}
$$

距 35.7 还差一点,把 $\gamma$ 从 1.20 降到 1.17 即可: $\Sigma cir_{j^*} = 35.4$ GB/s ✓ **通过**。

> **这一串迭代本身就是本节最有价值的部分。** 它说明 $\gamma$、$V$、$N_S$ 三个参数是**耦合**的,不能各自拍脑袋:提高 $V$ 能省盘,省下的盘又允许更大的 $\gamma$,而 $\gamma$ 直接决定失速率。建议把这段做成一个小脚本,输入 $(N_P, B_{req}, BW_{ssd}, \kappa_{agg})$,输出满足约束的 $(V, N_S, \gamma)$ 组合。

**最终参数表**($V=500$,$N_S=21$,$\gamma=1.17$;cir 一列**按盘的 $p_j$ 缩放**,下表给的是 $p_j = 1/N_S$ 的标称值)

| 组 | path 数 | cir(GB/s) | pir(GB/s) | β(MB) | 组权重 | 组内权重 |
|---|---|---|---|---|---|---|
| G0 URGENT | 64 | $0.12 \times cir_{G1,j}$ ≈ 0.053 | 4.0 | 1 | 8 | 1 |
| G1 NORMAL | 64 | $1.17 \times B_{req} \times p_j$ ≈ 0.446 | 1.6 | 4 | 4 | 1 |
| G2 BULK | 64 | 0.02 | 0.5 | 1 | 2 | 1 |
| G3 WRITE | 32(共享) | 0.00 | 0.5 | 1 | 1 | 1 |

**这张表在初始化时下发一次,运行期一个字都不改。** 每块盘的 cir 列因 $p_j$ 而略有不同,其余各列所有盘一致。

### 9.4 客户端侧要做的事(软件层描述,无代码)

客户端持有一张初始化时下发的映射表:`{URGENT_base, NORMAL_base, BULK_base, WRITE_base, my_index}`。

对每一个待发的 KV block 读请求:

1. **算 slack** = 目标层号 − 当前正在计算的层号。
2. **查表定组**:slack ≤ 1 → URGENT_base;2 ≤ slack ≤ d → NORMAL_base;slack > d → BULK_base。
3. **组装 KV SQE**,DW2 = `组基址 + my_index`,其余字段按 UCM kv client 原语义填写。
4. **经华为 UB 下发**到 ring hash 定位到的那块 SSD。

层边界检查(每层做一次):如果层 k+1 还有未到齐的 block,把这些**残余** block 用 URGENT 组基址**重发**(或标记为紧急)。这是唯一需要新增的状态:一个"本层未完成 block"的计数/位图。

> 客户端复杂度小结:**一次减法、一次三分支比较、一次加法、一个位图**。无网络交互、无全局状态、无锁。

### 9.5 为什么方案 B 能最大化 NPU 利用率

三条独立的机制叠加:

1. **预取深度 $d$ 把 deadline 预算放大 $d$ 倍**(§2.3)。$W = 2.42$ ms vs 预算 16 ms,余量 6.6 倍。
2. **消除队头阻塞**。深度预取(BULK)和即刻需要的数据(NORMAL)在**不同的令牌桶**里,BULK 抽干自己的桶不会影响 NORMAL 的滴入。方案 A 里这两类混在一起,BULK 的大块传输会把 NORMAL 的数据顶在队列后面——这在 IO 尺寸大(512 KB)时是实打实的毫秒级延迟。
3. **URGENT 通道把统计尾部拉回来**。$1.33\times10^{-3}$ 的失约事件被 0.063 ms 的高优先级抢救覆盖,几乎完全抵消(§7.2)。

$$
U_{NPU}^{(B)} \approx \frac{640}{640 + 5.1 \times 0.05} = \frac{640}{640.26} \approx \mathbf{99.96\%}
$$

(保守起见按 99.8% 报,因为模型没有涵盖 UB 抖动、盘内 GC 等因素。)

**而这一切的代价是:SSD 侧零运行时配置,客户端侧十行逻辑。** 这就是它好的原因——**收益全部来自"正确使用已有硬件语义",而不是引入新机制**。

## 10. 推荐方案二:方案 E(B 的骨架 + 慢速闭环)详解

### 10.1 什么时候需要它

方案 B 的软肋是**必须按最坏情况配 cir**。现实中各 P 节点的 prefix 命中长度 $H$ 差异很大(短对话 vs 长文档 RAG,可能差 3 倍)。静态方案要保证最坏的节点不失速,就得给**所有**节点配最坏情况的 cir。

**定量代价**:设 $H \in [8\text{K}, 24\text{K}]$,均值 16K。

| | 静态(方案 B) | 闭环(方案 E) |
|---|---|---|
| 配 cir 的依据 | $H_{max} = 24$K → $B_{req} = 12$ GB/s | 实时需求,均值 8 GB/s |
| 每节点每盘 cir | $1.2 \times 12 / N_S$ | 按实际分配 |
| 所需 $N_S$ | $\dfrac{64 \times 1.2 \times 12}{35.7} = \mathbf{26}$ 块 | $\dfrac{64 \times 8 \times 1.12}{40} \approx 14.3 \to \mathbf{18}$ 块(含裕量) |
| **省盘** | — | **31%** |

> 换算成钱:26 块 vs 18 块,省 8 块企业级 SSD 及其槽位/功耗。这就是闭环的全部价值——**它买的不是利用率,是硬件成本**。

### 10.2 控制环结构

```
   ┌──────────── 每 Δ = 50 ms 一轮 ────────────┐
   │                                            │
   ▼                                            │
① 采集:盘框 CPU 读每条 path 的 byte counter    │
   → 实测服务速率 s_i、积压指示                 │
   │                                            │
   ▼                                            │
② 申报:客户端在 KV SQE 的带宽需求字段          │
   携带量化后的 B_req(每层带一次即可,          │
   不必每个 SQE 都带)                          │
   │                                            │
   ▼                                            │
③ 平滑:EWMA 得到需求估计 r̂_i                  │
   │                                            │
   ▼                                            │
④ 分配:加权 max-min fair 算出 alloc_i          │
   │                                            │
   ▼                                            │
⑤ 过滤:死区 + 限幅 + 写次数预算                │
   │                                            │
   ▼                                            │
⑥ 下发:只写变化超过死区的那几条 path ──────────┘
```

**注意 ① 和 ② 是互补的**:① 看到的是"实际拿到了多少"(可能被 cir 卡住,低于真实需求),② 看到的是"想要多少"。只有两者结合才能区分"这条 path 不忙"和"这条 path 被饿着"。

$$
\hat{r}_i = \max\big(s_i,\; \text{declared}_i\big)
$$

### 10.3 加权 max-min fair:手把手推导

**问题**:一块盘有 $C$ 的带宽,$n$ 条 path 各自申报需求 $r_1 \dots r_n$,而 $\sum r_i > C$(僧多粥少)。怎么分才"公平"?

**"渐进注水(progressive filling)"算法——用生活比喻理解**:

> 想象你给 $n$ 个杯子同时注水,**水位同步上升**。
> - 有的杯子矮(需求小),先注满 → 它就"封顶"了,不再给它加水。
> - 剩下的杯子继续同步涨水位。
> - 一直涨到水用完为止。

这样的结果是:**所有还没满的杯子,水位一样高**。这个共同水位叫 $\theta$。

**数学表达**:

$$
\text{alloc}_i = \min(r_i,\; \theta), \qquad \text{其中 } \theta \text{ 满足 } \sum_{i=1}^{n} \min(r_i, \theta) = C
$$

**逐字解释**:每条 path 拿到的 = "它想要的"和"公共水位"两者中的**较小值**。需求小于水位的,全额满足;需求大于水位的,被削到水位。$\theta$ 由"总和恰好等于容量"这个条件唯一确定。

**加权版本**(不同 path 有不同权重 $w_i$,比如高优先级租户):

$$
\text{alloc}_i = \min(r_i,\; w_i \cdot \theta), \qquad \sum_i \min(r_i, w_i\theta) = C
$$

**手算例子**

$C = 40$ GB/s,8 条 path 的需求(GB/s):`0.5, 1, 2, 4, 8, 10, 12, 15`,总和 52.5 > 40。权重全为 1。

**第 1 轮试探**:假设 $\theta = 8$
- 需求 ≤ 8 的:0.5, 1, 2, 4, 8 → 全额满足,合计 **15.5**
- 需求 > 8 的:10, 12, 15 → 各拿 8,合计 **24**
- 总计 = 39.5,**比 40 少 0.5**,说明水位还能再涨一点

**第 2 轮试探**:假设 $\theta = 8.5$
- 需求 ≤ 8.5 的还是那 5 条,合计 15.5
- 剩 3 条各拿 8.5 → 25.5
- 总计 = 41.0,**超了**

**第 3 轮:直接解方程**。已知封顶集合是 {0.5, 1, 2, 4, 8}(合计 15.5),未封顶的有 3 条:

$$
15.5 + 3\theta = 40 \;\Longrightarrow\; \theta = \frac{24.5}{3} = 8.167
$$

验证 $8 \le 8.167 \le 10$ ✓(水位确实在"第 5 个杯子已满、第 6 个还没满"之间)

**最终分配**:`0.5, 1, 2, 4, 8, 8.167, 8.167, 8.167`,合计 40.0 ✓

**这个结果的公平性直觉**:小户全额拿到(0.5 的那位一点没被削),大户被平均削到同一水位(10/12/15 都变成 8.167)。**没有任何一条 path 可以在不损害比它拿得少的 path 的前提下拿到更多**——这就是 max-min fair 的定义。

**映射到硬件参数**:

$$
cir_i = 0.95 \times \text{alloc}_i, \qquad pir_i = \min\big(r_i,\ 3\,\text{alloc}_i\big), \qquad w_i = \text{round}\!\left(\frac{\text{alloc}_i}{\min_j \text{alloc}_j}\right)
$$

(cir 乘 0.95 是给硬件量化误差和统计误差留的安全边;$w_i$ 要裁剪到硬件支持的权重范围内。)

### 10.4 平滑、死区、写次数预算

**EWMA 平滑**(指数加权移动平均):

$$
\hat{r}_i(t) = \alpha \cdot r_i^{obs}(t) + (1 - \alpha)\cdot \hat{r}_i(t-1),\qquad \alpha = 0.3
$$

**逐字解释**:新的估计 = 30% 的新观测 + 70% 的旧估计。$\alpha$ 越大越灵敏,但也越容易被单次噪声带偏。

**时间常数**(响应速度):

$$
\tau = \frac{\Delta}{\alpha} = \frac{50\text{ ms}}{0.3} \approx 167\text{ ms}
$$

意思是:需求发生阶跃变化后,大约 167 ms 后估计值追上 63%,约 500 ms 追上 95%。**对"命中率漂移"这类慢变化足够快,对"层级抖动"则完全跟不上——这正是我们要的**(层级抖动交给令牌桶,别让闭环去追,追必振荡)。

**死区(dead-band)**:

$$
\text{只有当 } \frac{|cir_i^{new} - cir_i^{old}|}{cir_i^{old}} > \delta \text{ 时才下发},\qquad \delta = 0.15
$$

**逐字解释**:变化不到 15% 就不管。这一条把配置写次数砍掉一个数量级。

**限幅(slew-rate limit)**:

$$
cir_i^{new} \leftarrow \text{clip}\big(cir_i^{new},\ 0.7\,cir_i^{old},\ 1.3\,cir_i^{old}\big)
$$

单次最多变化 ±30%,防止过冲。

**保底下限(最重要的安全性质)**:

$$
cir_i^{new} \ge 0.8 \times cir_i^{static}
$$

其中 $cir_i^{static}$ 是方案 B 算出来的静态值。**这意味着:如果盘框 CPU 挂了、配置下发失败、或者闭环算错了,系统会退化到方案 B,而不是崩溃。** 这是方案 E 相对纯方案 D 的关键优势。

**写次数预算**:每周期按 $|\Delta cir_i|$ 排序,只写 Top-$K$ 条($K = 16$)。剩下的等下一周期。

估算:64 条 NORMAL path,稳态下需求变化超过 15% 死区的通常只有个位数条。**每 50 ms 写 3~8 条配置**,完全在"毫秒级设置"的能力范围内。

### 10.5 稳定性:为什么不会振荡

三重保险:

1. **时间尺度分离**。控制周期 50 ms,被控对象(需求漂移)的时间常数是秒级。**控制器比扰动慢,比被控量的慢分量快** —— 这是控制论里最舒服的位置。层级抖动(8 ms)在闭环眼里是高频噪声,被 EWMA 直接滤掉。
2. **环路增益 < 1**。$\alpha = 0.3$ 的低通 + 30% 限幅,单周期的有效增益约 $0.3 \times 1.3 = 0.39 < 1$,一阶系统必然收敛。
3. **死区消除极限环**。没有死区的比例控制器在量化系统里会在两个相邻量化值之间来回跳(极限环)。15% 的死区宽度远大于硬件量化步进,把极限环彻底消掉。

### 10.6 方案 E 的收益汇总

| 指标 | 方案 B(静态) | 方案 E(闭环) |
|---|---|---|
| $U_{NPU}$ | 99.8% | 99.8%(不变,B 已接近上限) |
| 异质命中率下所需盘数 | 26 | **18** |
| SSD 运行期配置写 | 0 | 每 50 ms 约 3~8 条 |
| 客户端增量 | 0 | 每层携带一次量化需求 |
| 故障降级行为 | — | **自动退化为方案 B** |

> **一句话总结两个推荐方案的关系**:
> **方案 B 买的是"NPU 不停顿",方案 E 在此基础上额外买"少买 8 块盘"。** 如果你的盘是充裕的,直接上 B;如果盘是成本大头,上 E。**先实现 B,再把 E 作为增量叠上去**,因为 E 的骨架就是 B。

## 11. 边界情况与失效处理

| 场景 | 表现 | 处理 |
|---|---|---|
| **命中率突变** | 某节点 $B_{req}$ 突然翻倍 | B:靠 pir 硬扛,可能短暂 stall;E:167 ms 内闭环跟上 |
| **热点 block** | 公共 system prompt 前缀被所有节点读 → ring hash 把它映射到同一块盘 → 该盘热点 | ring 上给热 block 放 $R$ 个副本,读时随机选一个,该盘带宽压力降为 $1/R$;或盘框 DRAM 做读缓存;或客户端本地 L1 缓存 |
| **慢盘**(GC / 掉速) | 某块盘实际服务速率低于 cir,成为木桶短板 | 盘框 CPU 对比各盘实测速率;客户端对该盘**单独加大预取深度** $d_j$(per-SSD 差异化预取),用时间换空间 |
| **BULK 饥饿** | cir=0 的 BULK 组长期抢不到带宽 | 给 BULK 配极小的非零 cir(0.02 GB/s);硬件的"最后 RR"本身也提供兜底 |
| **URGENT 被打爆** | 所有节点同时逃生 | §7.7 的三条准入限制;客户端逃生占比 > 15% 时**告警**,说明是系统性欠配,应加盘/加 cir |
| **盘框 CPU 故障 / 配置写失败** | 闭环停止 | 参数停留在最后一次有效值,且有 $0.8 \times cir^{static}$ 下限保护 → **降级为方案 B** |
| **chunked prefill 切换 chunk 大小** | $T_c$ 变化 → $B_{req}$ 变化 | 客户端在需求申报里体现;E 自动跟随,B 靠 pir |
| **单条 path 硬件故障** | 该节点某个等级不可用 | 方案 C′ 的控制面换绑;或临时降级到同节点的其他等级 path |

## 12. 落地步骤与需要实测标定的量

**必须实测,不能靠算的**:

1. **$T_c(\text{chunk\_size},\ \text{prefix\_len})$** —— 每层 NPU 计算时间。做一张离线 profiling 表。**这是整个方案的输入基准,精度直接决定 cir 配得准不准。**
2. **SSD 在 $G$ = 512 KB 粒度下的实际可用带宽** —— 40 GB/s 是标称值,小 IO 会掉。若实测只有 34 GB/s,所有 $N_S$ 的计算都要按 34 重算。
3. **UB 的往返时延与抖动** —— 用于校正 §5.3 的排队模型(我的模型里没算这部分)。
4. **$\kappa_{agg}$ 的实测值** —— 实测每块盘的带宽分布,算出真实的 $\kappa_{agg}$,替换掉 1.12 这个理论值。

**必须算,但不需要测的**:

5. **每块盘的环份额 $p_j$ 与 $\kappa_{ring}$** —— 初始化时枚举 ring 上所有虚拟节点的弧长即可精确得到,**不要用实测值代替**(实测会把随机抖动混进来)。这是 §4.5 的输入,直接决定 cir 表和盘数。
6. **$V$、$N_S$、$\gamma$ 的联合求解** —— 见 §9.3 第 9 步,三者耦合,建议脚本化。

**建议的灰度顺序**:

1. **阶段 1**:上方案 A(静态 1:1),把监控打通(per-layer stall 计数、per-path 带宽、$\kappa_{agg}$)。这一步验证"配 cir 的方法论"是否成立。
2. **阶段 2**:加预取深度 $d$ 从 1 到 2,观察 stall 下降。这一步几乎零成本,收益最大。
3. **阶段 3**:上方案 B(分级 path + URGENT)。观察 URGENT 使用率是否落在 5~10% 的预期区间——**如果远高于 10%,说明 NORMAL 的 cir 配小了**,回去调 $\gamma$。

   > **排查顺序很重要**:URGENT 使用率偏高时,**先看它是不是集中在少数几块盘上**。如果是,那是 §4.5 的环偏斜,应该修 $p_j$ 缩放和 $V$,而不是无差别调大 $\gamma$——后者会让 $\Sigma cir$ 白白涨一圈却治不好病根。
4. **阶段 4**:上方案 E 的闭环,先只读不写(shadow mode)跑一周,对比"闭环会算出的参数"和"当前静态参数"的差异,确认算法正确后再开写。

**核心观测指标**:

| 指标 | 健康区间 | 异常含义 |
|---|---|---|
| per-layer stall 次数 / 总层数 | < 3% | 偏高 → 加 $d$ 或加 $\gamma$ |
| URGENT 组流量占比 | 5% ~ 10% | > 15% → NORMAL cir 欠配 |
| $\Sigma cir$ / $BW_{ssd}$ | < 90% | 越界 → 必须加盘 |
| 各盘带宽的变异系数 | < 8% | 偏高 → 虚拟节点数 $V$ 不足(§4.5)或有热点 block |
| $\kappa_{ring} = N_S \max_j p_j$ | < 1.10 | 偏高 → 提高 $V$;这是**算出来的**,不是测出来的 |
| URGENT 流量在各盘间的分布 | 均匀 | 集中在少数盘 → 环偏斜,不是 $\gamma$ 的问题 |
| 每周期配置写条数(方案 E) | < 16 | 偏高 → 死区 $\delta$ 调大 |

## 13. 需要你确认的硬件/接口细节(会影响具体参数)

这些不影响方案选型,但会影响 §9.3 的数字:

1. **令牌桶桶深 $\beta$ 是否可配?可配范围?** —— §5.1 的突发吸收完全依赖它。如果 $\beta$ 固定且很小,$\gamma$ 就得配大,盘数上升。
2. **超过 pir 时是"整形(排队等待)"还是"丢弃/背压"?** —— 我全文按**整形**建模。如果是丢弃,客户端需要重传逻辑,复杂度上升一个档次,方案需要重新评估。
3. **cir / pir 的量化步进是多少?** —— 决定死区 $\delta$ 的下限。
4. **8 个组的成员是否可任意指派 path,还是固定 32 条/组?** —— §9.2 给了两套排布,需要确认走哪套。
5. **"最后 RR"的确切语义** —— 是两级 WRR 之后对剩余带宽做等分轮转,还是别的?这影响 §5.2 的份额公式。
6. **单次配置写的耗时,以及一个 50 ms 周期内能写多少条 path?** —— 决定 Top-$K$ 里 $K$ 的取值。
7. **DW2 的可用位宽** —— 寻址 256 条 path 需要 8 bit。若还要在同一个 DW 里编码"带宽需求",位宽是否够?还是用其他 DW?
8. **带宽需求字段的位宽与量化方式** —— 建议对数量化(如 4 bit 表示 0.1~10 GB/s 的 16 档),精度足够且省位。
9. **per-path 的统计计数器** —— 是否有 byte counter?采样周期能否做到 ms 级?是否需要盘框 CPU 主动轮询(轮询开销多大)?
10. **UCM kv client 的实际块粒度 $G$** —— 本文假设 512 KB。这是 §4 整条推导链上**最敏感的输入**:$G$ 降到 64 KB 会让 $\kappa$ 从 1.80 掉到 1.27(好事),但 IOPS 涨 8 倍(坏事)。请确认实际值,§4、§5、§9 的数字都要按 $n = D_L/G$ 重算。
11. **ring hash 的虚拟节点数 $V$ 是否可配?** —— §4.5 建议 $\ge 500$。若 UCM 固定为某个较小值(如 128 或 160),则 $\kappa_{ring} \approx 1.15$ 无法降低,只能靠 cir 按盘缩放 + 加盘来补偿,盘数要多约 5%。
12. **cir 是否支持按盘配置不同值?** —— 即同一套软件里,20 块盘的同一逻辑 path 能否有各自的 cir。§4.5 的主修法依赖这一点。若不支持,唯一退路是把 $V$ 提得很高($\ge 2000$)把偏斜压到噪声级。
