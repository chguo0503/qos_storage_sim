# 新版 14 秒原生验证：先确认阻塞确实存在

这是 `native_aligned_A10B45_14s` 的原生完整排空结果和图样，不是最终 60 秒实验报告。不要与早期失败的 `aligned_A10B45_14s` 混淆，也不要把 `phase_alignment` 中的筛选预测当作实测。

| 统计窗口 | ASU NPU 利用率 | Once NPU 利用率 | ASU SLO×1.5 | Once SLO×1.5 |
|---|---:|---:|---:|---:|
| [2,4) 秒 | 86.7409% | 98.3750% | 76.7857%（86/112） | 100%（92/92） |
| [2,14) 秒 | 85.0701% | 99.4890% | 55.6667%（334/600） | 100%（616/616） |

两个窗口的两种策略均满足：16 卡全程活跃、每卡都实际计算过 A 和 B、逐事件名义需求小于 40 GB/s。SLO 统计窗口内上卡的请求，并跟踪到最终完成，不排除窗口外完成者；分母是各请求自己的 8 层纯计算时间。它不含上卡前排队，不等于真实端到端首 token 时延。由于两种策略的推进速度不同，窗口人口数量不同。

这里的时间范围只验证到 14 秒。完整轨迹图保留了 14 秒后仍未排空的区间；ASU 随后出现恢复，不能把这一份短验证称为无限期低利用率。

## 一次能算清楚的 FIFO 阻塞

看 [单卡内部层放大图](figures/native_aligned_A10B45_14s_asu_B_internal_HOL.png)。选中的请求为 NPU 15 上的短 B，请求 ID 15000012，从内部层 4 到层 5（从 0 编号），没有跨请求边界。

在 2572.825650 ms，它为下一层发起读取，同时开始前一层计算。读取量为 42.69056 MB；计算只能持续 17.147177 ms。数据直到 2630.637904 ms 才全部到 HBM，因此：

```text
C = 17.147177 ms                       前层计算
R = 2630.637904 - 2572.825650
  = 57.812255 ms                       发起读取到 HBM 全部就绪
I = max(R - C, 0) = 40.665078 ms        真正露出来的 I/O 等待
```

`R` 包含排队、SSD 读取和后续传输，不能把它直接叫作 SSD 服务时间，也不能把 `io_ready` 叫作 SSD 完成时刻。

为什么它必然要等？NPU 0–7 的八个长 A 内部层已先把整层读取块提交到同一条 FIFO。它们总共要读 2269.673472 MB。最早 A 发起读取到 B 发起读取之间，仅过了 0.291882 ms；即使 SSD 一直按满速 40 GB/s 工作，也最多读掉 11.675271 MB。

```text
B 前方剩余 A 数据 >= 2269.673472 - 11.675271
                  = 2257.998201 MB

服务这些排前数据的时间 >= 2257.998201 / 40
                      = 56.449955 ms

B 自己的读取至少还需 42.69056 / 40 = 1.067264 ms

不可避免的等待下界 = 56.449955 + 1.067264 - 17.147177
                  = 40.370042 ms
```

实测等待是 40.665078 ms。这个下界已经解释了绝大部分等待，且只使用长 A 的内部层，不依赖跨请求首层预取的豁免。下界不是伪造的逐块服务轨迹：它来自原生时序、精确读取量、单盘容量，以及所有相关 I/O 都使用同一 FIFO 的事实。

全部块入队时间按原生每卡每块 0.1 微秒的下发规则推导。提取器先验证单盘、无提交深度限制、每卡前一次下发早于下一次读取激活完成，才使用这一推导。完整数字和前驱 A 列表在 [HOL 证据 JSON](native_aligned_A10B45_14s_hol_examples.json)。

## 为什么名义欠载仍不能保证每一层及时拿到数据

`B = V/C` 的意思是：如果把读取均匀摊进计算时间，需要多少平均速率。它没有承诺 FIFO 会在这段具体时间里提供这个速率。

本例中，同一个 B 请求的完整内部层周期恰好读完下一层的 `V`，所以可以直接核对：

```text
B = V/C       = 2.489655 GB/s
b = V/(C+I)   = 0.738434 GB/s
b/B = C/(C+I) = 29.6601%
```

这里的 29.6601% 是这张卡的这一个完整层周期利用率，不是整机利用率，也不是任意瞬时时刻的利用率。整机应把所有卡实际计算时间相加，再除以卡数乘统计时长；不能把长、短两类的利用率简单平均。

本研究的欠载口径是“16 卡当前已上卡请求在该盘的 V/C 总和”，包含正在等待的当前请求；按已约定的口径，不额外叠加跨请求首层预取的需求。实际 SSD 发出的读取仍完整计入仿真，没有删去这部分 I/O。

## 输入究竟调整了什么

它不是随机输入，也不是只有两个固定参数的画像。A、B 是两类角色：A 为大读取、长计算，B 为较小读取、短计算。A 类还含多种提前选好的插值画像，校正对象是每段的第一个 A 请求。

普通 A 约为 200K 总输入、3302 个 miss；B 为 32K 总输入、2448 个 miss。校正 A 的计算时间不是随意加一段等待，而是先选整数总 token 数和整数 miss 数，再用 `data` 原始表内的插值估计计算时间；读取量同步按 `hit = total - miss` 和每 token 1408 字节计算。这里只核实了来自 `data` 的原始条目，没有溯源这些条目最初如何测量或生成。没有第三种桥接角色，没有人为 idle，也没有把等待计为计算。

前八张卡与后八张卡按相反次序运行一段 A、一段 B，再交换角色。离线校正使相同组的长 A 更容易一起开始下一轮大读取，从而反复制造对短 B 不利的队列顺序。正式原生重放只读取已经冻结的请求参数和顺序，不在运行时根据反馈改请求。

这是针对 ASU 的确定性输入构造。数据插值、精细的时间对齐以及缺少真实计算/存储抖动都限制了结论：它说明当前模型中可以出现这种机制，不能据此推断自然随机输入中出现的频率。
