# 16 NPU：名义欠载下，单条 QoS Path 为什么仍可能让 NPU 等待

最终冻结输入 `full_input_aligned_A10B45` 已在原生仿真中完整排空。**在共同的 2–60 秒内，ASU 平均利用率为 84.86%，Once 为 99.75%；所有时刻按当前请求 V/C 计算的名义需求均低于 40 GB/s。** 再把 ASU 的观察区间扩大到 2–90 秒，利用率仍为 84.85%。这次低值延续至排空前，不是只取早期低谷或排空尾部造成的。

但这个反例高度依赖刻意安排的时序：同一池请求改为随机顺序，ASU 的 2–60 秒利用率均值恢复到 96.44%；连请求顺序都不改、只改变同刻提交仲裁种子，也恢复到 96.70%。因此它证明的是当前确定性模型中的**有限输入存在性**，不是一般随机负载下 ASU 都会很差。

这次研究针对的是 **ASU baseline**：所有 NPU 的读取进入同一条 QoS Path。它与每卡独立 Path 的 OD baseline 不同。

### A、B 是两类，不是仅有两个固定画像

| 角色 | 总输入长度 | miss token 数 | 每层计算 C | 每层读取 V | 带宽需求 B=V/C（GB/s） |
|---|---:|---:|---:|---:|---:|
| 普通 A：大读取、长计算 | 200K | 3302 | 113.966341 ms | 283.709184 MB | 2.489412 |
| 校正 A，连同普通 A 的取值范围 | 199.840820–200K | 3302–3504 | 113.966341–120.837964 ms | 283.195264–283.709184 MB | 2.343595–2.489412 |
| B：较小读取、短计算 | 32K | 2448 | 17.147177 ms | 42.690560 MB | 2.489655 |

这里“请求 B”是角色名称，公式中的“带宽 B”是 V/C，含义不同。普通 A 与短请求 B 的平均带宽需求几乎一样：A 读取更多，但能用更长计算时间预取；短请求 B 读取较少，可供预取的计算时间也更短。因此，长短计算不等于平均带宽需求差很多，关键区别是每次读取的大小和完成期限。

这里长度的 K 表示 1024 token；读取的 MB、带宽的 GB/s 均为十进制。A 类有 **25 种不同物理参数组合**，B 类有 1 种，共 26 种实际画像。配置使用 90 个画像标识，其中不少标识的参数相同，不能把标识数量当成不同画像数量。

画像来自 `data` 原始表的网格内插值。普通 A、B 在固定总长度下对 miss 插值；部分校正 A 同时对总长度与 miss 插值。每个请求的总 token 数和 miss 数均为整数，插值权重非负且总和为 1，不外推、不另乘计算缩放系数。

```text
hit = total_tokens - miss_tokens
V_bytes = hit * 1408
C = 相邻 data 原始条目给出的计算时间，按长度和 miss 做网格内插值
```

每 128 个命中 token 对应一个完整 176 KiB 块，最后不足 128 token 的部分保留真实大小。改变 miss 或总长度时，读取量与计算时间一起按上述规则改变。

例如普通 A 固定总长为 200K。`data` 中 miss=2048 和 miss=4096 的每层计算时间分别为 70.740538 ms、141.335788 ms。3302 位于两者之间，距离低端的比例为 `(3302-2048)/(4096-2048)`：

```text
C_A = C_2048 + (3302-2048)/(4096-2048) * (C_4096-C_2048)
    = 70.740538 + 0.6123046875 * (141.335788-70.740538)
    = 113.966341 ms

hit_A = 200*1024 - 3302 = 201498 token
V_A = 201498 * 1408 = 283709184 bytes = 283.709184 MB
```

B 同理，固定总长为 32K，在 miss=2048、4096 的条目之间选 2448，得到 C=17.147177 ms、V=42.690560 MB。

选数的顺序可以理解成三步：先算每卡预算 `40/16=2.5 GB/s`；再选总长 200K 的大读取 A 和总长 32K 的小读取 B；最后用 `C≈V/2.5` 反推各自需要的 miss，在 `data` 网格内寻找两者 `V/C` 都略小于 2.5 的整数取值，得到 3302、2448。因为 V 本身也随 miss 变化，实际筛选同时代入 `V=(total-miss)*1408` 和插值 C，不是任意指定 C。最终每卡需求约 2.49 GB/s，16 卡合计略低于 40 GB/s。这些是经过筛选的取值，不是公式唯一确定的数字。

这里只核实了数值来自 `data` 的原始条目，没有溯源这些条目最初如何测量或生成；网格之间的计算时间是模型估计，不应称为已经逐点测过的硬件性能。

### 每张卡怎么排请求

```text
NPU 0–7：  启动前缀 3A + 15B；然后重复 (10A + 45B)，共 5 轮
NPU 8–15： 启动前缀 15B + 3A；然后重复 (45B + 10A)，共 5 轮
```

两组卡都会跑 A 和 B，不是固定八张长卡、八张短卡。启动前缀让原 warm `[2,4)` 秒内每卡都有机会运行两类请求；后面较长的 A/B 段用于观察反复发生的阻塞。

每个 A 段的第一个 A 可以换成提前选好的校正画像。离线选择这些参数，是为了减小同组卡下一轮大读取开始时间的分散；正式仿真只读取冻结后的配置，不在运行时改变计算时间或插入等待。

校正的数学目标是：若这张卡的首 A 在 `t_i` 开始计算，希望八层计算在共同目标 `T` 附近结束，则候选计算时间约为 `C_i=(T-t_i)/8`。随后仍要映射回合法整数 token/miss 和 `data` 网格内插值，检查真实 I/O 等待，再用原生仿真验证；不能把这个近似式直接当作实际完成时间保证。校正首 A 的 C 稍增、V 略减，仍满足上面的每卡需求上界。最终取值、顺序在正式运行前全部冻结。

因此，这是**针对 ASU 的固定顺序、多画像构造**。没有第三种桥接角色，没有人为 idle，也没有把 I/O 等待冒充计算。它不是从 `data` 普通随机抽样就自然得到的输入。

最终版本对完整有限输入中剩余的 A 段也按相同规则校正，不只校正到某个统计窗口结束。输入仍然有限，最后必须排空；“全输入校正”也不等于已经证明无限时间的稳态性质。

## “欠载”在这里具体指什么

对当前已经上卡的请求，名义带宽需求定义为：

```text
B_i = 当前请求每层读取量 V_i / 当前请求每层纯计算时间 C_i
D(t) = 16 张卡在时刻 t 的 B_i 之和
```

正在计算和正在等 I/O 的当前请求都计入。每卡最大的 B_i 不超过 2.489655336 GB/s，所以即使任意组合当前请求，也有：

```text
D(t) <= 16 * 2.489655336
     = 39.834485362 GB/s
     < 40 GB/s
```

容量余量约 0.165515 GB/s，即 0.414%。这是**很接近满载的名义欠载**，不宜用“带宽很宽裕”描述。正式结果已从请求接纳、完成事件重新扫描 D(t)：ASU 全程峰值为 39.834485362 GB/s，Once 为 39.833025779 GB/s，均没有超限，而不只是窗口平均值低。

按前面约定，本口径不额外叠加“前请求最后一层计算期间预取下一请求首层”的需求。对应的实际 I/O 仍完整进入仿真，没有删除。因此结论应写成“按当前请求 V/C 定义的欠载”，不能改写为任意微小时间段内提交到 SSD 的字节都小于容量。

相同冻结输入在 ASU 与 Once 下推进速度可以不同，当前上卡的请求也随之不同，所以两条 D(t) 曲线不必相同。全部 arrival=0 也不意味着所有请求同时执行：每卡仍按自己的队列串行上卡。

## 为什么平均需求不超盘容量，短 B 仍会被堵

`V/C` 只说“把一次读取均匀摊进计算时间，平均需要多快”。单条 FIFO 不会据此给每张卡保证一个恰好够用的服务时段。

长 A 一次读取约 283.7 MB，短 B 一次读取约 42.7 MB。A 的计算约 114 ms，B 只有约 17 ms。如果八个 A 的大读取先排进 FIFO，B 后来的读取必须等排前的块完成。A 可以在较长计算中藏住这些服务时间，B 的计算先结束，就出现真正的 I/O stall。

这可以用保守下界证明。设 B 在 `t_B` 发起读取，前面八个 A 的全部块已提交；它们中最早发起读取的时间是 `t_A`：

```text
B 前方尚未完成的 A 数据
    >= 八个 A 的总读取量 - 盘容量 * (t_B - t_A)

B 的不可避免等待
    >= max((排前 A 剩余数据 + B 自身读取量) / 盘容量 - B 的计算时间, 0)
```

这条公式先假定 SSD 在期间一直满速服务，得到对 B 最有利的下界。如果读取耗时下界仍超过 B 的计算时间，亦即等待下界大于 0，就已经能从队列顺序和容量推出必然等待。

原生证据提取器只选同一 B 请求的内部层，并优先只使用排前 A 的内部层。它会核对实际 Path、提交节拍、每卡提交流是否重叠、读取大小、计算和等待区间，再计算下界。`io_ready` 表示数据全部到 HBM，不冒称 SSD 完成时间。

对这种同请求、只提前一层的完整周期，下一层的全部读取量确实是 V 时，还可以核对教程中的关系：

```text
R = 发起读取到 HBM 全部就绪的时间（包括排队和传输）
I = max(R - C, 0)
T_layer = C + I

B = V/C
b = V/T_layer
b/B = C/(C+I) = 这张卡这个完整层周期的利用率
```

它不是瞬时利用率公式，也不能直接用于跨请求、前后读取量和计算时间不同的边界。整机利用率仍用所有卡的真实计算时间积分，不能按 A:B 的请求数量直接平均两个类别的利用率。

## 为什么还需要随机顺序和敏感性对照

每层自然错开确实可能使问题减轻。本构造提前调整各段首 A 的画像，就是在输入中有目的地减小这种错开。能构造出反例，与自然随机工作负载经常出现反例，是两个不同的结论。

最终随机对照使用**同一批画像、相同每卡画像数量**，只打乱每卡请求顺序：输入随机种子为 7、17、27。仿真器处理同一时间戳提交的种子统一保持为 7。构造与逐卡多重集校验记录在 [full_input_control_construction.json](full_input_control_construction.json)。不能拿旧画像池的随机实验替代这一对照。

## 如何判断不是统计窗口造成的假象

主横向比较固定使用共同的 `[2,60)` 秒；原 `[2,4)` 秒 warm 结果同时保留。报告还列 `[20,60)`、`[40,60)`，以及 ASU 的 `[2,90)` 扩展验证。

完整输入利用率使用各策略各自的 makespan；排空前利用率使用各策略各自“首张卡最终完成”的时刻。表格必须写明这些边界，不能把两种不同长度的运行误说成同一墙钟窗口，也不能在 Once 已经结束后补零再与 ASU 比较。

每个窗口都检查是否全部 16 卡持续活跃、每卡是否实际计算过 A 和 B、是否逐事件名义欠载。连续 2 秒 U 曲线只画首卡排空前的完整窗口，并保留后期回升。完整 16 卡时序从 0 开始画到各策略自己的首卡完成时刻。

混合条件要求原 warm `[2,4)` 秒及整段输入每卡都运行两类请求；它**不要求每一个后续滑动 2 秒窗都同时包含 A 和 B**。连续 A/B 段本来就会让某张卡在一小段时间内只运行一类。

SLO×1.5 的计数是：窗口内上卡的请求，从上卡追踪到最终 prefill 完成，耗时不超过自身 8 层纯计算时间的 1.5 倍。窗口外才完成的请求仍计入。它不含上卡前排队，不等于完整端到端 TTFT。另给完整 4688 个请求人口的 CDF/SLO，以便比较同一请求人口。
