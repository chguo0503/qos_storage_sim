# 请求顺序与长期阻塞：候选筛选记录

这里是**选候选的辅助模型**，不能代替上级目录的原生仿真结果。没有修改核心仿真器，也没有增加第三种请求、主动暂停 NPU 或等待指令。所有候选的控制量都是各卡预先排好的 A/B 请求队列。

**后续校准发现的重要限制：**这里的 `block_issue_probe.py` 仍未模拟原生每轮提交时对 NPU 的随机打乱，也未完整维护 NPU 接收 FIFO。相同画像的整机利用率吻合，掩盖了逐卡时序身份不同；不能用它给指定 NPU 设计精细校正画像。修正模型及逐层校准证据在 `../phase_alignment/native_like_probe.py`、`native_like_14s_calibration.json` 和 `native_like_60s_calibration.json`。旧模型输出保留为失败筛选记录，不是最终成功结果。

## 先纠正一个容易高估阻塞的假设

若十张卡的 A 同时排在 B 前面，可以估算这批 A 的总服务工作量；但不能由此假定**以后每一层仍然保持相同的聚集状态**。I/O 完成时刻、计算结束时刻、跨请求首层预取和请求切换都会改变相位。只算第一波排队，无法证明长期利用率低。

最初的 `approx_phase_search.py` 把一整层读取原子地放进 FIFO。这个近似适合估计总工作量，但会改变同时提交时的块交错顺序，因而不适合直接证明周期锁相。

原生客户端是每次提交一个块，间隔 0.1 微秒。多个 NPU 同时提交时，其块会交错进入 FIFO。`block_issue_probe.py` 加回了这一点，使用 128-token 块、精确尾块、40 GB/s 单盘和 50 GB/s NPU 接收链路。它仍是独立辅助模型，缺少原生 QoS 状态及完整统计，最终结论仍需原生仿真确认。

## 严格欠载如何检查

在同一块盘上，当前 16 个请求的名义需求为：

```text
需求 = A 卡数量 × B_A + B 卡数量 × B_B
```

I1 的 `B_A=2.489412 GB/s`、`B_B=2.489655 GB/s`，因此任意组合都低于 `16×2.489655=39.83449 GB/s`。这一充分条件与策略、请求相位无关。沿用主实验定义：跨请求首层额外预取不另加到名义需求中，但产生的等待仍计入利用率。

原始数据行 A200/miss4096 与 B32/miss2048 不具备这个保证：只有 B 卡数量不超过 7 时才能保证单盘需求低于 40 GB/s。整层模型筛出的一个 12 秒合格样本，延至 60 秒后出现 8 张 B 卡而超载，因此不能作为长期严格欠载的成功案例。若要保留这类候选，必须分别检查 ASU 和 Once 的实际轨迹。

## 候选搜索结果应如何使用

- `block_phase_results.json`：245 个 q=6–10、双群卡数 6–10 及有理请求比例的逐块候选。
- `block_phase_shortlist_60s.json`：其中四个较好候选延至 60 秒。最好的 q7/cohort8/offset3 从 [2,12) 92.98% 上升至 [2,60) 95.58%；不能只展示短窗口。
- `block_low_q.json`：15 个 q=1–5 的逐块补充候选。
- `block_rational_low_q.json`：113 个 q=3.5–5.5 附近的逐块候选，未找到长期 80% 多的成功输入。
- `*_approx*`、`I1_cohort_q5_180s.json`：早期整层近似的筛选记录，**不作为原生结果或长期锁相证据**。

队列中 `ABBBBB` 的意思是先完成一个 A，再连续完成五个 B，然后重复；卡之间只改变预先给定的请求次序。每张卡最终仍然执行两类请求，并不固定绑定为长卡或短卡。

在已经校准的这一批逐块相位筛选中，还没有找到满足长期目标的成功输入。这不证明所有输入都不可能，只说明“初始让许多 A 聚集”本身不足以保证长期阻塞。
