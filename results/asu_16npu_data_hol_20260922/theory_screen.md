# 16 张 NPU：怎样从原始 data 找长短请求

这是**运行前的数学筛选**，不把队列示意当成仿真结果。这里 A 指“相对较大读取、较长计算”，B 指“相对较小读取、较短计算”，不沿用总长度/miss 分类字母的含义。

本次直接读取根目录 `data` 的 84 个原始数据点，不插值、不外推、不人为缩放计算时间。它们的总输入长度为 32K–200K，miss 为 64–4096 token。筛出 2014 组同时满足 `V_A > V_B`、`C_A > C_B` 的 A/B。

## 1. 先说明原来那条公式的边界

把所有盘暂时想成一个理想总带宽池 D，单位 GB/s：

```text
B_A = V_A / C_A
B_B = V_B / C_B
```

要保证 16 张卡无论当前碰巧处理 A 还是 B 都欠载，至少要：

```text
D > 16 × max(B_A, B_B)
```

要让**一个完整的 A 读取**排在 B 前面，就超过 B 一整层的计算时间，则要：

```text
D < V_A / C_B = (V_A/V_B) × B_B
```

这两条同时成立，必然要求 `V_A/V_B > 16`。但是这 84 个原始数据点的最大读取量比只有：

```text
最大命中 token / 最小命中 token
= (200×1024−64) / (32×1024−4096)
= 7.140625
```

因此，**原始 data 不可能满足这个理想模型中的“16 卡任意组合欠载，同时单个 A 独自堵住 B”条件。** 这不是说 ASU 一定没有等待：多个 A 的积压、分盘偏斜、B 已经只剩很短计算余量等情况，不在这个简单结论的范围内。只保证某条实际轨迹欠载，也比“保证任意组合”弱。

## 2. 改为寻找“多个 A 一起挡住 B”

优先候选直接来自两个原始数据点：

| 参数 | A：200K、miss 4096 | B：32K、miss 4096 |
|---|---:|---:|
| 命中 KV token | 200,704 | 28,672 |
| 每层读取量 | 282.591 MB | 40.370 MB |
| 每层计算时间 | 141.336 ms | 28.593 ms |
| 每层带宽需求 | 1.999 GB/s | 1.412 GB/s |

使用 **16 NPU、1 SSU，每盘 40 GB/s**。最不利的 16 个 A 同时存在，需求也只有：

```text
16 × 1.999432 = 31.990912 GB/s < 40 GB/s
```

所以无论请求如何排列、如何推进，普通名义需求都欠载。这里只有一块盘，不存在把总量均摊到各盘的假设。

一个 A 的纯盘服务工作量约为 `282.591/40 = 7.065 ms`。若五个 A 的整层数据已经排在 B 前面：

```text
五个 A 的盘服务时间 = 5 × 7.065 = 35.324 ms
B 可以隐藏读取的计算时间 = 28.593 ms
超出部分约为 6.731 ms
```

这时 B 会等。若十个 A 完整排在前面，前方工作量约 70.648 ms，超过 B 的计算窗口约 42.055 ms。

这里故意先不加 B 自己的读取时间：用“A 已经占满计算窗口”说明产生等待的一个充分队列条件。实际完成时间还取决于 B 自身读取、其他插入的块、NPU 接收链路和提交交织。

**欠载限制的是 V/C，不是瞬间提交的字节突发。** 多张卡同时把整层读取塞进 FIFO，即使随后有很长的计算时间，仍可能在这个时刻互相挡住。

## 3. 为什么先试请求数 1:3，而不是沿用 1:12

长请求占用卡的时间更久。忽略等待，A:B 请求数为 `1:q` 时，A 占据卡时间的比例约为：

```text
A 时间占比 = C_A / (C_A + q × C_B)
```

对上述画像，取 `q=3`：

```text
A 时间占比 ≈ 141.336 / (141.336 + 3×28.593) ≈ 62.2%
16 张卡中，平均约 10 张在处理 A、6 张在处理 B
```

这个比例有机会同时保留“足够多的 A 制造读取积压”和“足够多的 B 受到影响”。因此建议先测 **1:2、1:3、1:4**。这是无等待近似下的候选选择方法；出现等待后，各类别占据卡的时间也会改变，不能用这个近似证明实际并发比例。

## 4. 最需要防止的逻辑跳跃：存在坏队列，不等于长期反复出现

五个 A 排在 B 前面会很差，但随机输入是否经常形成这种队列，必须检查层时序。

例如十个 A 的读取相位若大致均匀，它们“正在读或排队”的平均数量量级只有：

```text
10 × 7.065 / 141.336 ≈ 0.5
```

平均有十张卡运行 A，并不意味着有十个 A 同时挤进盘队列。FIFO 完成时刻本身也可能把各卡后续提交时刻拉开。这个近似只用于提醒相位问题，不是一个精确排队模型。

因此后续实验必须同时回答：

1. 普通名义需求是否全程逐盘低于容量？
2. B 发生等待时，前方究竟积压了多少 A 的字节，等待能否由其解释？
3. 这种积压是否在启动之后反复发生，而不是仅出现一次？
4. 长时间统计的真实计算利用率是否下降？每张卡是否都持续轮流处理 A、B？
5. Once 在同一输入上是否减少了这些等待？

TTFT SLO×1.5 还允许额外等待。上述 B 的八层纯计算约 228.743 ms，SLO 允许的额外等待约 114.371 ms。**产生某一层等待，不能直接推出整条请求违约。** 必须累加请求实际等待并与自身阈值比较。
