# 离线选择少量长请求，使读取再次集中

这是一个**有意构造请求次序和少量长请求画像的实验**，不是普通随机输入，也不是只使用两条原始 `data` 行。主目录的原生 ASU/Once 结果才是最终仿真结论。

## 输入到底如何排

16 张卡分成两个八卡组，但每张卡都执行 A、B：

```text
NPU 0–7：  3个A，15个B，然后重复 [10个A，45个B]
NPU 8–15：15个B， 3个A，然后重复 [45个B，10个A]
```

长版本重复五轮，每张卡总计 53 个 A、240 个 B。首次角色切换落在原来的 warm `[2,4)` 秒内；随后各卡仍会换角色。长段内同类请求相邻，这是刻意保留相位的输入安排，应当明确披露。

标准 A：200K 总输入、miss3302、每层计算约 113.966 ms。

标准 B：32K 总输入、miss2448、每层计算约 17.147 ms。

这两个 miss 都由 `data` 测量网格内插值得到。没有外推、没有修改仿真器的计算公式、没有填充 KV，也没有暂停 NPU。

## 为什么需要校正每一段开头的 A

八张卡经历 B 请求的排队后，进入下一段 A 的时间可能相差几十毫秒。若它们各自算一样久，后续 A 的读取也会错开，FIFO 的阻塞就减弱了。

于是对这一段的首个 A，离线选择稍微不同的总长度和 miss，让八张卡完成这个 A 的时间接近。之后的九个 A 都恢复标准画像。

```text
选一个共同的结束时间 T

第 i 张卡首个 A 的每层计算目标
    = (T − 这个 A 第一层实际开始计算的时间) / 8
```

这里的除以 8，是因为每个请求有八层。这个关系以该 A 的内部读取已被计算隐藏为前提，生成过程还会重放并检查实际结束时间，不能只代入一次就认定同步。

每个校正画像都从 `data` 相邻测量点做双线性插值：总 token 数、miss 都是整数，读取量随真实命中 token 数重算。它们不是直接篡改 C，也不是保留 V 不动。之后把全部输入冻结，再交给 ASU 和 Once 运行；运行时没有根据反馈改请求或等待。

完整输入版本有 88 个 A 位置被校正，共 24 种校正数值。这 88 个位置分布在 11 次八卡角色切换中，每次只改各卡这一段的首个 A：

| 参数 | 范围 |
|---|---:|
| 总输入 token 数 | 204,637–204,702 |
| miss token 数 | 3,304–3,504 |
| 每层计算 | 113.9676–120.8380 ms |
| 需求带宽 | 2.34360–2.48778 GB/s |

它们均在测量网格内，但仍属于构造出的插值画像，不应说成原始测量行。

## 欠载保证独立于相位

标准 A 需求约 2.489412 GB/s，标准 B 约 2.489655 GB/s；校正 A 的需求更低。因此：

```text
任意时刻的名义总需求 <= 16 × 2.489655 = 39.83449 GB/s < 40 GB/s
```

只用一块 SSU，因而这也是逐盘保证。沿用主实验口径：跨请求首层的额外预取不另加到名义需求中；它造成的所有等待仍计入利用率。

## 辅助模型如何校准

旧的 `align_probe.py` 曾预测低利用率，但原生没有复现。原因已经核实：原生每个提交时刻会用 NumPy RNG 打乱同时提交的 NPU 顺序，旧模型固定次序；旧模型也漏了短尾块前的 NPU 接收队列等待。

修正后的 `native_like_probe.py` 复现这两点，并用原生相同的 GiB 算式。它只支持当前的 16 NPU、单 SSU、ASU FIFO、8 层、128-token I/O、精确尾块、0.1 微秒提交间隔，不能当成 Once 或多盘的通用替代品。

| 校准输入 | 逐层对比数量 | 计算起点最大差异 |
|---|---:|---:|
| 旧 14 秒校正候选 | 5,951 层 | 0 ms，逐浮点相同 |
| 旧 60 秒校正候选 | 26,960 层 | 0 ms，逐浮点相同，排序时序 SHA256 相同 |

新版 14 秒校正候选也已经由主任务完成原生验证：ASU warm 利用率 86.74091%，`[2,14)` 利用率 85.07006%，与新版选择模型一致。

最终输入文件：

- `aligned_sequential_14000ms_native_like_config.json`：短版原生校准。
- `aligned_sequential_60000ms_native_like_config.json`：先前只校正 60 秒范围的冻结候选。
- `aligned_sequential_60000ms_full_input_native_like_config.json`：完整有限输入版本；所有 11 次角色切换均校正，不在 60 秒处停止构造。
- `sequential_align.py --native-like`：按时间顺序逐段求解并冻结校正。
- `native_like_controls.py`：冻结输入后改变提交 RNG、微调 token/miss、随机重排的控制实验。
- `verify_full_input.py`：把最终官方导出配置重放到全部请求结束，检查完整输入的忙碌区间。

没有 `_native_like` 后缀的旧校正配置和旧模型敏感性不能作为成功证据。是否具有现实稳健性，要看新版长窗敏感性和原生结果，不能由短窗低利用率推出。

## 冻结输入后的稳健性检查

以下为已完成逐层校准的选择模型结果，**不是额外的原生 Once/ASU 对照**。这里使用的是先前只校正 60 秒范围的冻结候选（SHA256 `1352cdb511be178775dd48331e4adc3d2b17b6b09df48fea412f4f3e00910bed`），不是后面的完整输入版本。候选输入冻结后，不再重新求解校正。

| 只改变这一项 | ASU `[2,60)` 利用率 |
|---|---:|
| 原构造，提交 seed7 | 84.8593% |
| 相同请求、相同次序，只把提交 seed 改为17 | 96.7080% |
| 相同请求、相同次序，只把提交 seed 改为27 | 97.5752% |
| 每个校正A总长度随机加减1 token | 94.7166% |
| 每个校正A的miss随机加减1 token | 94.9412% |
| 校正A总长度取整到1K | 95.0292% |
| 校正A的miss取整到64倍数 | 96.1182% |
| 同一请求集合，每卡独立随机打乱，seed7 | 96.5674% |
| 同一请求集合，每卡独立随机打乱，seed19 | 96.5636% |

所有控制仍满足逐时刻名义欠载。除最后一行的 NPU15 在 warm 仅执行 B 外，其他控制均通过 warm 每卡 A/B 覆盖检查。

**因此它是一个对执行次序非常敏感的、离线精细构造的反例，不能声称现实微小扰动下仍普遍存在。** 初始 warm 的低利用率在扰动后仍可能保留，而长窗已经恢复较高利用率；这也是必须看长窗的原因。提交 seed 控制仅改变同时下发 I/O 时的排序，不改变请求内容，所以这一负面结果尤其不能忽略。

完整记录在 `native_like_controls_60s.json`，其每行记录冻结配置 SHA256、实际提交 seed 和队列 SHA256。对 token/miss 做扰动时，C 和 V 都从同一数据规则重新计算；没有通过修改计算时间而保持读取量不变来制造结果。

## 为什么还要检查 60 秒之后

每卡 53 个 A、240 个 B，不会恰好在 60 秒耗尽。旧候选仅校正了 60 秒前观察到的切换，后续未校正的角色切换会再次让 A 错开：其 `[60秒,首卡结束)` 利用率回升到 91.9986%。因此，不能只凭前 60 秒低就说整批输入始终低。

完整版本保持同样的请求数量和排列规则，把所有后续首 A 也按同一办法校正。它不是通过延长尾部空闲来拉低平均值，主要指标截止在**第一张卡耗尽输入**之前：此前全部 16 张卡都有工作。

完整版本配置 SHA256：`9464437a332d50b20f75dd4a8e4b0675215bb789ea64d9fd4e858541c58b809f`。以下暂为校准后的选择模型预测，最终应以主目录原生 ASU/Once 结果为准：

| 统计范围 | ASU 利用率 |
|---|---:|
| warm `[2,4)` 秒 | 86.7409% |
| `[2,60)` 秒 | 84.8593% |
| `[60秒,首卡结束)` | 84.7409% |
| `[2秒,首卡结束)`，16 卡始终有工作 | 84.8140% |
| `[0秒,末卡结束)`，完整有限批次 | 84.7030% |

首卡约在 95.9389 秒结束，末卡约在 96.0680 秒结束。完整批次仍是每卡 53A+240B，没有增加请求来追求低平均。完整校正重选了七个接近 60 秒边界的首 A，总长度相对旧版本减少 1–14 token，因此前 60 秒不是逐事件完全相同，但利用率仅变化约 0.00000624 个百分点，warm 和 2.57 秒附近的阻塞案例不受影响。

此修改消除了“仅把坏现象凑在统计窗口内”的问题，**没有消除精细离线校正对执行顺序敏感的问题**。不能把有意构造成功等同于普通随机输入也普遍低。

完整输入版本也重复了四项冻结后的敏感性检查，同样只使用已经逐层校准的选择模型，统计 `[2,60)`：

| 改动 | ASU 利用率 |
|---|---:|
| 不改动 | 84.8593% |
| 仅提交 seed 改为 17 | 96.7046% |
| 仅提交 seed 改为 27 | 97.5845% |
| 校正 A 总长度随机加减 1 token | 94.5054% |
| 校正 A miss 随机加减 1 token | 93.6965% |

四项控制都仍满足名义欠载，且 warm 内 16 张卡均运行 A/B。记录在 `native_like_full_input_controls_60s.json`，可用 `native_like_controls.py --full-input` 重现。扰动没有重新求解校正，C 和 V 都由实际参数重算。其结论与旧版一致：**持续低利用率依赖精细的确定性时序，稳健性不足**。

具体构造步骤、首 A 如何选 C、实际八号卡与十号卡的数值例子，见 [construction_walkthrough.md](construction_walkthrough.md)。
