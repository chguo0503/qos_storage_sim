# 这批欠载输入是怎样构造的

核心事实：这是一批**提前算好、之后冻结的特殊输入**。它说明单 FIFO 在名义欠载时仍能长时间受阻；它不是从 data 随机抽两条数据就普遍出现的结果。校正需要细致掌握仿真器的执行次序，换同时提交的排序 seed 就可能失效。

## 1. 先选两种标准请求

16 张 NPU，共用一块带宽 40 GB/s 的 SSU。这里 GB/s 是十进制；读取量表格用 MiB。每个请求有 8 层。

| 标准请求 | 总输入 token | miss token | 每层读多少 | 每层算多久 C | 需求 V/C |
|---|---:|---:|---:|---:|---:|
| A | 204,800 | 3,302 | 270.566 MiB | 113.9663 ms | 2.489412 GB/s |
| B | 32,768 | 2,448 | 40.713 MiB | 17.1472 ms | 2.489655 GB/s |

miss 不在原始测量网格点上，因此计算时间是相邻 data 测量行插值所得。读取量严格由命中 token 数重算；没有任意修改计算时间，也没有让请求读取虚假的数据。

两类请求的平均需求接近，但节奏很不一样。A 一层读的数据是 B 的约 6.65 倍，计算时间也约为 6.65 倍。如果八个 A 的读取挤在一起，单盘服务它们需要：

```text
8 × 283,709,184 字节 ÷ 40,000,000,000 字节/秒
    = 56.742 ms
```

B 只计算 17.147 ms 就需要下一层数据，可能来不及隐藏这段等待。这里的 56.742 ms 是八个 A 读取的合计盘服务时间，用于解释可能的阻塞量级；并不是说每一个 B 都恰好等这么久。实际等待还取决于 B 什么时候提交、前面到底排了多少块。

## 2. 每张卡都运行 A 和 B

```text
NPU 0–7：  3A + 15B + (10A + 45B) 重复五次
NPU 8–15：15B +  3A + (45B + 10A) 重复五次
```

每张卡的完整输入都是 53A + 240B，共 293 个请求。第一次切换落在 warm [2,4) 秒，所以 warm 内每张卡都运行 A/B；后面也继续轮换。长段内让同类请求相邻，属于刻意安排次序，不能描述成随机混合。

如果只使用标准 A/B，这种次序还不够。八张卡经历不同的 B 排队后，下一段 A 的开始时间会逐渐散开，A 的读取也就不再集中。固定两条画像的多轮测试出现的正是这种恢复。

## 3. 每段只微调首个 A，重新对齐后面的 A

把一段十个 A 想象成一队人。最前面的人原来出发有早有晚；给早出发的人安排稍长一点的计算，让他们算完首个 A 后差不多一起开始第二个 A。后面九个 A 完全使用标准画像。

离线生成输入时，对一组八张卡这样处理：

```text
t_i = 第 i 张卡这个首 A 的第一层实际开始计算的时刻
C0  = 标准 A 每层计算时间，即 113.9663406 ms

共同目标结束时刻 T = 八张卡中最晚的 t_i + 8*C0 + 0.01 ms

第 i 张卡首 A 的每层计算目标 C_i = (T - t_i) / 8
```

T 是这一次对齐的目标时刻，不是利用率统计窗口。除以 8 是因为请求有八层。这个公式要求首 A 开始计算以后，内部各层读取能被计算隐藏；所以生成器会重放验证，不能只代公式就宣称成功。

以第一组切换的实际原生时序为例（这段前缀在最终输入中相同）：

| NPU | 首 A 开始计算 | 选出的每层 C | 首 A 算完／第二个 A 开始 |
|---|---:|---:|---:|
| 8 | 2942.488877 ms | 120.837964 ms | 3909.192593 ms |
| 10 | 2997.451475 ms | 113.967615 ms | 3909.192398 ms |

8 号卡早开始约 54.963 ms，所以首 A 的总计算约多 54.963 ms。二者下一请求的开始相差约 0.000195 ms。数据来源：`runs/native_aligned_A10B45_14s/asu_baseline/native_summary.json.gz` 中请求 8000015、10000015 及其后继请求。

## 4. 如何把 C_i 变成真实请求参数

生成器不会直接写一个任意 C_i。它在 data 网格内部寻找整数总输入和整数 miss：总输入在 192K–200K 范围，miss 搜索 3200–4096。

对每个整数 miss，先求该 miss 在 192K、200K 两端的插值计算时间；目标 C_i 落在两者之间时，再反求最接近目标的整数总 token 数。优先保留与上轮相近的 miss，再最小化计算时间误差。随后依据所选的总输入和 miss 同时重算 C、读取量 V、需求 V/C。

选好八个首 A 后重放输入，观察第二个 A 的实际开始是否集中。若八张卡仍相差超过 0.05 ms，就再次微调、重放。先冻结较早的组，再解下一组，避免后面的调整反过来影响已经确认的前缀。所有这些步骤都在正式实验之前完成。

完整输入共有 11 组这样的首 A：0–7 号卡各有 5 次，8–15 号卡各有 6 次，总计 88 个校正位置。其余 760 个 A 使用标准画像；所有 3,840 个 B 都相同。88 个校正位置最终使用 24 种不同的实际参数：

| 参数 | 最小值 | 最大值 |
|---|---:|---:|
| 总输入 token | 204,637 | 204,702 |
| miss token | 3,304 | 3,504 |
| 每层计算 | 113.9676 ms | 120.8380 ms |
| 需求带宽 | 2.34360 GB/s | 2.48778 GB/s |

校正 A 仍属于长读取、长计算的 A 家族，但严格说来它们是多种具体画像。不能声称整个实验只用了两条相同的请求模板。

## 5. 为什么能严格满足约定的欠载条件

不管各卡正在运行标准 A、校正 A 还是 B，单卡的名义需求都不超过 2.489655 GB/s：

```text
16 卡任意组合的名义总需求
    <= 16 × 2.489655335
    = 39.834485 GB/s
    < 单盘 40 GB/s
```

这不依赖 ASU/Once 的具体执行轨迹。沿用本实验已约定的口径：跨请求首层额外预取不再另外加一份名义需求；它造成的盘服务、等待和 stall 都仍参与原生仿真。这里的欠载是 V/C 名义需求的约束，不能据此声称所有瞬时提交的 I/O 字节都均匀低于带宽。

## 6. 为什么不能把这当成一般输入都会出现的现象

输入一旦生成就冻结；ASU 和 Once 收到同样的参数与请求顺序。运行时不会暂停 NPU，不会根据盘反馈临时改变 C，不会临时挑下一条请求。

但生成时确实利用了完整的、确定的执行时序。这种构造对微小扰动敏感：之前版本只换同时提交的 shuffle seed，长窗利用率就从约 84.86% 回到 96%–98%。因此应得出的结论是“可以构造长时间的 FIFO 阻塞反例”，不能进一步跳到“随机真实流量经常低到这个程度”。最终完整输入的原生对照和敏感性记录见主报告及本目录 README。
