# 同一批输入，ASU 为什么没有 OD 那段空档？

**不是 ASU 把所有画像的结果随机打散了，而是共享 FIFO 使不同读取量的层都承受了相近的背景排队时间；六种总长度混合后，部分画像向右移动、部分向左移动，把间隔填上了。** 单独限制为 128K 时，ASU 的 miss256 与 miss1024 仍明显分开，不能说 ASU 内部完全没有两群。

这里的“读取时长”是 `io_ready_time - io_start_time`，包含 SSD 排队、SSD 服务及 NPU 接收链路；“层周期”还要等这一层计算完成，两者不是一回事。

## 先排除 warm 样本不同造成的混淆

输入 manifest 完全相同，但策略改变执行速度后，进入 [2,4) 秒的请求会变化：ASU 为 589 条，OD 为 586 条，其中相同 seed/request_id 有 529 条。下面的主表只用这 529 条交集中的对应画像，两种策略的请求 ID、读取量、计算时间、原始分卡和落盘位置一致。

| 同 ID 子样本画像 | 请求数 | 每层计算 C | 每层读取量 | ASU 平均内部读取时长 | OD 平均内部读取时长 | ASU ratio 中位数 | OD ratio 中位数 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 32K、miss2048 | 15 | 14.369 ms | 41.250 MiB | 29.054 ms | 8.551 ms | 2.099 | 1.000 |
| 64K、miss1024 | 34 | 12.626 ms | 86.625 MiB | 31.082 ms | 18.170 ms | 2.354 | 1.468 |
| 200K、miss256 | 40 | 9.044 ms | 274.656 MiB | 34.863 ms | 56.181 ms | 3.840 | 6.116 |

读取量差约 6.7 倍，但 ASU 的平均内部读取时长都在 29–35 ms。OD 则由 8.6 ms 增长到 56.2 ms，更明显地跟随自己的读取量。

因此，ASU 的小读取请求也会等很久：32K/miss2048、64K/miss1024 的 ratio 被推到约 2–2.4；某些大读取的 miss256 请求反而比 OD 更快，向较小 ratio 移动。不同总长度一起画 CDF 时，这些点填进 OD 的空档。原始分布审计记录 ASU 的空档区间内有 92 个请求；限制为上述 529 个相同 ID 后，ASU 仍有 78 个，OD 为 0。

## 一个请求就能看出小读取被拖慢

同一个 `seed43 / request16000007 / NPU16`，画像为 32K、miss2048；它在两种策略中都于 warm 内接纳。

| 指标 | ASU | OD |
|---|---:|---:|
| 接纳时间 | 2241.582 ms | 2267.253 ms |
| 每层计算 | 14.369 ms | 14.369 ms |
| 7 个内部层平均读取时长 | 32.420 ms | 9.111 ms |
| 内部 L1–L7 等待总计 | 126.355 ms | 0 |
| L0 暴露等待 | 0 | 0 |
| TTFT | 241.308 ms | 114.953 ms |
| 纯计算时间 | 114.953 ms | 114.953 ms |
| TTFT / 纯计算 | 2.099 | 1.000 |

ASU 的读取需要约 32 ms，14 ms 计算只能遮住一部分，所以每层继续等。OD 约 9 ms 就读完，完全藏在 14 ms 计算里。

该请求的原始逐块平均排队指标也支持这一解释：ASU 的 SSD 排队均值为 **31.500 ms**，NPU 接收链路排队均值为 **0.0478 ms**；OD 对应为 4.472 ms 和约 0.000091 ms。它确实经历了显著的 SSD 排队，而不只是归一化分母造成的视觉差异。这些是逐块均值，不能直接相加当作整条请求的关键路径等待。

方向并非总是 OD 更好。同一个 `seed43 / request12000008 / NPU12`，画像为 200K、miss256：ASU 内部读取平均 34.001 ms、ratio=3.845；OD 为 55.529 ms、ratio=6.282。它在 ASU 中获得的实际层周期平均带宽较高。

## 与共享 FIFO 的关系：哪些是事实，哪些是推断

代码事实是 ASU 的全部 NPU 都向同一盘的 Path0 追加 I/O，队列从头部取出，后来的请求不能绕过前面已入队的其他 NPU 命令。OD 则把这些命令隔到 32 条独立通路，再在通路间仲裁；每盘每卡 CIR=1.25 GiB/s，PIR 不限，可以借用，并不是固定封顶。

本实验每个 I/O 命令都是 **176 KiB**，所谓“大读取”是很多相同大小的块。不能说某个大块单独占盘很久，也不能把一整层当成一个不可拆分的原子请求；并发提交的块可能交错。当前提交配置为每卡每 0.1 微秒一块，一层只有几百到一千多块，入队过程远短于实测约 30 ms 的排队时长。

结合共享 FIFO 的代码行为、约 30 ms 的逐块 SSD 排队和上述同 ID 对比，证据支持：其他卡已经排在前面的块让小读取也承担显著背景等待；轮到自己的块时，大读取可以取得比 OD 均分通路时更高的平均供给。OD 则更早完成小读取，但持续竞争时大读取要按自己的通路份额逐步完成。这让不同总长度在两种策略下呈现不同的相对快慢。

这仍不是逐块因果归属：原档没有保存完整队列顺序，无法指出某一层恰好被哪个长请求阻塞了多少毫秒。ASU 的 NPU 接收链路排队也不总是零，尤其大读取有一定贡献；不能把所有 `io_start → io_ready` 时间都归因于 SSD FIFO。

## 与先前 128K 两个例子并不冲突

先前的相同 ID 128K 例子，ASU 的 ratio 分别为 5.125、1.367，OD 为 5.737、1.539；两者仍是两群。ASU 整体曲线没有空档，主要来自 **32/64/80/160/200K 等其他总长度的画像落入中间区域**，不应该用“同一个 128K 画像变得非常随机”来解释全部现象。

完整逐层数字、两种策略各自 warm 分组、相同 ID 交集分组、五组配对请求及原始文件 SHA 均在 `asu_mechanism.json`。运行 `python analyze_asu_mechanism.py` 只读复算，不调用仿真。
