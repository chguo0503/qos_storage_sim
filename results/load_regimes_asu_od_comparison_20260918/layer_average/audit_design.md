# 按层周期统计带宽：数据可恢复范围与审计设计

本文件只读检查三类负载 × ASU/OD 的六个 seed 7 原始结果，不运行仿真，不修改原始结果。统计窗口仍为 `[2000, 4000)` ms。

## 结论

现有数据足以确定每卡层周期的边界，也能在当前严格的预取机制下，用工作量守恒确定**完整周期内每盘为该卡服务的数据量**。但它不足以独立重建逐块 SSD 服务时序，尤其不足以准确分开窗口两端截断周期的服务量。

因此有两种合法做法：

1. 不重跑：只显示完整周期的工作量守恒均值；窗口两端留空或明确标为未求值。若将完整周期均值延伸显示到窗口边缘，只能称为“完整周期均值的可见部分”，它的窗口内面积不代表真实窗口服务量。
2. 需要连续覆盖完整 warm 窗口、并核对实际供给总量：补采逐块 SSD 服务时间，按真实服务区间积分。不能把旧的全盘 10 ms 均值按时间比例分摊给各卡或各层。

`V/D` 并非一概错误：在下述完整周期成立时它是守恒推导得到的精确均值；错误在于未经证明就把它当作任意截断区间的实际服务量，或把下一请求的读取量混成上一请求的读取量。

## 周期如何定义

沿用历史图中的定义，每张卡分别划分：

```text
周期起点 a = 开始计算当前层
周期终点 z = 开始计算下一层
D = z - a
D = 当前层计算时间 + 等待下一层数据的时间
```

周期不是 `io_start → io_ready`，也不是 `compute_start → compute_end`。后一种定义会漏掉使利用率下降的等待。

当前代码为 batch=1、预取深度为下一层：在当前层开始计算时提交下一层 I/O；必须等下一层所有盘的数据通过 NPU 链路接收完毕，才能开始下一层计算。代码证据：`continuous_batch_sim.py:3276` 的 `_handle_compute_schedule`、`:2634` 的 `_schedule_compute_dispatch`、`:4082` 的 `_handle_link_completion`。

对同一请求内部的周期，当前层的所有 I/O 已结束，下一层 I/O 又没有在 a 之前发出，且必须在 z 前结束。这个周期里该卡唯一读取的就是下一层。因此：

```text
完整周期内 SSU s 为 NPU i 服务的数据量 = 下一层放在 SSU s 的 V_next,s
完整周期 SSD 平均供给 b_i,s = V_next,s / D
```

上式中的时间用秒，数据量用 GiB。它包含周期内没有读取的时间，不能只除以 SSD 正在服务该卡的时间。

同一请求各层的 V、C 相同且预取规则不变时，`b_i / B_i = C / D`；这是该次执行的周期工作量核对，不是可独立预测另一种调度效果的公式。

## 跨请求周期必须单列

当前请求最后一层开始计算时，会预取下一请求的第 0 层。此时从当前最后层开始到下一请求第 0 层开始，仍然是一个完整周期，但：

```text
计算属于当前请求
读取属于下一请求
服务量 = V_next_request,layer0
```

其 SSD 平均供给可以正常积分或用完整周期守恒求得；不能拿它除以当前请求的 `V_current/C_current`，再宣称等于当前周期计算占比。两请求画像不同会破坏这个等式。

需求也有两个不同概念：

- 沿用本次三类负载图的“当前已接纳请求画像 V/C”：在请求 admission/completion 处切换；跨请求周期中可能有两个值。
- “为了在当前计算结束前预取完成，下一层需要的 V_next/C_current”：这是另一种需求定义，跨请求处会不同。

本次对比应保留前者，避免更换分类口径。若需求也按层周期取均值，应将现有逐事件需求在该周期内按时间积分，再除以该周期时长；同请求内部它自然等于原 B。

## SSD 已服务与 NPU 已收到不是同一个时序

逐块数据路径为：

```text
SSD 开始服务
  → SSD 服务完成、进入 NPU 链路队列
  → NPU 链路开始传输
  → NPU 链路传输完成
```

原 runner 的实际供给统计用：

```text
SSD 服务区间 = [flow.ssd_activation_time, flow.link_enqueue_time)
SSD 服务速率 = 40 GiB/s
```

NPU 接收应使用：

```text
NPU 链路服务区间 = [flow.link_start_time, flow.link_end_time)
NPU 链路速率 = 50 GiB/s
```

字段名 `io_ready_time_ms` 表示这一层全部数据已经接收完成，不是 SSD 读盘完成。`_register_complete` 在 NPU 链路完成后调用，不过此时 flow 中仍保留真实 SSD 服务起止时间，所以可以在这个回调里补采两种时间。

对完整内部周期，两端均没有该卡相关的在途数据，SSD 服务总量与 NPU 收到总量相同；在任意时间片或 warm 边缘，它们可能不同。不能把接收时刻、SSD 完成时刻和服务区间混为一谈。

## 已有 raw 数据提供什么

六个 case 均有：

- 每层 `compute_start_ms`、`compute_end_ms`、`io_start_time_ms`、`io_ready_time_ms`；每请求 admission/completion。
- manifest 的每个块所属 SSU 与块大小，可求精确 `V_layer,s`。
- `warm_ssd_10ms_GiB_s`：全盘 10 ms 服务平均值，3×200。
- `warm_ssd_GiB_s_by_ssu_npu`：整个 2 秒内每卡每盘的服务平均值，3×32。

六个 case 都没有逐块 trace。`summary.causal_layer_observations` 是计数整数，不是服务记录列表。完整 warm 每卡累计量可用于核对，但不能唯一分解成每张卡左右两个边缘周期各自的读取量；全盘 10 ms 量也丢失了卡归属和区间内部时序。

独立检查了所有与 warm 相交的周期：下一层 I/O 开始时刻均等于本层计算开始；下一层计算开始均等于 `max(本层计算结束, 下一层 io_ready)`；所有 32 条卡时间线完整覆盖 2 秒。

| 负载 | 策略 | 完整内部周期 | 完整跨请求周期 | 窗口裁边周期 |
|---|---|---:|---:|---:|
| 持续过载 full | ASU | 1357 | 192 | 64 |
| 持续过载 full | OD | 1327 | 186 | 64 |
| 局部欠载 semi | ASU | 1199 | 173 | 64 |
| 局部欠载 semi | OD | 1214 | 174 | 64 |
| 持续欠载 random | ASU | 1010 | 143 | 64 |
| 持续欠载 random | OD | 1007 | 142 | 64 |

每个 case 有 64 个窗口裁边周期，即每卡左右各一个。不能为填满图形而把完整 V 全塞入裁边段，也不能按裁边时长占整周期的比例虚构实际服务量。

## 建议的轻量 collector

若重新执行相同输入，保持核心代码、manifest、策略、seed、提交顺序与所有仿真参数不变，只增加旁路观测。以旧结果构建每卡完整周期边界，再在 `_register_complete` 回调中采集或直接积分：

```text
request_id, npu_id, layer, block_idx, disk_id, path_id, total_GiB
ssd_activation_time, link_enqueue_time
link_start_time, link_end_time
```

仅做 SSD 带宽图时，两个 link 时间不是必需输出，但保留它们有利于检验“SSD 已服务”和“NPU 已收到”的差别。观测回调必须调用原回调一次，不更改事件队列或流对象。

每个服务区间与周期、warm 边界求真实交集：

```text
服务 GiB = 40 × overlap(SSD 服务区间, 待统计区间) / 1000
```

这里 overlap 以 ms 为单位。对完整周期，除以完整 D；对窗口裁边段，如果图要求真实 warm 总量守恒，单独使用裁边段的真实服务量 / 裁边段时长，并标记它是部分周期。不要把部分周期说成完整层均值。

若采集器只保存 warm 内 I/O，筛选条件应基于服务区间与 warm 相交，而不是回调发生时间在 warm 内。SSD 在 4 秒之前服务、NPU 在 4 秒之后才接收完成的块也必须计入。若还要核对边缘完整周期均值，需覆盖跨越 2 秒和 4 秒的完整周期，而不只是窗口本身。

## 汇总曲线的一个额外陷阱

32 张卡各自的层周期起止不同。先对每张卡在自己的周期内平均，再逐时把 32 个均值相加，得到的是“各卡周期均值的叠加”。它**不是同一个时间区间内的物理 SSD 平均吞吐**，局部可能高于 40 GiB/s，甚至整机高于 120 GiB/s。

例如 A 在 0～1 ms 独占盘，均摊到自己的 0～2 ms 周期为 20；B 在 1～2 ms 独占盘，自己的周期为 1～2 ms，均值为 40。1～2 ms 处两个均值相加为 60，但真实盘始终只有 40。这是不同平均区间叠加的效果，不是仿真带宽超限。

可选呈现：每卡独立显示周期均值，整机图明确标为“周期平均值叠加”；或使用统一公共边界，对所有卡在同一段内的 SSD 真实服务积分，后者保留 40/120 的容量上限，但不是每卡独立层周期。无论选哪一种，逐盘过载分类仍必须用原先精确请求事件的需求值，不能改用平滑曲线判定。

## 必须核验的边界

1. 重跑结果的每请求 admission/completion、每层时刻、U/SLO、I/O 总量与原结果一致；记录源文件、输入和结果哈希。
2. 每块恰好观测一次；每盘服务时长×40等于块量；NPU 链路时长×50等于块量；同盘服务区间不重叠。
3. 每卡周期无重叠、无缺口；跨请求周期读取下一请求第 0 层；初始首层读取和最后一层无后继读取的尾段单独处理。
4. 对完整周期，每卡每盘的实际积分量等于下一层 manifest 块量；完整内部周期满足 `b/B=C/D`。
5. 对窗口裁边，只用区间真实交集。所有周期裁片的 SSD 服务量之和，应逐卡逐盘匹配旧的 `warm_ssd_GiB_s_by_ssu_npu × 2秒`，逐盘匹配旧 10 ms 曲线积分。
6. NPU 利用率继续按真实计算区间与 warm 的交集计算，不从平滑曲线的瞬时 `b/B` 反推，也不对周期比值作不加权平均。

本审查未补采 I/O、未运行新仿真；以上完整周期守恒值属于基于已核验模型语义的可推导量，不能冒充独立保存的逐块实测日志。
