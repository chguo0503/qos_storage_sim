# 新一轮全局 coflow 比较：报告与独立审计设计

这是新实验的设计稿，不是已经获得的性能结果。最终 PDF 只在完整 36 组结果及正式机制接口冻结后生成，不用旧轮 S1/JIT 或旧 PDF 的数字填充。

## 1. 固定输入，不再跨拓扑调整画像

矩阵为 32 NPU × 5/6/7 SSU × 两个种子 × 六策略，共 36 组。每组完整处理同一批 704 个请求，每个请求 8 层；一条 IO 是一个 128-token KV Block，176 KiB。每盘 40 GiB/s，每卡多盘返回共用唯一 50 GiB/s 接收链路。数据载荷 SSD→HBM，不引入主机 DRAM 缓存。

每个种子内，三个拓扑的请求参数、原始 NPU 绑定、到达顺序和时间完全相同；只有原生一致性哈希对应的 SSD 放置变化。每个拓扑内六策略必须共享同一完整 manifest、logical/native fingerprint、数据源 SHA。执行时允许的选卡不等于改变原始输入。

初始每卡 4 个、合计 128 个已经到达的请求单列。对 t>0 的请求，按固定全局顺序用“累计携带的八层字节 / 目标带宽”生成到达时间；不是把初始积压分摊进到达平均值。

全局顺序先把参考到达时间规范到 1 ps（毫秒数保留 9 位），再按时间和 request_id 排序；正式输入版本必须是 `canonical_reference_ps_v2`。此前跨 Python 的约 1e-13 ms 浮点误差曾交换名义同时的请求，累计工作时钟又把交换放大成数十毫秒。修复前 pilot 只留在 `data/exploratory_precanonical`，不进入正式矩阵。源码一致不能代替实际 manifest 一致。

必须同时展示三个不同量：

- 正时间请求携带工作率：`后续请求完整8层GiB / 最后arrival秒`，目标约 218.31565 GiB/s。
- 初始已经到达的请求数量及完整未来读取工作量，不当作已经提交到 SSD。
- 按连续满算假设得到的计算加权需求 `sum V / sum 8C`，以及每盘倾斜。

218.31565 GiB/s 超过 5 盘合计 200 GiB/s，因而 5 盘属于外部携带工作率过载组，不能称为平均容量可行的 near 组。6/7 盘也须逐盘检查，不能只看总容量。有限轨迹和初始积压不构成无限稳定流量；单个到达桶携带工作也不要求在同一桶内完成。

## 2. 策略权限必须逐级写清

| 策略 | 主要控制位置 |
|---|---|
| Baseline | 每盘 Path0，原生 FIFO |
| Once | 保留原独立 Once 路由函数，读取 5 ms 副本 |
| New once | 原路由引擎 + 全局客户端 Path 承诺/完成账本 |
| 新 S1 | 到达选卡 + 全局入队前发射协调，不是旧独立 JIT |
| 新 S2 | 继承 S1；原生最小 finish-tag 等价集合内跨 Path 选择及 Path 内换头 |
| 新 S3 | 继承 S1/S2；使用共同 coflow 进度键协调各盘分量 |

S1 是“什么时刻把尚未入盘队列的工作交给设备”；S3 是“设备上已排队的不同盘分量怎么协调”。不能混称同一种客户端预取时机控制。最终表需写明每一级是否继承前一级的到达选卡/全局发射，不能仅靠策略名字推断。

所有策略由同一全局 collector 每 5 ms 读取每 SSU，host 查询只拿副本。CIR/PIR 首版静态，运行期 CIR 写入 0；初始配置单列。静态 CIR 数值没改，并不自动证明改变跨 Path 选中顺序仍符合原生仲裁，S2 需要额外的等价候选/权限证明及单测。

对 S3 分别列出：5 ms SSD 副本、客户端已提交/未发射信息、HBM 完成回执、设备本地 pending 信息以及跨 SSU 消息。若用了即时跨盘隐状态，就不能仍声称只是同样的 5 ms host 信息。控制消息延迟和执行开销是否进入数据面时序必须明确。

当前接口中，S3 读取已激活层的客户端剩余块数（减去 HBM 回执），不读取其他 SSD 即时队列。它在本盘原生可选集合中使用相同全局键；不同盘的可选集合和忙碌状态不同，因此不是保证各盘同时处理同一个 coflow 的“全局最优 EDF”。S2/S3 不抢占正在读的 IO，不移走已入队 IO，不跨越原生 finish-tag 允许范围。当前原生模型 PIR 为无限；不能声称已验证有限 PIR 的兼容性。

开发仅使用 6 盘种子 20260906：先比较全局信用窗口 0.1/0.25/0.5/1 ms，以及 S3 的 `least_slack` / `urgent_short`；另保留 fixed 选卡消融，再加 pipeline 选卡的 S1 0.25/1 ms 与 S3 0.25/1 ms 两种 joint-rule，连三个参考共 16 个 canonical 开发 case。新增 S3 是为检查选卡、窗口与 joint-rule 的交互；没有使用验证种子再选参数。客户端配置已按中间一秒 U 首要目标冻结为 pipeline/1 ms，S3 joint-rule 等同一开发集对照后冻结。审计器要求三新策略的有效客户端配置相同，S3 自身跨拓扑种子的 joint-rule 相同；S1/S2 不生效的 joint-rule 参数可以保留默认，但仍应与各自 adapter 声明一致。开发候选不混入主矩阵，也不提前宣称验证集提升。

纯选卡函数的 backlog/counter 数组按物理 NPU ID 0…N−1 排列，返回索引就是 NPU ID；不能把按利用率排过序的列表直接传入再把索引当物理卡号。pipeline 流体评分同样只是启发式，不是混合 SSD/链路依赖下的精确完工时间。

S1 三套客户端数不能混用：Path 账本是“已经规划但还没到 HBM”的 IO；全局信用是“已经实际发送但还没到 HBM”的 IO；coflow 剩余是“该已激活层的全部 IO 减去 HBM 回执”。均不等于 SSD 当前队列精确深度。以信用窗口 \(w\) 毫秒为例，单盘上限为 \(\max(1,\lfloor40w/(1000b)\rfloor)\)，单卡为 \(\max(1,\lfloor50w/(1000b)\rfloor)\)，\(b=176/1048576\) GiB。一批最多规划 64 个发射授权，实际发射消耗信用，HBM 回执归还信用。

S1–S3 共用全局每 IO 0.1 微秒的发射间隔，比原参考策略各卡独立的 0.1 微秒约束更严格。这不等于把策略计算/消息开销加进了仿真：Python 路由、全局规划、ACK 账本、盘内决策的本机墙钟耗时需单列；跨客户端消息与一致性延迟仍为 0，不能由仿真性能直接推断可部署收益。

## 3. 三组指标，不互相替代

主利用率固定为 [1000,2000] ms，逐卡计算区间与窗口求交后除以 1000 ms，再对 32 卡平均。每卡 active=compute+stall；1000=active+idle。若并非全部 32 卡整秒有已接纳工作，必须显式显示空闲，不能把所有低利用率都称为 IO stall。

主 SLO 是 `completion - admission <= 1.5 * 8C`。副 SLO 改用 arrival 起算，包含接纳前排队。两者分母均是完整相同的 704 个 request_id，不使用各策略不同的窗口入组人口。

全程另按每卡分成四个互不重叠的部分：

`makespan = compute + IO stall + 首次/中途空闲 + 末尾等待`

其中末尾等待严格为 `全局最后完工 - 该卡最后完工`，不能把所有 idle 都称为“末尾不均衡”。报告每卡平均 stall、平均及最大末尾等待、末次完工时间跨度，同时列完整 makespan、全程 U、arrival 均值和 P99。

固定一秒更好，并不必然意味着整批更快：减少 stall 可能同时增加尾部不均衡。SLO 是按请求数加权，U 是按计算毫秒加权，也可能向不同方向变化。

## 4. 独立审计，不让同名策略混轮

`build_coflow_report.py` 只接受 `experiment_id=coflow_global_5ms_v1` 和 `regime=arrival218`。沿用的只是旧报告逐层计算/完整请求 SLO 的公共核验函数，不复用旧策略选择逻辑或旧 JIT 审计。

核验项包括：

- 同组输入完整原始归档、源代码闭包 SHA、原生 core/原 Once 引擎不变。
- 独立重算 native/logical fingerprint、每请求 arrival/C/块数、初始各卡 4 请求。
- 重算每个正时间到达点的累计工作时钟，而不只核对最后一个平均数。
- 强制 1 ps 规范化输入版本，并拒绝与正式 experiment_id 相同但修复前的 pilot。
- 重算每盘到达工作率、计算加权需求和实际完成 GiB。
- 输入和执行的逐请求有序 placement fingerprint 相同，忽略允许变化的执行 NPU。
- 原生提交/完成守恒，5 ms 实际 fresh 读取与 collector 事件相符，运行期 CIR 写 0。
- [1,2] 秒逐卡计算/等待/空闲，以及全程四项分解与 makespan 一致。
- 实际 704 请求的两个 SLO，选卡在真实 arrival 发生且快照不来自未来。
- 全局实际 sent−HBM ACK 信用上限、最后归零、激活 8×704 层和实际提交/完成守恒。
- 跨 Path 等价候选集合计数、改变顺序次数、原生最小 tag 容差及已记录决策；未记录决策还须依赖逐决策运行时断言和集成测试，不能用计数器伪装为完整时序回放。
- S1–S3 的信用窗口和选卡配置一致且与各自归档声明一致，S3 生效的共同优先级规则在整个正式矩阵中固定；不要求 S1/S2 无效的 joint-rule 参数替 S3 作选择。

空目录只会输出缺失的 36 个 case，不会填充 0 利用率或生成看似完整的 PDF。输入和源码归档作为不可变对象核验，避免重复解析大 manifest；不同实验结果不递归混入。

## 5. 为什么仍可能有等待：两种计算预算

同请求从第 l 层预取下一层，隐藏预算是本请求当前层的计算时间 C。跨请求 L0 不同：当前协议只在前一个请求最后层开始计算时，才激活下一个已到达队首请求的 L0；隐藏预算是 C_previous，不是下一请求的 C_next。

仅考虑孤立硬件的必要读取时间下界为 `1000 × b × max(max_s K_s/40, sum_s K_s/50)` ms。它没有包含盘间首块/接收流水的启动耗时、发射间隔和竞争；下界小于预算只能说明“没有这个容量证书”，不能证明一定没有 stall。

容量模块已独立核对本轮七种画像：单层孤立下界均小于自身 C。但给定一项具体相邻转换，前一个 32K/128 请求 C=1.178025959 ms，后一个 192K/512 请求每层 1532 IO、接收链路下界 5.142822266 ms，则该 L0 至少需要额外 3.964796307 ms，尚未计竞争。这是协议加这次转换的局部不可行性证书，不证明这种转换一定在某次策略执行中出现，不证明每个策略的固定一秒上限，也不等于该请求 admission SLO 必失败。

正式报告将从实际 S3 [1000,2000] ms 找到并标注一个真实转换，再给 request_id、前后画像、激活、前请求完工/预算终点、HBM 到齐和实际 stall。若窗口里没有这个转换，就如实报告不存在，不拿冷启动或全程示例代替窗口证据。以上数值来自原始 `data` 参数和真实 ordered placement 的容量核算；尚非新策略性能结果。

## 6. 版式与复现

主目录仅放最终 PDF；原始结果/audit/CSV 在 data，图在 figures，Markdown 在 docs。Figure 2 拟为横向独立页：三拓扑面板 × 六策略行 × 32 固定物理 NPU 列，不逐行排序；最终文字至少约 7 pt，格内整数，精确数值留 CSV/JSON。

正文先报告成功及退化，不以开发集收益冒充验证集收益。跨拓扑、跨种子的完整结果都保留；控制代价必须在正文，不能只放脚注。每个新独立函数的必要输入、返回值、调用事件与组合方式在接口冻结后补齐。

当前检查命令：

```bash
python -B -m pytest -q test_coflow_report.py
python -B build_coflow_report.py
python -B build_coflow_report.py --require-complete
python -B build_coflow_report.py --render
```

混用 unittest CLI 可能漏掉 pytest 函数式测试，因此统一使用 pytest。单测不能代替 36 组完整仿真，更不能证明硬件在线控制代价足够低。
