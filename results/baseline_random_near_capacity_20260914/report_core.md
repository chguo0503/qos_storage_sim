# 为什么按这些公式寻找请求

这份说明只解释研究方法；完整结果见 [逐组统计](comparison.md)，最终结论以研究报告为准。代码中的 `baseline` 是**每块 SSU 各有一个 Path0 FIFO**，不是所有盘共用一条队列，也不是两个请求类别各自有不可借用的限速。

## 先纠正一个因果关系

另一张卡的长计算不会占用本卡的计算器。真正可能挡住短请求的是：**它的读取排在别人的读取后面，没赶上下一层需要数据的时刻。** 长计算通常反而提供了更长的预取时间。

所以选请求时，我同时看三个数，而不是只看“长流、短流”名称：

```text
V：这一层要从 SSU 读多少数据。
C：这一层实际计算多久。
B = V/C：希望把下一层读取藏进本层计算，需要的平均带宽。
```

V 用 GiB、C 用秒时，B 的单位就是 GiB/s。固定画像的一层内，B 是参考常数；实际服务带宽会变。总输入、miss 数、命中比例都影响画像，单凭 miss 百分比不能确定 C。教程里“B 正比于 (1-p)/p”中的`p=miss token数/总输入token数`，也就是未命中比例；这个关系还要求每 token 计算成本近似不变。本次使用 data 的 C 或明确标注的拟合 C，没有把这个简化关系当成所有请求的共同实测规律。

## 第一步：用 B 决定一个可行的混合比例

设 L 为计算较长的请求，S 为计算较短的请求。每卡数量比为 nL:nS，32张卡按同一比例准备请求，然后各自独立打乱。

```text
理想总需求 = 32 * (nL*VL + nS*VS) / (nL*CL + nS*CS)
rho = 理想总需求 / (盘数 * 每盘带宽)
```

这不是把所有请求的 B 直接取算术平均：请求计算时间不同，必须用它们实际占用的计算时间加权。每请求都是8层，因此这个公共倍数在公式上下抵消。

若希望理想平均刚好等于容量，先算每卡平均可用带宽 `b_target = 总容量/32`，再解：

```text
nS/nL = (b_target*CL - VL) / (VS - b_target*CS)
```

当 `min(B_L,B_S) < b_target < max(B_L,B_S)` 时，才有这种严格一高一低的正比例混合。本次主要配方选择低B的长计算与高B的短计算，因此对应 `B_L < b_target < B_S`；“计算长/短”本身不决定B大小。之后选接近这个值的简单整数比例，重新算 rho；不能为了凑整数，悄悄把平均负载推高很多。

**rho 接近1只说明整批请求的理想平均接近容量。它不保证任何时刻、任何盘都欠载。** 仿真另按事件逐盘检查当前 V/C，并用实际服务区间计算盘忙率。首层预取的真实读取也全部执行，不会从物理流量中删除。

## 第二步：算短请求有多大的权重

```text
f = nS*CS / (nL*CL + nS*CS)
```

f 是输入中短请求的**纯计算时间占比**。请求数量很多，f 仍可能很小。例如一个长请求计算1秒，一个短请求只算1毫秒；十个短请求也只有10毫秒。让这十个短请求等待，并不自动损失很多整机计算时间。

f 是用输入算出来的设计量。它不是实际 warm 窗中短请求的占卡时间比例；短请求等待后会占卡更久，窗口内执行到的请求也会变化。

## 第三步：反算需要多大的等待，才值得测试

设 w 是**所有短层**的平均额外等待，零等待的层也算进去。先作一个有条件的近似：长层不等待，长期完成比例接近输入比例，暂时把每层都看作同样的稳定预取周期，忽略首层交接和窗口边界。

```text
U_approx = 1 / (1 + f*w/CS)
```

理由很简单：原来完成一份工作需要一份纯计算时间；现在额外增加了短层等待。总耗时变大，计算时间没有变，因此利用率下降。

用户最终希望长期 U 落在 80%～89%，不要求恰好80%。对任意目标 U（代入小数），反算：

```text
w_needed = (1/U_target - 1) * CS / f

目标89%：w_needed ≈ 0.12360 * CS / f
目标85%：w_needed ≈ 0.17647 * CS / f
早期80%：w_needed = 0.25 * CS / f
```

早期候选表保留当时80%的筛选阈值，避免事后改写预测；后续另外核对89%和85%。

这回答的是“在上述近似下，平均等待需要达到什么数量级”，**不是保证实际会等这么久**。例如主组 `main512` 的 CS≈3.702ms、f≈19.68%，按早期80%连续层目标需要约4.702ms的平均短层等待；不是当前89%目标的阈值。5个种子实际只有约0.998ms，因此长期 U 仍约95.02%。一个特别差的短层截图不能代替这个含零等待的均值。

### 本次只有8层，要怎样修正

上面的短公式便于筛选，但本次一个请求只有7个内部预取周期，首层交接要另算。设 dL、dS 为每请求首层没藏住的平均等待，更准确的固定完成混合近似是：

```text
纯计算 P = 8 * (nL*CL + nS*CS)
内部等待 W = 7 * (nL*wL + nS*wS)
首层等待 F = nL*dL + nS*dS
U ≈ P / (P + W + F)
```

如果只让短内部层等待，其他等待全为零，目标阈值为：

```text
wS_needed = (8/7) * (1/U_target - 1) * CS/f
```

这比早期连续层近似大8/7倍。实际首层也会等待，所以最终按真实日志分别核对两项，不能把全部8层等待和首层等待重复相加。有限窗口内执行的请求比例又可能变化，因此最终窗口 U 仍直接按计算区间求和。

## 第四步：检查 FIFO 能否真的制造出这些等待

B 描述平均需求，但没有包含“前面突然排了多少读取”。单次 V 很大时，即使 B 不高，也可能给后来的短请求留下一段较长的排前工作。

不过 Baseline 的服务单位是176KiB块，不是整层不可分割的大包；长层提交与其他请求可能交错。所以 `VL/总盘带宽` 只是一个读取尺度，不能直接冒充实际等待。需要从日志看真正排在前面的剩余块、目标读取何时开始、何时全部到齐。

一个便于选输入的尺度比是：

```text
R = (VL / SSU总带宽) / CS
  = 一次长读取的盘侧服务尺度 / 短层计算预算
```

例如384K组，长读取按总盘速率折算约1.607毫秒，而短层只算0.717毫秒，R约2.24。这个长读取如果形成足够靠前的剩余工作，就有机会让后来的短层错过截止。R不是平均等待，也不是充分条件：块可以交错，多个读取也可以共同排在前面。因此R小仍可能等，R大也不保证每层都等。还要配合第二步的短计算权重f、第三步的等待阈值，以及真正的排队日志。

平均带宽够，也不表示每次都及时：短层需要数据的时刻已经到了，前方读取却还没处理完，它就必须暂停。即使盘稍后出现空闲，刚才损失的计算时间也补不回来。等待还会推迟本卡后续层的读取释放，所以实际收到的平均带宽也可能低于整批输入按“完全不等”算出的需求。

主组的1:24也能反算。总容量320GiB/s除以32卡，得到用于配输入的平均预算d=10GiB/s；它不是每卡的限速。每个长请求配q个短请求时，让`(VL+q*VS)/(CL+q*CS)=d`，解出`q=(d*CL-VL)/(VS-d*CS)=24.4279`。取24后，32卡理想总需求为319.0009GiB/s。每卡33长、792短只是按这个比例准备数量，再把整条队列完全打乱，没有反复播放固定的25请求小段。

这也说明为什么32卡不必重现4卡的低利用率：如果增加NPU同时增加盘带宽，一次长读取的服务尺度会缩短；独立队列的释放时刻也会变化。只保留“长、短”两个类别名，没有保持R、f、负载率和输入顺序的分布，就不是同一个竞争条件。

还必须算每卡50GiB/s接收链路。若一个短层直到计算开始后 tau 秒才开始接收数据，那么：

```text
最早收完时间 >= tau + VS/50
如果 tau > CS - VS/50，就一定赶不上本层计算结束。
```

这是同请求内部预取周期的条件下界。磁盘和链路可以边读边传，不能把完整盘服务时间与完整链路服务时间机械相加。跨请求首层使用前一个请求末层的计算预算，需要单独统计。

## 怎样与教程中的平均 b/B 对上

对同一请求内部、完整的一个层周期：

```text
D = C + 额外等待
平均 b = 这个周期实际收到的下一层数据 V / D
B = V/C
因此：平均 b/B = C/D
```

这是一条可以逐字节核验的事后记账关系，不是瞬时利用率，也不是只看 B 就能提前算出等待的算法。

早期main512有一个正等待样本：短层 C=3.702ms，等待1.739ms，总周期D=5.441ms；V=43.3125MiB，B=11.425GiB/s，平均b=7.774GiB/s。因此这个周期的计算比例是68.04%。[局部PNG](runs/main512_ssu3_h22000_seed7/baseline/figures/internal_median_wait/baseline_random_short_internal_cycle.png)画出了前方长请求读取、计算截止和累计收齐过程。这个局部周期虽差，整机长期仍约95%，不能据此说整机很差。该例部分时间名义需求超限，也不能证明严格欠载下的反例。

整机统计始终使用原来的口径：

```text
U_actual[T] = T窗口内全部实际计算卡时间 / (32*T)
```

完整内部层周期的 b/B 必须按周期持续时间加权；请求交接和窗口截断部分按真实计算补回。不能平均32张图上的蓝紫线高度比，也不能用“整窗平均供给/整窗平均需求”替代 U。

## 用当前87%左右的例子再算一遍

384K组每卡33个长请求、792个10K短请求，再把整批请求独立Random。32卡、8盘，理想平均负载99.69%。这里长短计算时间都有data区间外推，结论是模拟器构造实验，不是实机测量。

先看[同一短请求内部的一层](runs/context8_L384m1024_S10m128_ssu8_h22000_seed7/baseline/figures/internal_median_wait/baseline_random_short_internal_cycle.png)：

```text
本来只算：0.716653毫秒
算完之后，还等IO：1.154052毫秒
从这层开算，到下一层能开算：1.870704毫秒

这个周期用于计算的比例 = 0.716653 / 1.870704 = 38.31%

这层需求B：18.502534 GiB/s
把等待也算进周期，实际平均收到b：7.088180 GiB/s
同周期平均b/B = 7.088180 / 18.502534 = 38.31%
```

最后几位由未四舍五入的原始时间计算。两种算法得到同一个38.31%，因为它们在核算同一层、同一批字节、同一个时间段。图中紫色长请求IO先被盘服务，目标短IO直到计算截止后才得到服务；**阻塞来自读取队列，不是别的NPU正在做长计算这件事本身**。

但这只是有等待的短层中间附近的样例。不能把38.31%当成整机利用率，也不能把1.154052毫秒当成所有短层的平均等待。该组长窗中所有短内部周期（包括不等的周期）平均只等0.467224毫秒。

最后按整机真实时间核算：2～20秒是18秒，32卡共576卡秒，其中计算503.922796卡秒。所以整机U=503.922796/576=87.4866%。剩下的时间主要是短内部层等待56.985434卡秒，以及首层交接等待15.091770卡秒。

从“读取排在后面”到“这层b/B下降”，再到“全部卡时间汇总为87.49%”，需要这三步。只看一条带宽线或一个很差的层，会漏掉其余层和长请求的计算时间。

## 这套方法什么时候会失准

- 教程里`B与(1-p)/p成正比`还要求每个未命中token的计算成本近似相同。本例有效成本`C/miss`在384K长请求中约0.06476ms/token，在10K短请求中约0.00560ms/token，并不相同。因此不能只凭miss比例比较B；本次直接使用各画像的C和V。这里的`C/miss`是有效平均成本，不是在断言prefill逐token串行计算。
- 把少数很坏的层当作所有层的平均等待，会高估整机损失。
- 短画像改变后，队列变短，原配方的等待未必保留；本次确实出现了这种预测失败。
- 长画像改变后，C、V、Once策略的类别路径池、首层交接成本和窗口内人口可能一起变化，需要逐项说明。
- 每卡队列都含长短请求，不等于每卡在 warm 两秒内都实际算过两类；本次逐卡核对，并保留不满足的种子。
- data区间外的拟合是模型假设。训练残差很小，也不能证明未测长度的真实设备耗时。

我们把这些条件保留在表格与日志中。仿真用来验证数学筛选的假设，不会只留下符合预期的结果。
