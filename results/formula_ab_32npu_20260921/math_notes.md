# 五组 A/B 扩到 32 张 NPU：为什么统一用 6 块盘

这份笔记解释**运行前的容量筛选**，不把数学上界当成仿真实测利用率。输入保留原五组画像、每卡 A:B 请求数量比 1:12、三个种子 7/19/43、8 层和原随机洗牌方法。只将原生成器的卡数从 8 改成 32，再检查实际 RingHash 分盘。

`horizon_ms=4500` 用于决定准备多少请求，不是运行到 4.5 秒就停止。原生成器按纯计算工作量生成足够长的有限队列，之后应完整排空。五组每卡分别有 52、65、65、78、78 条请求；每卡都含 A 和 B，全部到达时间为 0。

## 1. 总容量够，不等于每块盘都够

对一个请求，先计算它在盘 s 上的名义需求：

```text
B_request,s = 这个请求每层在盘 s 上读取的字节数 / 每层纯计算秒数
```

这里的“需求”表示希望把读取藏在计算里所需的平均速率。它不是 SSD 此刻实际传输速度，也不是请求一次提交时的突发速率。

如果只看所有盘合起来的容量，任意 32 个当前请求的总需求最多为：

```text
总需求上界 = 32 * max(A的总需求, B的总需求)
```

五组的这个上界约为 137.62–152.61 GB/s。3 盘只有 120 GB/s，不够保证所有组合；4 盘合计 160 GB/s，已经通过**总量这一关**。

但是，RingHash 并不保证每个请求都精确均分到各盘。短请求的块数较少，分盘比例的波动尤其明显。因此不能直接用“总需求除以盘数”证明逐盘欠载。

本次用的是更保守、可以直接复算的检查：

```text
先对每张卡、每块盘：
    找出该卡所有输入请求中最大的 B_request,s。

再对每块盘：
    H_s = 把 32 张卡各自的这个最大值加起来。

如果每个 H_s 都严格小于 40，
那么无论每张卡当前推进到哪条请求，普通名义需求都小于该盘容量。
```

这相当于允许每张卡恰好选中对该盘最不利的请求，因而比实际轨迹检查更保守。它对同一冻结输入下的不同策略都成立，不依赖它们推进速度相同。

下表取三个种子、所有盘中的最大 H_s。单位全部是**十进制 GB/s**，每盘容量为 40。

| 画像组 | 4 盘上界 | 5 盘上界 | 6 盘上界 | 通过该检查的最小盘数 |
|---|---:|---:|---:|---:|
| XY12_32 | 45.349201 | 37.913890 | 33.026153 | 5 |
| XY12_24 | 47.275395 | 39.680068 | 34.846341 | 5 |
| XY12_20 | 49.038662 | 40.942289 | 36.259339 | 6 |
| XY12_16 | 51.322102 | 42.820456 | 38.040147 | 6 |
| X16 | 51.322102 | 42.820456 | 38.040147 | 6 |

因此统一使用 **32 NPU、6 SSU，每盘 40 GB/s**。这里的“最小盘数”是通过上述任意组合保守检查的最小值；上界超过 40，只表示这个保证没有建立，不能据此声称实际仿真一定发生过载。

## 2. 原来的“一个 A 就堵住 B”条件不能直接搬到 32 卡

原画像中 A 读取大、计算长，B 读取小、计算短。定义：

```text
x = V_A / V_B       读取量之比
y = C_A / C_B       每层计算时间之比
```

先考虑一个理想的共享总带宽池：一个 A 的整层读取完整排在 B 前方，而 B 还剩完整的 C_B 计算窗口。想同时满足“当前组合欠载”和“这个 A 单独就让 B 来不及”，需要：

```text
n_A * B_A + n_B * B_B < 存储总带宽 < V_A / C_B

因此必须满足：
n_A/y + n_B/x < 1
```

当 32 张卡都有当前请求时，n_A+n_B=32。不管它们怎样组合，总有：

```text
n_A/y + n_B/x >= 32 / max(x,y)
```

| 画像组 | x | y | 32/max(x,y) |
|---|---:|---:|---:|
| XY12_32 | 6.4266 | 11.9991 | 2.6669 |
| XY12_24 | 8.6945 | 11.9983 | 2.6670 |
| XY12_20 | 10.5285 | 12.0010 | 2.6664 |
| XY12_16 | 13.3053 | 11.9984 | 2.4051 |
| X16 | 13.2848 | 14.1577 | 2.2603 |

右边已经全部大于 1，所以在这个理想总带宽池模型中，**32 卡均活跃时，欠载与上述“单个 A 完整阻塞”条件无法同时成立**。请求数量比 1:12 不能代替此刻的并发数量比 n_A:n_B。

这不证明真实系统没有等待：多盘分布、多个请求积压、块级提交交织、跨请求预取和接收端限制仍可能造成等待。它只说明不能直接把原 8 卡实验的那一条机制当成新实验的预测。OD 又将不同 NPU 放在独立 Path 中，原来同一 Path 内的跨卡 FIFO 排队条件也已经改变；多张卡仍共享物理盘。

## 3. 需求超过 OD 保底，不代表供给一定不够

OD 每盘有 32 条独占 Path，配置的每卡每盘保底为：

```text
40 / 32 = 1.25 GB/s
```

统一 6 盘后，实际输入中单卡单盘的最高需求如下。数量按 seed 7/19/43 分别给出。

| 画像组 | 最高单卡单盘需求 GB/s | 存在超 1.25 请求的卡数 | 超 1.25 的请求数 |
|---|---:|---|---|
| XY12_32 | 1.136360 | 0 / 0 / 0 | 0 / 0 / 0 |
| XY12_24 | 1.207645 | 0 / 0 / 0 | 0 / 0 / 0 |
| XY12_20 | 1.287409 | 2 / 3 / 3 | 2 / 3 / 3 |
| XY12_16 | 1.370633 | 11 / 11 / 10 | 13 / 13 / 12 |
| X16 | 1.370633 | 11 / 11 / 10 | 13 / 13 / 12 |

这些峰值都来自 B。不能把 `CIR=1.25` 当作每条 Path 的最大速率：盘带宽有剩余时，可以按原生调度规则借用。借用还受活跃 group 和 group 内活跃 Path 的分布影响，不是任意时刻简单均分给所有活跃卡。

因此，“有少数请求需求超过 1.25”不能直接推出 OD 利用率很低；反过来，“需求低于 1.25”也不是所有离散读取都必定零等待的证明。是否等待、等待多久，最终要看原始层时序和实际服务。

## 4. “普通需求欠载”的边界要说清楚

沿用原实验定义：在请求从上卡到完成的整个区间内，持续计入该请求的逐盘 V/C；它正在计算或正在等待 I/O，都计入。前一请求末层计算时额外预取下一请求 L0，这部分突发**不额外加入普通需求**。

这个豁免不删除任何时间段，也不删除 L0 等待：L0 导致的 NPU 空等仍完整计入利用率和请求耗时。因而本实验能够保证的是“按原定义的普通名义需求逐盘欠载”，不是“包含所有跨请求预取突发的任意瞬时带宽请求都不超过容量”。实际物理 SSD 服务仍受容量限制。

另应保留原有内部层审计：对 k>=1 的未完成读取统计 V_s/C，结束点取整层所有盘到齐的 io_ready，以得到保守的逐盘待处理需求包络；不要把这个包络或 V/C 叫作真实瞬时 SSD 吞吐。

## 5. 保持原画像和统计口径，避免换了题目

- **单位：**40 GB/s 是每秒 40×10^9 字节，不是 40 GiB/s。原生接口以 GiB 为体积单位时，容量应传入 `40*1e9/2**30`。本文所有带宽表已转换为十进制 GB/s。
- **读取量：**每层 V=`(总 token 数-miss)*1408` 字节。每块最多 128 token，最后不足 128 token 时按实际尾块读取，不能一律向上补齐到完整块。本次逐请求调用原 RingHash 函数，没有强行平均分盘。
- **计算时间：**保留原配置。XY12_32 的计算时间来自 data 网格内插值；24K、20K、16K 的 B 使用原 32K/48K 数据作长度外推，并进行 miss 方向插值。X16 的 A 是原始 200K/2048 数据行。应明确披露外推，不能把所有画像称为直接抽取的原始 data。
- **利用率：**warm `[2,4)` 的真实计算区间交集，除以 `32*2000 ms`。不能用只计算请求平均值替代这一指标。
- **TTFT/SLO 代理：**使用 `prefill完成时间-上卡时间`，基准为该请求自身 8 层纯计算时间；SLO×1.5 表示耗时不超过基准的 1.5 倍。它不含上卡前卡内排队，不是完整端到端首 token 时延。
- **CDF 与 warm：**原五组公式 A/B 的 CDF 使用完整输入人口，包括启动阶段。warm SLO 则使用 `[2,4)` 内上卡的请求，并跟踪到它们完成。两个口径应分别标注，不能把全人口 CDF 在 1.5 处的百分比直接写成 warm SLO。跨种子先分别计算比例/CDF，再对三个种子等权平均，不能用合并请求冒充种子等权。
