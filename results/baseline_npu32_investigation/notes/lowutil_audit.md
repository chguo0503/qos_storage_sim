# 旧四卡低利用率实验的独立复核

2026-09-07；子任务 `audit_lowutil`。本文件只记录审计、机制推导和独立小型测试；原实验文件未修改。

## 已确认的事实与边界

主要依据：`results/baseline_4npu_ssu1_low_utilization/docs/report.md`、`docs/path0_deadline_and_staggering_notes_v3.md`、`data/result.json`、`data/tutorial_sensitivity_results.json`、`data/path0_phase_probe.json`，以及对应 Python runner 和 `continuous_batch_sim.py`。已复读 `.learnings` 中关于相位、窗口、固定/变化输入和配对种子的修正。

旧反例同时固定以下条件：4 NPU、1 个 40 GiB/s SSU、每卡 50 GiB/s 接收链路、每请求 8 层、batch=1、单层预取、跨请求 L0 预取开启；每卡始终重复自己的固定 profile，全部请求在 t=0 到达。Baseline 在该 SSU 上所有物理块均排入 Path0 FIFO。

|---:|---|---:|---:|---:|---:|
| 0 | (1,169) | 1.148071 | 0.582149 | 1.925903 | 21.655961% |
| 1 | (192,368) | 263.505859 | 12.390165 | 20.768888 | 83.248430% |
| 2 | (192,896) | 262.796875 | 29.856563 | 8.595684 | 100% |
| 3 | (192,896) | 262.796875 | 29.856563 | 8.595684 | 100% |

总名义需求 39.886158 GiB/s，低于 40；实际 SSD 忙 86.910452%，实际吞吐 34.764181 GiB/s，平均 NPU 利用率 76.226098%。每卡 compute+barrier 覆盖完整 1000 ms，不存在缺输入造成的卡空闲。物理 trace 共 207,297 个与窗口相交的块，Path0 enqueue/service 次序零错配；观察器前后 summary 哈希相同。

NPU0 有 783.440389 ms barrier，其中 779.589750 ms 与其他卡的 SSD 服务重叠，是明确的外部排队伤害。NPU1 的 barrier 167.515696 ms 却几乎都与自己的 SSD 服务重叠：已经轮到它，但它的大读取尚未结束。因此“全部 stall 都是等待其他卡”不正确。

只改固定路由为四个 Path 的旧诊断对照：平均 95.8124%、短卡 100%，但 NPU1 仍约 83.25%。共享 FIFO 是关键因素；SSD 突发和单层预取余量也共同影响结果。

长度 1K 来自 32K/48K 计算时长斜率外推，NQL=169/368/896 来自相邻原始格点插值。此实验不是全部原始 data 格点，不能声称真实硬件测得这个 profile，也不是线上分布抽样。

## 造成 stall 的条件：不是 NPU 数本身

在本模型中，当前层开始计算时发出下一层预取，下一层在全部 I/O 到 HBM 后才可计算。因此一次预取的判据是 `ready_time > deadline`；固定计算时长且没有其他调度空档时，同一卡相邻 release 间隔为 `C + max(0, L-C)`，其中 L 是预取 release→HBM-ready 延迟。

在单盘 FIFO、已入队的前方工作固定、自己的命令连续跟随的简化局部模型下：`前方剩余 SSD 服务 + 自己 SSD 服务 + 接收尾延迟 > C` 就导致 exposed stall。实际按原生 0.1 us/命令提交时还应保留提交时序、命令交错和 HBM 队列；这个标量公式是解释/局部诊断，不代替完整仿真。

旧短卡自己的 SSD 服务只需 0.028029 ms，在忽略 HBM 的近似下只能容忍约 22.696772 MiB 的前方工作，即约 132 个完整 176 KiB 命令。单个 192K 大流约 1,529 条命令、服务约 6.416 ms，就足以超过它的 0.582 ms 预算。大流在 C=29.857 ms 内读完，即使排队也不停算，因此不会因等待继续改变自身周期。短卡发生 stall 后虽然错开，仍可落到下一次大队列的后面。

故足以制造明显损失的组合是：持续短 deadline 的受害者 + 共享 FIFO 上的大块工作突发 + 足够高的竞争占空比 + 只有一层预取余量。平均总负载不过载不是满足每个短 deadline 的充分条件。另一方面，该组合不是必要条件的完整刻画；物理过载、热点盘、接收链路瓶颈、入口缺工作也会降低 NPU 利用率，原因需要另分。

## 近同步不是必要条件

已有 NPU3-only 启动偏移探针保持 C/V/输入数量等不变，并测量真实稳态 release 相位，而非把启动偏移当成稳态结果：

| NPU3 启动偏移 | 稳态相位分离/ms | 平均 U | 短卡 U | NPU1 U |
|---|---:|---:|---:|---:|
| 0 | 0.004196 | 76.226098% | 21.655961% | 83.248430% |
| P/4 | 6.461278 | 78.317299% | 15.152568% | 98.116628% |
| P/2 | 10.518068 | 78.439451% | 14.437307% | 99.320498% |
| 3P/4 | 10.490039 | 78.439451% | 14.437307% | 99.320498% |

两大流已显著错开，平均仍低于 80%，且短卡反而更差。不能把“自然错开”与“不排队”或“满足 deadline”等同。也不能凭三个点断言所有偏移都无效；偏移探针没有逐物理块 trace，不能把短卡恶化的更细机制说成已证实。

其他已保存敏感性：submit seed=1 精确复现均值；四卡启动时刻 0/7.5/15/22.5 ms 得到 78.3173%；仅 NPU3 NQL 改成 900/928 时均值 78.5778%/78.2365%。故坏例不依赖唯一种子或大流绝对同周期，但这些是五个确定性点，不是噪声/随机分布普适性试验。

旧搜索只是在固定三个 blocker 时，对短卡 NQL=153..192 共 40 点复跑，169 是此网格最低。不是连续参数或所有工作负载上的全局最小值。十个 100 ms 子窗口均值约 75.02%–77.31%，支持该测量秒内重复损失；无限时间收敛仍需单独论证。

## 为什么新的 32 卡变化输入容易表现较好

除了分盘缩小每盘突发量，新变化输入在同一卡上切换 profile，短 profile 的请求个数占比不等于其占据的卡时间。

按 `multi_ssu_stall_experiments/docs/multi_ssu_experiment_report.md` 的原始 data 7种 profile 和 near 配额精算：

| 配额 | 32K 两种短 profile 请求占比 | 理想计算时间占比 | 192K 三种 profile 理想计算时间占比 |
|---|---:|---:|---:|
| 6 SSU near | 6/22=27.2727% | 1.581088% | 92.805216% |
| 7 SSU near | 6/22=27.2727% | 1.803489% | 91.793174% |

原始四卡固定例则有 25% 的卡永久承受短计算 budget。新实验大量卡时间运行 C=17/34/68 ms 的长 profile，更容易覆盖多盘读延迟。上表是全输入理想计算权重，不是特定 [1000,2000] ms 窗口的实际活跃组成，不能直接把它当作窗口归因。

## 公平扩大到 32 卡的控制设计

1. **保持干扰结构的平铺**：8 份旧四卡组→32 NPU/8 SSU，每组四卡只读该组 SSU。每盘负载仍39.886158，卡 link/C/V 不变。这是检验“32 本身会救 baseline”的最干净反例。物理子系统相互独立，所以预期重现低利用率；统一全局提交 RNG 可改变微小相位，具体数值仍由实测确认。
2. **同 profiles、相同总容量改为 striping**：相同32条固定流，分散到8盘，改变的主要是每盘突发/并发结构。单个约263MiB层若均匀分8盘，每盘约32.9MiB、0.802ms，已远小于旧6.416ms但仍可超过外推短卡0.582ms。还需要全部盘完成屏障和50GiB/s卡链路，不能简单除8外推性能。
3. **容量归一化**：旧profile平铺8份总需求319.089265 GiB/s；32/6和32/7容量仅240/280，直接迁移必过载。若要做非过载对照，可增加至8盘，或显式统一放慢C使每盘rho相同；后者是合成计算控制，不再是原始data画像。数据落盘热点还要求逐盘而非只看总和。
4. **原始 data 格点轨**：使用下文 fixed profiles，避免1K外推与尾块；先固定各卡角色，再分别改为卡内profile随机切换、启动相位扰动、不同SSU放置。
5. **少量公平保持不变项**：同一策略对共享完全相同不可变 requests、到达、placement和native submit种子；固定绝对主窗口，同时报告每卡active/idle/stall、完整请求集延迟及完工时间。调度改变卡分配时应另列作联合策略。

原 runner `_profile(table,npu_id,key,role)` 可构造画像；`_placement(profile)` 只落 SSU0；`ContinuousBatchRequest(..., placement=(tuple((ssu,size),...),))` 支持显式放置。旧 `_build_requests` 有四卡固定 counts=(3000,150,150,150)，不能直接用于32卡；需要按各卡的计算时长和总测试时长设置持续 backlog。

## 其他策略不保证在一切坏输入上表现好

原生Once在已完成的固定FIFO受害者用例中明显改善，符合多Path绕开排队的机制；旧四Path固定映射只恢复到95.8%，而Once约100%，已经说明“有多个Path”不是充分算法描述。

5ms遥测远大于外推短卡0.582ms或原始短卡1.18–3.70ms计算budget，仅靠旧队列快照不能保证这些deadline。共享客户端已发送未ACK账本可以提供额外因果信息，但需按新coflow策略实现评估，不能把native Once结果移植给5ms版本。多SSU下还存在最后一盘/最后接收块的完成屏障；只优化某盘不保证整个层早完成。

物理过载/热点/卡接收带宽不足不可能由排序消除。EDF或最小slack也可能持续照顾巨大逾期层，短任务策略又可能伤害长任务尾延迟；更高平均利用率不等于更高逐请求SLO。必须保留失败用例，并同时报最差卡与请求级尾部，避免靠牺牲少数卡提高平均值。
