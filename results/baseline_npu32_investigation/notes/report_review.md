审阅对象：`docs/report.md`，SHA256 `311780c75bc9118e8dda08c0d1937d9ddd2bf4f9fd1b6ef72b6794ca98ce0261`。行号对应本次读取的 223 行草稿。仅审阅已写结论；未将待补策略全表列为问题。未改报告或任何模拟核心。

## 1. Hash 输入并未实际缩放 C（第 98 行）

原句“更换为原生hash并按最热盘归一化到98%以内”会使读者以为 hash 的低 U 是 C 被调过的结果。实际 `screen/inputs/strong32_hash_feasible.json.gz` 的 `compute_scale_actual=1.0`，最热盘名义需求为 **39.18610009661609 GiB/s**，原本就低于 39.2；其主窗口 U 为 **50.96218121582566%**。这是不修改 C 的布局反例，应该保留这个更强而准确的事实。

建议替换：“更换为原生 hash 后，最热盘为 39.186 GiB/s，已低于 98% 阈值，因此无需缩放 C，Baseline 仍约 50.96%。”后续“这些 C 缩放”改为专指六盘变体。

六盘相关数字没有错误。我从 manifest 每个请求的实际 placement 和 C 重新求和，逐盘名义需求得到：

`[39.18457222862343, 39.19999996079973, 38.43651396799055, 38.43651396799055, 38.42108623581425, 38.40565850363795] GiB/s`。

与记录逐项一致；实际统一 C 倍率 **1.2493208762775747**，最大接收链路比例 **47.33228231688561%**，主窗口 U **47.69277981219221%**。因此 38.41–39.20、1.24932、47.33%、47.69% 均可保留。

## 2. 四格到达反事实应就近披露 Baseline 包装器差异（第 141–148 行）

四格中 A+fluid/B 的原始与交错输入由同一个 native assignment 包装器运行；这条直接反事实成立。Baseline 原输入则来自 shared/coflow 包装器，新输入来自 native Baseline。目前正文在表格附近没有披露这一差异，第 190 行关于一般遥测差异也不足以解释这两格。

我重新读取 aligned pilot 的 shared/native Baseline：同一 `87c0bcd8b497...` 指纹下，**全部 175 个 microbatch 与 request 时间线逐项相等**。这支持桥接，但它是一个对齐 pilot 的验证，不应写成四格全由完全相同包装器得到，或所有输入上已证等价。

建议在表后加入：“原输入的 Baseline 来自共享包装器，新输入的 Baseline 来自原生包装器；两者都保持 Path0 FIFO、不使用压力决策。此前同输入 aligned pilot 的 175 个请求/批次实际时间线完全一致，作为包装器桥接；B 的前后两格则使用同一原生包装器。”

审计与精确数字在 `analysis/04_arrival_counterfactual_audit.json` 和 `04_four_cell_comparison.csv`。2736 请求只有 2735 请求的 `arrival_time_ms`、`load.arrival_ms`、`load.arrival_time` 改变，最大 2.735 µs，其他请求字段和整个 placement catalog 完全相同。每个输入内部两策略 fingerprint 配对正确。

## 3. 开头不能让人理解为只增加旧例的受害者数量（第 25 行）

“把旧坏输入中……受害者增加到每组四卡中的三卡”容易被读成从旧四卡例到 52% 例只改角色数量。实际旧画像为 `(1,169),(192,368),(192,896),(192,896)`，新例为 `(1,128)×3,(192,256)`；短卡 C/V 和背景长卡 C/V 都改变了。

建议改成：“基于旧例的 FIFO 机制，另构造三张低带宽短计算卡和一张长卡的四卡组，再复制为 32 NPU / 8 SSU……”。第 83–88 行详细参数表可保留。三短一长 **4→32 的局部复制**确实是受控规模对照；**旧输入→新三短一长**不是只改受害者数的因果对照。格点中固定长 NQL 后的数量扫描才支持后一种控制解释。

## 4. I/O 审计证据的粒度应明确（第 139 行）

“独立核对了……8,292,352条物理I/O”容易被理解为保存并逐条独立重放了物理块服务 trace。此次负例未做高代价物理 trace。实际证据包括全部请求的 I/O 数与 manifest 一致、全部物理提交/完成数一致、逐盘总完成字节一致、assignment 不修改 placement 的冻结源码，以及模拟器对每次提交的 disk ID/size 与 manifest 匹配断言。

建议写成：“对全部 2736 请求及 2651 次重绑逐项核对；逐请求 I/O 数、逐盘完成字节与 manifest 一致，物理 I/O 提交/完成总数均为 8,292,352。冻结模拟器在每次提交时检查实际 disk ID/size 与原 placement 一致。”这样仍充分支撑 placement 未变，但不会暗示不存在的独立 SSD 服务 trace。
