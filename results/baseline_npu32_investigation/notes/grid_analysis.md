# 4卡格点调查：受害者比例、总负载与 FIFO 堵塞

2026-09-07。18个冻结输入 × Baseline native / Once native 两种策略，36组全部完成，无失败。所有36次仿真的两个1秒窗口都通过每卡active全覆盖及仿真器全部invariants；结束时根目录Python源码哈希检查通过。进程运行总时长337.8秒，汇总仅读取保存结果。

## 实验条件

- 4 NPU / 1 SSU，SSD 40 GiB/s；每卡50 GiB/s接收链路。每请求8层、batch1、单层预取、启用跨请求L0预取。
- 短卡数 m∈{1,2,3}；其画像固定1K/NQL128，计算0.527908845 ms、7条176KiB IO/层，自身理想读需求2.225624309 GiB/s。其余4−m卡均为相同192K画像，NQL∈{256,384,512,768,1024,1536}。每卡反复处理自己的画像，角色不换卡。
- 全部请求在t=0到达，horizon=3100ms。生成器额外加两次最长请求理想计算时间的backlog，以防窗口内输入耗尽。共同窗口固定[1000,2000]ms和[2000,3000]ms。每组完整请求数及每卡理想计算下限保存在input_metrics.csv。
- seed固定42；compute_scale=1，不做target_rho归一化；每个输入两策略共享同一冻结manifest和提交seed。两策略是原生baseline/layer_once适配，压力TTL=0。结果不能直接当作5ms collector约束下Once的结论。
- `blocks=exact`：保留真实命令尺寸、不补齐；本格点全部NQL均为128整数倍，实际每条都恰好176KiB，没有部分尾块，padding_total_gib全部0。
- **1K短画像的计算时长由data的32K/48K外推**。192K/NQL384、768、1536在相邻NQL行之间插值，256/512/1024直接取data。此格点为机制研究，不是全部来自实测data行，也不是线上请求分布。

## 受害者比例的效果不是单调的

固定长画像192K/NQL768，仅改变短卡数：

| 短卡数 | ρ | Baseline短卡U% | Baseline长卡U% | Baseline全卡U% |
|---:|---:|---:|---:|---:|
| 1 | 0.8076 | 28.824 | 100.000 | 82.206 |
| 2 | 0.6126 | 53.642 | 100.000 | 76.821 |
| 3 | 0.4176 | 78.348 | 100.000 | 83.761 |

短卡数1→2时，总需求反而下降（ρ0.8076→0.6126），每张短卡也变好（28.824%→53.642%），但全卡U从82.206%降到76.821%，因为受到损失的卡数翻倍。再增加到3张短卡，背景长卡仅剩1张，短卡U提高至78.348%，全卡U又恢复83.761%。NQL1024与1536也出现中间m=2最低的非单调形状。

本格点所有容量可行输入的Baseline长卡U都为100%。因此在这些具体输入中可直接使用时间账目：`U_fleet = 1 − (m/4) × (1−U_short)`。它解释“受害者更多”和“每名受害者受到的堵塞减少”两股相反作用；并不是任何输入下都成立的性能预测器。不能只按卡数或ρ排序来推断U。

固定m时，长NQL增加，长计算C明显增长而每层读取量变化很小，长背景突发之间的间隔增大，ρ下降。这18点内Baseline U随NQL递增而上升；这只是本有限格点的观察，不是调度器对任意工作负载的单调性定理。

## 过载输入单独解释

5个过载输入为m1/NQL256、384、512和m2/NQL256、384。Baseline在这些点更低，Once也未达到100%。总容量不足本身不可通过更换Path消除。

不过，过载不代表各策略只能得到同一个计算利用率：短卡读需求低，保护短卡通常能以更少字节换取更多NPU计算时间。若固定角色长期保持，令每张短卡需求b_s、长卡需求b_l，b_s<b_l，本格点有m b_s<40，则忽略离散层与预取约束的字节守恒松弛为：

`U_relax = [m + min(4−m, (40−m b_s)/b_l)] / 4`。

这是固定画像长期计算利用率的松弛上限，不能作为任意有限1秒窗口硬上限；预取和边界可产生小偏差。5个过载输入的松弛值与Once主窗口如下：

| 输入 | 长期松弛U% | Once [1,2]s U% | Baseline [1,2]s U% |
|---|---:|---:|---:|
| m1_long256 | 56.940 | 56.953 | 34.586 |
| m1_long384 | 72.404 | 72.401 | 50.924 |
| m1_long512 | 87.888 | 87.897 | 67.305 |
| m2_long256 | 80.058 | 80.067 | 36.299 |
| m2_long384 | 94.611 | 94.608 | 52.840 |

不能将heterogeneous队列的全卡U简单套成1/ρ。两类请求每单位NPU计算需要的读字节不同；改变谁在计算就会改变平均U与实际盘吞吐之间的关系。

## 与32卡研究的关系和局限

- 该格点确认“短deadline/低自身读量的固定受害者 + 长请求大突发”能在不过载时制造很低的Baseline U，且Once在本格点可改善。要推广到32卡，必须明确复制拓扑、SSU共享方式和负载变化，不能直接外推4卡百分比。
- 同样“短请求”二字不能把1K外推画像换成原data的32K/128而不检查负载；后者每卡约36.33 GiB/s，与本格点约2.23 GiB/s很不同。
- 所有请求t=0入队，arrival→completion主要反映构造的入口积压；不把其低用户SLO当作真实生产SLO证据。完整请求数在跨输入变化，makespan、full_run_U和完整SLO仅在同一manifest的两个策略间作直接对比。
- 最终完整排空时可能出现某类卡先结束、另一类卡仍积压，拉低full_run_U；主窗口核对每卡active用于把该尾部效应与持续I/O stall分开。相关完整指标均保留run_window_metrics.csv及原始结果。

## 复算与文件

运行仿真：

```bash
python sweep_baseline_npu32_stress.py --plan results/baseline_npu32_investigation/grid/grid_plan.json --output results/baseline_npu32_investigation/grid --label grid --workers 3
```

已有完整结果会进行输入、策略、源码匹配检查后复用，不覆盖结果。只重算汇总：

```bash
python results/baseline_npu32_investigation/grid/aggregate_grid.py
```

- `grid/grid_plan.json`：全部18输入与36作业。
- `grid/inputs/*.json.gz`：完整冻结manifest；每种输入另有`.spec.json`。
- `grid/runs/<input>/<strategy>/`：完整压缩结果、命令、每进程日志。
- `grid/grid_status.json`：36/36完成、0失败，运行时间。
- `grid/grid_environment.json`：Python/NumPy/平台、开始时根目录源码SHA256。
- `grid/input_metrics.csv`：18输入容量、构造方式、精确块与输入指纹。
- `grid/run_window_metrics.csv`：72行策略窗口汇总，含短/长卡分解和完整指标。
- `grid/paired_metrics.csv`：36行同输入同窗口策略差异。
- `grid/per_npu_metrics.csv`：288行逐卡compute/stall/idle。
- `grid/grid_metrics.json`：上述摘要、输入与结果文件SHA256、每run保存的核心/策略/runner指纹。

CSV/JSON的utilization字段以0–1存储，本文显示乘100；gain_pp已经是百分点。汇总脚本直接从microbatch层时间线重新求交，并断言与原窗口U一致、每卡active满1000ms、manifest指纹一致、每个输入两策略完成请求数相同。
