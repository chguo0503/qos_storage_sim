# AB 首层预取候选：存在短窗退化，但没有找到长期低利用率

本目录保存两次 4 秒原生仿真初筛，以及一个候选的 OD、Once 完整排空对照。**这个候选不满足“长期平均利用率持续很低”的目标，也不是严格逐盘全程欠载。** 不把 warm 的 91.00% 当成稳态结论。

## 输入和硬件

32 NPU、3 SSU，每盘 40 GiB/s，每卡链路 50 GiB/s；8 层，batch=1，预取深度 1，启用跨请求首层预取。每卡固定 `(AB)^16`，共 32 个请求；全部 1024 个请求在 0 时刻到达，实际依次 admission。没有运行时 barrier、到达错峰或地址筛选。

|请求|总输入|miss|每层读取|每层计算 C|V/C：跨三盘总需求|
|---|---:|---:|---:|---:|---:|
|A，正式候选|10K|1024|72 × 176 KiB = 12.375 MiB|3.566243619 ms|3.388708745 GiB/s|
|A，另一个初筛|10K|512|76 × 176 KiB = 13.0625 MiB|1.856638860 ms|6.870667167 GiB/s|
|B|200K|2048|1584 × 176 KiB = 272.25 MiB|75.25 ms|3.533144726 GiB/s|

这里的 K=1024。画像的读取量按 hit token 数和 176 KiB/128 tokens 构造；**计算时间是构造值，不是直接选取的两条原始实测数据**：A 使用根 `data` 中同 miss 的 32K/48K 计算时间线性外推到 10K；B 将原 200K/2048 的 70.740537841 ms 调整到 75.25 ms。每个请求的元数据保留原值、权重和缩放。

采用普通 Ring Hash，物理请求 ID 为 `npu_id*1000000+queue_position`，各 ID 不同。请求的每层使用同一个合法 Ring Hash placement。OD 每盘总槽位 8192，每卡独占 256，不能借槽，SSD 完成释放；带宽仍是等 CIR、无限 PIR、允许原生空闲借用。Once 使用当前原有配置，未施加 OD 专属槽位限制。因此这是两种完整策略的对照，**不能把差值全部归因为路由本身，也不能由此判断限制槽位有害**。

## 结果

正式候选是 `ab_a10k1024_b200k_cb75p25_c16`。表中 U 从真实 compute 区间与窗口的交集重算，分母为 32 × 窗口长度；每个列出的中间窗口都有 32 张卡持续活跃、每卡实际计算过 A 和 B。

|统计窗口（秒）|OD NPU U|Once NPU U|OD 任一盘超载时间比例|Once 任一盘超载时间比例|
|---|---:|---:|---:|---:|
|[2,4)|91.002%|98.160%|0.03797%|0%|
|[4,6)|93.287%|98.568%|0%|5.78297%|
|[6,8)|96.393%|98.793%|5.53603%|1.82711%|
|[4,8)|94.840%|98.681%|2.76802%|3.80504%|
|[8,10)|98.446%|98.918%|0%|0%|

两种策略在各窗口 admission 请求上的 TTFT SLO×1.5 均为 100%；全体 1024 个请求也都达标。这里 `TTFT=completion-admission`，阈值为 `1.5 × 8 × C`，不是 arrival 到 completion 的外部排队口径。两种策略进入同一窗口的请求数量会不同；完整人口对照包含完全相同的 1024 个请求。

OD 完整输入的 U=91.888%，总时长 10.979146 秒；Once 为 95.353%，10.580138 秒。**全输入值包含起步与排空，不能替代长期稳定运行指标。** 首张卡完成全部请求分别在 10.455707 秒、10.123212 秒，因此 [8,10) 利用率恢复并非已经开始排空。

OD 的 warm 峰值为 `[36.34227, 40.07265, 39.22047] GiB/s`，第二块盘出现极短轻微超载，不能写成严格欠载；完整运行峰值 40.68543 GiB/s，任一盘超载时间比例 1.04561%。Once 的完整运行也有轻微局部超载。

另一候选 `a512` 的 4 秒初筛 warm U=92.524%，任一盘超载比例 20.245%，峰值 61.58767 GiB/s。它没有优于正式候选，且更偏离欠载要求，因此没有扩展；不为未完成的 pilot 报 SLO。

## 为什么先下降、后恢复

短 A 最后一层只提供 3.566 ms 的预取机会，但下一请求 B 的首层需要读 272.25 MiB。这里真正要及时完成的是 `V_B/C_A`；仅用当前画像的 `V_A/C_A` 判断欠载，没有涵盖跨请求首层读取的期限。

OD warm 丢失的 5758.75 卡毫秒中，5744.57 卡毫秒来自跨请求 L0 等待，内部 L1–L7 等待只有 14.18 卡毫秒。初期主要是 A→B 切换的同步读取，不是长计算本身占着 SSD 不放。

普通 Ring Hash 的分盘量不同，加上原生逐块服务和链路完成，逐渐使各卡错开。第 0 轮 B 首层计算开始时刻的跨卡范围只有 9.60 ms，第 3 轮为 117.81 ms，第 7 轮为 287.34 ms，第 15 轮为 523.44 ms。对应 OD 的跨请求等待从 [2,4) 的 5744.57 卡毫秒降到 [8,10) 的 994.60 卡毫秒。无需强制错峰，退化已自行减弱。

因此，数学上“每轮都保持同步”得到的约 90% 预测不能直接延伸到这个原生动态系统的长期行为。周期内有高有低当然可以使长期平均偏低；但必须证明低值能反复出现，本次实际队列没有维持这种反复同步。

## 口径与验证

需求按每个 admission/completion 事件之间的活跃请求，逐盘精确求和 `V_i,d/C_i`。跨请求下一请求首层不会另外作为第二个“当前请求”加入该需求曲线；其物理 I/O、host 等待、SSD 服务和 NPU stall 全部照常计入。因此“当前画像欠载”不等于任意 I/O deadline 窗口都满足可调度性。

- 两次完整运行的 simulator 源码 SHA 完全相同，输入 manifest SHA 完全相同；运行期间源码未变化。
- 所有原生守恒/时序不变量通过；每次完成 6,782,976 个命令。
- OD 的 96 个 `(NPU,SSU)` 配额全部实际触及 256，退出时 host/SSD/link pending 全为 0；限深确实生效。
- 完整指标保留在 `comparison.json`，便于比较的列在 `comparison.csv`；原始请求/层时序在 `runs/*/result.json.gz`。
- `summarize_comparison.py` 只读已有结果重算窗口、相位散布和守恒，不启动仿真。
- [math_notes.md](math_notes.md) 给出假设、近似公式和不能扩大解释的边界。

本轮到此停止，不扩展到 `(AB)^100`，因为 [8,10) 已经恢复到约 98.45%，不符合需要验证的长期低平均假设。
