# 仅改变 OD 队列深度的正式对照

同一份 50 周期冻结输入，用原始 API、两个独立进程完整重放。两次都没有规划 hook；32 NPU、3 SSU、每盘 40 GiB/s、8 层、seed 7、Ring Hash、OD 路径及带宽仲裁完全相同。

- 限深：每盘保留 8192 个槽位，32 卡各 256，不借用槽位；SSD 完成时释放。
- 不限深：`od_queue_depth_per_ssu=None`。
- 两者带宽都允许原生空闲借用；本对照没有改变 CIR/PIR。

输入 SHA256：`7bb8c6be24b7f9341d2de55829ec1890574d31fd94e3dbb5f1e240ee45cbd14f`。

| 统计区间 | 256 槽位 U | 不限深 U | 两者入场后 SLO×1.5 |
|---|---:|---:|---:|
| 2–4 秒 | 81.884008% | 81.884008% | 70.642202% |
| 20–40 秒 | 79.321675% | 79.321675% | 67.567568% |
| 40–60 秒 | 80.175183% | 80.175183% | 66.666667% |
| 20–60 秒 | 79.748429% | 79.748429% | 67.123288% |
| 完整输入 | 79.867651% | 79.867651% | 66.666667% |

这些固定区间内，32 卡都持续活跃，每张卡都实际计算过 A 和 B。首卡排空发生在 82.499927 秒；最后完成时刻为 82.500093 秒。SLO 使用窗口内入场请求的完整完成时间，判定 `(完成−入场) <= 1.5×该请求8层纯计算时间`，包含所有冻结的尾 B 计算。它不包含 all-arrival=0 后等待入场的队列时间。

## 深度限制确实触发，但没改变本输入的完成时序

96 个 `(NPU,SSU)` 的最大占用全部达到 256；满额阻塞事件共 8,654,959 次。激活、下发、SSD 完成、HBM 完成数全部是 38,630,400，最终 host、SSD 和传输中的未完成量全部为零。因此，不能把一致的利用率解释成“深度限制没有生效”。

逐项比较结果如下：

- 全部 38,400 层的完整记录相等。计算开始、结束、计算时长、I/O 开始、I/O 就绪、I/O stall 的最大差异都是 0。
- 4800 个请求的到达、入场、完成、处理时延、I/O stall、纯计算时间等关键字段差异都是 0。
- 原生模拟器源码、数据、manifest helper、统计脚本及输入的公共 SHA 均相同。
- 请求记录中只有 `avg_ssd_queue_wait_ms` 和 `avg_end_to_end_io_latency_ms` 不同。后者是沿用的入 SSD 后延迟字段名；它没有覆盖新增的主机侧等待。不能把这两个诊断字段变小解释为请求端到端加速。

本例中，足够深的队列让盘始终有下一条命令可服务，部分等待从 SSD 队列转移到了主机。队列深度不是这份输入低利用率的原因；这个结论只针对本输入，不推广到更浅队列或其他工作负载。

原始证据为 [depth_comparison.json](depth_comparison.json)、[限深正式结果](formal/abb_interp_unique_50_od_baseline/command.json) 与 [不限深正式结果](formal/abb_interp_unique_50_od_depth_none/command.json)。不限深独立入口是 [replay_depth_none.py](replay_depth_none.py)，比较脚本是 [compare_depth.py](compare_depth.py)。

这仍是根据 OD 时序离线构造、基于 `data` 内插的合成输入，存在周期性强突发过载；不是普通随机输入，也不是严格持续欠载。
