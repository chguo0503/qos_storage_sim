# 怎样让 OD 的长期平均 NPU 利用率低：公式与验证边界

本轮只修改输入。32 NPU、3 SSU，每盘 40 GiB/s；8 层、每卡 batch=1、固定卡内 FIFO、Ring Hash。OD 每盘 32 条独占 Path，CIR=1.25 GiB/s、PIR 无限，仍可借空闲带宽。沿用新队列限制：每盘 8192 槽，每卡每盘固定 256 槽，不能借槽。没有把 CIR 偷改为硬限速。

用户的长期要求是：**后期长区间平均仍低，允许周期内有高有低**。不能只选启动后的低谷，也不能用末尾卡做完后的空闲拉低平均。

## 一、ASU 旧公式不能直接搬到 OD

旧式推导中的关键条件是：

```text
总参考需求 < 存储容量 < 前面大读取的数据量 / 后面请求的计算时间
```

右边意味着：后面的请求还没获得服务，前面的大读取就已经用完它可隐藏 I/O 的时间。这依赖不同卡共用同一个 FIFO 队列。

OD 让每张卡有独立队列，后面的卡可以在大读取未读完时获得服务。因此原公式中的“必须等待其他卡的大读取全部完成”不再成立。它仍会有物理盘竞争、多盘到齐等待和预取不及时，不能由独占 Path 推出没有等待。

另一个重要事实是：**每卡每盘 1.25 GiB/s 是保证份额，不是硬上限。** 别的卡暂时不读时，当前卡可以借用带宽；队列槽不可借也不改变这个带宽规则。

## 二、持续欠载为什么更难构造

本项目沿用的需求定义是：

```text
B_i,s = 当前请求每层落在盘 s 的数据量 / 当前请求每层纯计算时间
D_s(t) = 时刻 t，32 张卡的 B_i,s 之和
逐盘持续欠载：每个实际事件区间、每块盘都满足 D_s(t) < 40 GiB/s
```

I/O 等待中的当前请求仍计入需求。下一请求首层的提前读取不额外计为第二个当前请求，但其真实 I/O 和等待照常计入。这是当前画像需求的欠载，不是所有短时间截止要求都一定可满足。

当少数短计算卡在等 I/O，多数长计算卡往往仍在计算。后者读完以后又让出带宽；不同卡逐渐错开，就可能消除最初的集中竞争。因此短窗低利用率不足以证明长期低。

本轮重新完整运行旧严格欠载输入，并加上每卡每盘 256 槽限制，得到了：

|窗口|OD 利用率|
|---|---:|
|2–4 秒|94.0580%|
|4–8 秒|98.2892%|
|8–12 秒|99.3782%|
|12–16 秒|99.4821%|

逐请求、逐层时刻与原来不限深度的结果完全一致。该输入不满足长期低要求；有限队列没有把它变成成功案例。证据在 `strict_replay/independent_audit.json`。

这也不是“所有持续欠载输入都不可能低”的数学证明。只能说，目前这条已充分验证的构造会恢复。

## 三、局部过载改用“反复集中进入高需求阶段”

选用 data 的两条原始画像，计算和读取均不缩放：

|角色|总输入 / miss|每层读取 V|每层计算 C|整卡参考需求 V/C|
|---|---|---:|---:|---:|
|A：短计算|128K / 256|175.65625 MiB|6.0240 ms|28.4759 GiB/s|
|B：长计算|128K / 4096|170.5 MiB|93.0173 ms|1.7900 GiB/s|

两者**总长度相同、读取量也接近**。这里的长短指计算时间，不是总输入长度，不能叫“大读取阻塞小读取”。

假设暂时 32 张卡都在读，三盘均衡且 OD 近似公平服务：

```text
整卡实际读取速率 r ≈ 3 × 40 / 32 = 3.75 GiB/s
A 的读取时间 R_A ≈ V_A / r = 45.744 ms
B 的读取时间 R_B ≈ V_B / r = 44.401 ms

A 每层可能暴露的等待 ≈ 45.744 − 6.024 = 39.720 ms
B 的 93.017 ms 计算足够隐藏约 44.401 ms 读取
```

这些是近似预测，不是固定限速或实测平均。真实 Ring Hash、不同活跃路径数和逐块仲裁会改变读取时间。

若每卡重复 `A → B → B`，并假设各卡一直保持相近进度，一个循环的近似为：

```text
纯计算 P = 8 × (C_A + 2 × C_B) = 1536.469 ms
A 内部层等待 = 7 × max(R_A − C_A, 0)
A 转 B 首层等待 = max(R_B − C_A, 0)
总额外等待 W ≈ 316.416 ms
U ≈ P / (P + W) = 82.923%
```

这条推导最容易漏掉的假设是“进度一直相近”。实测原始 ABB 在 2–4 秒为 79.85%，8–12 秒已恢复到 97.66%。因此不能把 82.92% 直接当成长期仿真结论。

本轮还测试了同一批请求分段重复，例如 `AAAA → BBBBBBBB`。各卡都运行 A 和 B，没有固定长卡/短卡，也没有加入人工空闲；但这些候选的后期利用率仍在回升，因此没有作为稳定的长期低例子。最终采用的构造见第六节之后。

## 四、“局部过载”不等于“轻微过载”

忽略盘间偏差，所有卡处在 A 时，每盘需求约为 `32 × 28.4759 / 3 = 303.74 GiB/s`；全 B 时约为 `19.09 GiB/s`。这是时间上时而过载、时而欠载，**峰值约为盘容量的 7.6 倍**，不是只超一点点。正式报告用 Ring Hash 的真实逐盘事件值，不用总量除以 3 代替。

对于数量比 A:B=1:2，不发生等待时完整人口的平均每盘数据速率约为 28.02 GiB/s。它和执行中对 `D_s(t)` 做时间平均是两种数：等待会延长 A 的驻留，后者可能超过 40。不能用 28.02 把这种输入称作持续欠载。

## 五、最终应以什么证据判定

- 预先固定统计 20–40、40–60 秒，另保留连续 2 秒窗口及完整重复周期的平均；不等结果出来再挑窗口。
- 所有统计窗口 32 卡都有活跃请求；宽窗口内各卡都实际计算过 A、B，报告短窗口是否只有某一类。
- 检查逐盘需求超 40 的时间占比、峰值及低谷；同时披露实际平均供给。
- 等完整排空后，才计算窗口接纳请求的 SLO，避免漏掉慢请求。
- 若 Once 同样低，不能把共同的短时容量不足完全归咎于 OD；需要单独说明策略之间有没有可恢复的差距。
- 60 秒有限验证也不是无限时间的证明；若后期仍在明显恢复，不能称为稳定的长期低平台。

普通混合输入的对照结果位于 `local_overload/runs/`。最终构造的正式结果在 `scheduled_input/formal/`。未完成的预览不能充当正式 SLO 或无限稳态结论。

## 六、怎样避免“错开后恢复”：提前选定各卡的 miss

自然重复的 A、B 请求会逐渐错开。小规模验证表明，可以预先选择各卡的最后一个 B 请求的 miss 数，让这种错开不逐轮累积。输入依然是每卡 `A → B → B`，三条都是真正的请求；正式运行中没有插入睡眠、没有等待其他卡的屏障，也不改变 OD 的仲裁。

通俗理解：希望大家下一轮都在同一时刻开始 A。已经跑得快的卡，其本轮最后一个 B 多一点真实计算；已经跑得慢的卡，最后一个 B 少一点真实计算。把这些请求参数提前写进输入文件，然后把文件冻结，重新启动原始仿真器运行。

```text
先选下一轮开始的目标时刻 E。
某卡本轮最后一个 B 的第一层，在时刻 s 开始计算。
如果这个 B 的后续读取都能被计算隐藏：
    B 完成时刻 = s + 8 × 每层计算时间
所以希望：
    每层计算时间 ≈ (E - s) / 8
```

这里没有把等待记成计算。B 的命中量固定为 127744 token，读取量固定为每层 171.53125 MiB；改变整数 miss，并同步改变总输入长度：

```text
总输入 token = 127744 + miss
miss 取 2048 到 4096 之间的整数。
每层计算时间由 data 中四个网格点做双线性插值。
```

“插值”就是用已知点之间的位置估计中间请求的计算时间，不是新的实测数据。它保持命中量、读取量、总长度、miss 和计算时间之间的一致性。整数 miss 不能任意精确地调时间，因此每卡的周期末端允许约 0.094 ms 误差，卡间跨度上界约 0.188 ms。

离线规划可以利用 OD 的一次试运行来选请求，但那次规划不算正式结果。**正式结果必须来自一个新进程：只读取已经冻结的输入，调用原始仿真器；逐请求、逐层结果还要与规划完全吻合。** Once 也使用这一份冻结输入，不为 Once 重新调整 miss。

这是一种针对已知 OD、种子和配置定制的压力输入，不能推广成普通随机负载的典型表现。正式长跑已核对：所需 miss 一直在 data 的插值范围内，B 的内部层没有额外等待，下一轮 A 首层提前读完，20–40 和 40–60 秒都没有任何卡排空。B 的首层仍可能等待，不能把“B 内部层不等”说成“整条 B 完全不等”。

## 七、正式 OD 长跑已经验证了什么

冻结输入为 `scheduled_input/inputs/abb_interp_unique_50.json.gz`。32 卡各 150 条请求，全部在时刻 0 就绪、每卡 FIFO 串行；每卡运行 50 轮 `A → B → B`。4800 条请求使用不同物理 ID，落盘均由原始 Ring Hash 计算，没有筛选地址来挑盘。

|每轮位置|总输入 token|miss token|每层读取 MiB|每层计算 ms|来源|
|---|---:|---:|---:|---:|---|
|A：短计算请求|131072|256|175.65625|6.024012|data 原始行|
|第一个 B：长计算请求|131072|3328|171.53125|75.603838|data 插值|
|最后一个 B：长计算请求|131001–131574|3257–3830|171.53125|73.956998–87.293717|data 插值，提前按 OD 轨迹选 miss|

所以“两类长短”主要指计算时间，总输入都约 128K，读取量也相近。所有 A 使用同一画像；尾 B 参数不同。它不是从 data 独立随机抽样的工作负载。

原始 API 在新进程中重放冻结输入：4800 条请求与 38400 层的指标同离线规划完全一致，六类层时刻最大误差为 0；没有安装规划用的额外事件钩子。观测到：

|统计窗口|OD：每卡每盘 256 槽|OD：不限队深|活跃且运行两类的卡数|
|---|---:|---:|---:|
|2–4 秒|81.8840%|81.8840%|32|
|20–40 秒|79.3217%|79.3217%|32|
|40–60 秒|80.1752%|80.1752%|32|
|20–60 秒|79.7484%|79.7484%|32|
|60–78 秒|79.6924%|79.6924%|32|

首张卡约 82.499927 秒才完成全部请求，因此这些窗口没有混入末尾排空。每轮卡间结束时刻的最大跨度只有 0.185729 ms；这里反复出现的低利用率没有被自然错开修复。

读取和计算总量提供一个简单核对：

```text
每卡全部纯计算的均值 = 65.890887 秒
整个输入的设计周期总时长 = 50 × 1.65 = 82.5 秒
利用率核对值 = 65.890887 / 82.5 = 79.867741%
正式全程利用率 = 79.867651%

平均每轮：约 1317.818 ms 计算 + 332.182 ms 等待
```

20–60 秒只覆盖部分边界周期，因此为 79.7484%，不要求与全部 50 周期恰好相等。利用率是对实际计算区间求交集后统计的，并不是用上述近似公式替代仿真记录。

队深限制确实触发了：96 个卡盘队列的峰值都到 256，总计约 865 万次满额阻塞事件。但不限深度对照的所有层执行时刻、请求关键时刻完全相同。这说明本例中队深主要改变了等待记在主机还是 SSD 一侧，没有改变 NPU 计算开始时间。不能把各盘可重叠的主机阻塞累计值直接当成 NPU 等待。

**负载边界必须同时看：** 20–60 秒各盘约 22% 的时间超过 40 GiB/s，峰值接近 320 GiB/s；低谷约 20–22 GiB/s。当前请求 V/C 的时间平均约 76–84 GiB/s/盘，也超过 40。因而这只是间歇性强过载案例，既不是持续欠载，也不满足“连时间平均 V/C 需求也欠载”的更强要求。

另一方面，完整输入最忙盘的总读取量除以容量只有 56.2111 秒；最长卡纯计算为 66.0619 秒。它们是完成时间的必要下界，不保证可达，但说明总字节量与总计算量本身没有强迫执行必须耗时 82.5 秒。问题在于工作发生的先后与重叠方式。Once 的正式同输入对照见第九节。

## 八、把以前的 b/B 公式对上一个真实的层周期

正式 OD 记录中，NPU 0 的请求 72 有这样一个内部层周期（层索引 2 的计算开始，到层索引 3 的计算开始）：

```text
真正计算 C = 6.024012 ms
随后等 I/O I = 42.189947 ms
整个周期 T = C + I = 48.213959 ms
该周期要读下一层的数据 V = 175.65625 MiB

需求 B = V / C = 28.475926 GiB/s
按完整周期平均的供给 b = V / T = 3.557876 GiB/s

b / B = C / T = 12.494331%
```

只要看这一小段，卡约八分之一时间在计算，约八分之七时间在等。这不是某个瞬时的利用率，而是一个完整层周期的平均值。两层属于同一 A 请求，所以这里可以使用相同的 V 和 C；跨请求边界不能随意照搬。

整机长期约 80% 与这一层约 12.5% 并不矛盾：每轮后面还有两个计算时间很长的 B。20–60 秒，A 类请求在上卡期间的利用率约 14.23%，B 类约 96.82%；整机平均按各类占用的卡时间加权，而不是把这两个百分数简单取平均。

|窗口|OD NPU 平均利用率|Once NPU 平均利用率|OD SLO ×1.5|Once SLO ×1.5|
|---|---:|---:|---:|---:|
|2–4 秒|81.8840%|93.5575%|70.6422%|81.0811%|
|20–40 秒|79.3217%|98.9450%|67.5676%|99.8612%|
|40–60 秒|80.1752%|98.9028%|66.6667%|99.3060%|
|20–60 秒|79.7484%|98.9239%|67.1233%|99.5836%|

这些区间两策略都满足 32 卡持续活跃且每卡实际计算过两类请求。Once 第一张卡到 66.615813 秒才完成全部输入，不存在通过排空尾部拉低对照的情况。两策略的输入文件 SHA 相同；同一个周期、同一张卡的计算量不因策略而变化。

SLO 使用上卡时间到 prefill 完成的耗时，不含卡内排队；它不是完整端到端 TTFT。上表按窗口上卡队列取样并追踪到完成。为了核对推进快慢带来的不同窗口人口，另外统计同一批全部 4800 条请求：OD 达标 3200 条（66.6667%），Once 达标 4662 条（97.1250%）。

实际时序图显示，Once 下各卡的长短计算阶段错开，短计算请求不再每轮整齐聚集。20–60 秒，A 的类内利用率从 14.2327% 提高到 93.5525%，B 从 96.8192% 提高到 99.1399%。这解释了整机平均值的差异；不是说每一条 A、每一时刻都分到了更多带宽。

同一输入在两策略下的当前请求集合不同，因此 V/C 需求曲线也不同。OD 的 20–60 秒逐盘时间平均需求为 76.36/83.93/81.70 GiB/s，Once 为 31.59/34.70/33.84；后者仍有局部超过 40 的时段。不能把 OD 的需求曲线视为两种策略共同面对的固定外部到达速率。

最后要区分机制与泛化：本例针对 OD 的轨迹选 miss，不能据此排列策略对普通随机负载的普遍优劣。OD 使用 32 条独占 Path 与均分 CIR，Once 使用原来的 256 条 Path、类别 CIR 预算和候选池；当前对照检验的是完整 L3 策略配置，不是纯选路的单变量实验。取消 OD 队深限制没有改变时序，排除了本例中的队深原因；将提交种子从 7 改为 19 也没有改变时序，但这个变化没有形成实际扰动，不能作为对真实计时噪声的鲁棒性证据。
