状态：两种顺序均完整排空。

32 NPU、3 SSU × 40 GiB/s；OD 每盘 8192 深度，每卡每盘固定 256；每请求 8 层。

这一个随机顺序中，三个窗口的利用率比原 ABB 分别高 19.0083、7.6029、1.5851 个百分点。相同请求集合并不必然产生相同退化，L2 顺序有明显影响；原 ABB 本身也从 79.85% 恢复到 97.66%，仍不能当作长期低利用率案例。画像的读取量和计算时间直接来自 data，未缩放。

同时不能把差异全部归因于“同步被打散”：随机后窗口内实际计算过两类请求的卡数为 19/30/29，原 ABB 均为 32；顺序还改变了窗口内画像构成和驻留时间。每卡全输入仍严格保持 11A+22B，没有删除 A 请求。这里不宣称随机对照满足“每个统计窗口每卡都运行两类”的约束。

需求逐事件统计当前已接纳请求 V_i,s/C_i，等待期间仍计入；下一请求 L0 不额外叠加第二份画像需求。逐盘峰值和超限占比均来自实际各自执行轨迹。若超限，此对照不属于严格欠载反例。

SLO 使用窗口内接纳请求、跟踪至最终完成，以接纳至 prefill 完成为耗时，自身八层纯计算时间 ×1.5 为门槛；不含接纳前排队，不是真实首 token 时间。NPU U 对窗口内所有计算片段积分。三个固定窗口均不因结果变动。

随机对照只有一个输入种子，不可推断所有随机输入；本次保持有限请求总量不变，也不是 60 秒长期平台验证。完整原始输出、逐卡角色计算和逐盘事件区间保存在 runs/；comparison.json/csv 为复算结果；input_checks.json 和 request_identity_mapping.csv 证明只改变 L2 顺序。

独立原始 JSON 核对通过，见 [independent_checks.json](independent_checks.json)：物理身份/画像/逐块 placement、58 份冻结运行时代码及 data、结果 SHA、三窗计算积分/SLO计数/逐盘事件需求、队列深度和排空守恒均匹配。完整运行处理 8,464,896 块，随机顺序 makespan 为 17.3658 秒，原 ABB 为 18.8400 秒；不把全程尾部计入长期平台论证。
