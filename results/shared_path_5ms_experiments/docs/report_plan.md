# 新报告的审计口径与图表方案

当前尚无性能结果；本文不填入预测数字。

## 同输入、公平性

- 五策略为Baseline、原Once、New once、Strategy 1、Strategy 2；32 NPU，SSU为5/6/7。
- 每个拓扑使用相同完整704请求集，核验input fingerprint、原data SHA、请求ID、到达、计算量、IO总量和原SSD放置。
- Baseline/Once/New once固定原NPU；Strategy 1在真实到达时选卡，Strategy 2使用相同选卡函数再加同Path理想重排。状态不同可能产生不同后续选卡，不能将所有最终差异归为某一条IO被移动。
- Strategy 2不得跨Path、不得抢占当前IO、不得读取未到达请求；它需要盘内配合，是理想参照，不等同仅客户端可部署策略。
- collector在0 ms初始化，之后每5 ms采集一次。所有策略包括Baseline同样采集；路径决策只能读副本。实际SSU fresh读必须与collector计数一致。
- 运行期CIR不写入。初始化配置另计；这满足不高于每100 ms一次写入，而不是验证了100 ms动态CIR策略。

## 指标

固定测量[1000,2000] ms，逐层求交计算每卡compute、IO stall、idle，验证每卡是否整秒有已接纳工作。不能移动窗口挑最好结果。

主SLO为admission→completion≤1.5×8C。arrival→completion另报，包含接纳前排队。两种SLO均使用完整同704请求集，不使用各策略窗口内不同的接纳样本作主分母。

还需同时报告完整makespan、平均用户延迟、每种操作的次数及墙钟开销。更好的接纳后SLO不能掩盖更长的接纳前等待。

## 信息与边界

客户端全局账本不是SSD实时队列。需要区分已规划、已提交、新快照已包含、已完成但回执未到等状态，避免重复计账。

5 ms副本年龄、共享账本协调与竞争性修改、计算时间估计、SSU调度接口均影响部署。Python墙钟不是纯CPU时间，更不是设备实际控制延迟；数据面不模拟这些控制耗时时必须显式说明。

输入平均需求用计算时间加权，只约束对应长期完整配比；不能作为某一有限秒利用率的硬上界。data参数表也不是线上请求概率分布。
