# 数学候选筛选：这些是代理预测，不是原仿真结果

本目录只负责选择静态输入。原仿真的结果以相邻 `runs/` 目录为准。没有修改原调度器、Ring Hash、到达时间或运行时加入 barrier。

三个大型搜索结果以完整、无损的 `.json.gz` 发布；原始字节 SHA 与验证、恢复方法见 [PUBLICATION.md](PUBLICATION.md)。本地原始 JSON 保留，历史搜索脚本未改动。

## 代理保留了哪些机制

- 32 张 NPU，8 层，每卡同时执行一个请求，所有请求在 0 ms 到达。
- 每盘 40 GiB/s，每卡独占一个路径，CIR 为 1.25 GiB/s，空闲份额按原来的组间/组内两级规则借用。
- 第 k 层开始计算时提交下一层读取；最后一层开始计算时提交下一个请求的首层读取。下一个请求直到上一个请求计算完成才 admission。
- 下一层须等计算结束和三盘读取、NPU 接收全部完成。NPU 接收上限 50 GiB/s。
- 需求按**当前 admission 的请求**逐盘计算 V/C。跨请求首层实际读取仍计入服务量；需求不把两个请求重复相加。
- 精确按事件区间检查整个 [0,8) 秒是否有任一盘需求超过 40；同时计算 [2,4)、[2,6)、[4,8) 秒的 U、实际计算过两类请求的卡数及每类计算时长。

代理没有模拟每个 176 KiB 命令的非抢占服务，而使用连续服务。`fluid_proxy.cpp` 还假设三盘均匀分布；`ring_fluid_proxy.cpp` 则读取真实 manifest 的每请求逐盘读取量。两者都不能代替正式仿真。

## 先发现的反例为什么不够

均匀分盘时，静态队列可以形成稳定相位。例如 4 组各 8 张卡，先分别运行若干 B，再重复 `35 个 A → 3 个 B`。A 的计算短、带宽需求高；B 的单层读取大、计算长。B 的大块预取反复同时出现，A 在此前后的等待损失不能靠后面的空闲带宽追回。

但把同一输入换成普通 Ring Hash 地址后，每个请求的逐盘字节数不同。三盘 barrier 使各卡启动时间出现差异，这些差异逐渐打散 B 的读取突发。本次直接读取正式 manifest 的三盘代理中，原来约 93% 的均匀分盘候选恢复到约 98%–99%，并且 A 角色有时重叠造成短时超限。因此，**均匀分盘的低 U 不能当成普通 Ring Hash 的结论**。

原始 `data` 的 A32K/1024、B128K/4096 或 B200K/4096 也进行了静态前缀与分块扫描。筛选到的严格欠载候选普遍约 97%–99%，没有据此证明原始数据一定做不到更低。

## 可供正式验证的地址敏感候选

`fixed_bottleneck_safe_38.json` 提供完整 32 卡队列，6 次循环，足够覆盖 8 秒；另存的代理指标使用 64 次循环检查到 64 秒。

| 项目 | A：短计算请求 | B：长计算请求 |
|---|---:|---:|
| 每层总读取命令数 | 80 | 1210 |
| 每命令大小 | 176 KiB | 176 KiB |
| 每层计算 | 1.8959612617422492 ms | 93.62343678022687 ms |
| 要求 SSU 1 上的命令数 | 28 | 419 |
| 另两盘分别允许的最大命令数 | 28 | 419 |

计算时间是显式合成参数，不是 `data` 的实测值。80 个读取块对应 10,240 个命中 token；如采用 256 个新增 token，总输入为 10.25 Ki token。

把 NPU 0–7、8–15、16–23、24–31 分为 4 组。它们分别先运行 3、1、2、4 个 B，然后所有卡执行 `A×35 → B×3`，重复 6 次。这里的前缀本身是正常请求，没有人为等待。

这个候选要求使用合法但特意挑选的不同物理 request ID，使**瓶颈盘的块数固定**。Ring Hash 算法不变。它属于对抗性数据地址选择，不能称为普通随机请求。

在固定瓶颈盘块数的连续服务代理中：

| 窗口 | U | 实际计算过 A/B 的卡数 |
|---|---:|---:|
| [2,4) 秒 | 92.824% | 32 |
| [2,6) 秒 | 92.798% | 32 |
| [4,8) 秒 | 92.753% | 32 |
| [8,16) 秒 | 92.756% | 32 |
| [16,32) 秒 | 92.765% | 32 |
| [32,64) 秒 | 92.765% | 32 |

其三盘需求上界分别约 34.142、37.859、36.720 GiB/s；整个 64 秒没有超限。warm 中，每卡至少实际计算 A 139.61 ms、B 1252.11 ms。这些仍是代理预测。

另一个 `fixed_bottleneck_safe_39p2.json` 把 U 降到约 92.25%，但最忙盘峰值增至 39.162 GiB/s，余量更小。

## 为什么固定瓶颈盘块数有作用

如果 SSU 1 的读取量始终不小于另两盘，且同类请求的 SSU 1 读取量相同，则这个盘反复决定层读取什么时候结束。即使另两盘的块数不同，也有机会维持相同的读取完成节奏。

在 4 组轮转接近稳定时，一组执行 A，其余三组执行 B。若一整段 `m 个 A` 的墙钟耗时接近一个 B 请求的 `8×C_B`，一张卡的完整周期近似为：

```text
周期长度 ≈ 32 × C_B
周期内真正计算时间 = 8 × m × C_A + 24 × C_B
U ≈ (8 × m × C_A + 24 × C_B) / (32 × C_B)
  = 0.75 + 0.25 × m × C_A / C_B
```

这是用于解释相位接近稳定时的近似式；最终数值始终由计算区间积分得出。它没有把瞬时 b/B 直接当成瞬时 NPU 利用率。

此构造对瓶颈盘的扰动敏感：在更激进候选中，允许每请求随机挪动 1 个块，就能使后窗 U 回升到约 98%，并出现短时超限。反之，仅在另两盘之间随机分块，保持瓶颈盘块数固定且不小于另两盘，在三个随机种子的代理测试中未改变 U。正式离散调度仍需验证。

## 文件入口

- `ring_initial.json`：直接读取普通 Ring Hash 正式 manifest 的反证。
- `fixed_bottleneck_safe_38.json`、`fixed_bottleneck_safe_39p2.json`：建议正式验证的完整静态队列。
- `fixed_counts_candidate_00.json`：更激进的低 U 候选及 ±1/±2 块扰动测试。
- `fixed_bottleneck_jitter.json`：只扰动非瓶颈盘的测试。
- `search.py`、`expand_search.py`、`resonance_search.py`、`safe_search.py`：均匀分盘搜索。
- `data_search.py`：原始 data 画像的均匀分盘扫描。
- `ring_search.py`：真实逐请求 Ring Hash 分盘量的连续服务扫描。
- `fixed_counts_search.py`：固定每类分盘量与小扰动扫描。

编译代理后运行对应 Python 脚本即可重做筛选：

```bash
g++ -O3 -std=c++17 fluid_proxy.cpp -o fluid_proxy
g++ -O3 -std=c++17 ring_fluid_proxy.cpp -o ring_fluid_proxy
python ring_search.py
python fixed_counts_search.py
```
