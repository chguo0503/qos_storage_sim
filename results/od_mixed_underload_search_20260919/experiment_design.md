# 每卡混合长短请求，为什么 OD 仍可能等 I/O？

本实验检验一个具体问题：32 张 NPU 都运行长短请求，3 张盘各有 40 GiB/s，而且逐盘的当前请求参考需求一直低于 40，OD 的计算利用率是否仍会下降？这里不预设 OD 一定很差，最终以完整仿真的结果为准。

## 1. 先纠正“均分”的一个容易误解的地方

OD 在每张盘上给每张 NPU 一条独占 Path，保证份额是：

```text
q = 40 / 32 = 1.25 GiB/s
```

**1.25 是保证份额，不是硬上限。**别的路径没数据时，当前路径可以借用空闲带宽。所以不能只用“某张卡需要 2.4，大于 1.25”就证明这张卡必然长期堵塞。

OD 也没有 ASU 那种不同 NPU 共用一条 FIFO、短读取排在别人的大读取后面的队列结构。它的问题可能是：大家同时有读取时，分到的服务机会与各自下一层的紧迫程度不匹配。物理盘仍只有一条串行服务通道。

实现见 [策略定义](../../docs/baseline_strategies.md)。

## 2. “欠载”在这里具体怎么算

对当前占用第 i 张卡的请求，取它每层实际落在第 s 张盘的数据量，再除以它的纯计算时间：

```text
V_i,s：这一层实际落在盘 s 的读取量，单位 GiB
C_i：这一层纯计算时间，单位秒，不包含 I/O 等待
B_i,s = V_i,s / C_i
D_s(t) = 时刻 t 所有当前已接纳请求的 B_i,s 之和

逐盘严格欠载：每个事件区间、每张盘都满足 D_s(t) < 40
```

请求在等 I/O 时仍计入需求，不会因为它被堵住就把需求删掉。分盘量来自原生 Ring hash 的实际块分布，不用总量除以 3 代替。所有请求接纳和完成事件都检查，不靠 10 ms 采样判断是否越限。

沿用此前约定：跨请求的首层预取不额外作为第二个当前请求叠加；它的真实读取仍正常占用盘，真实等待也正常计入利用率。因此，这个条件是**当前画像的参考需求欠载**，不等于“所有已提交 I/O 在任何短时间内都能按截止时间完成”。全文中的“欠载”均指这个口径。

## 3. 一个可复算的例子

候选 `native_phase_lock_a101_b0995` 中，A 是短计算请求，B 是长计算请求。注意：角色 B 和公式中表示带宽的 B_i 是两件事。

| 项目 | A：短计算请求 | B：长计算请求 |
|---|---:|---:|
| 总输入 | 10.25K token | 155.25K token |
| hit / miss | 10K / 256 | 151.25K / 4096 |
| 每层总读取 | 13.75 MiB | 207.96875 MiB |
| 每层计算 | 1.914921 ms | 93.155320 ms |
| 瓶颈盘 SSU1 的读取 | 28 × 176 KiB | 419 × 176 KiB |
| SSU1 的参考需求 | 2.454257 GiB/s | 0.754952 GiB/s |

这些是**构造的画像**：token 与块量一致，但计算时间不是直接从 data 原行测得。原始 data 的未修改画像另有完整测试，不能把两者混为一谈。

假设某时刻有 8 张卡运行 A，24 张运行 B，那么瓶颈盘的参考需求为：

```text
8 × 2.454257 + 24 × 0.754952 ≈ 37.7529 GiB/s < 40
```

但是，如果 32 张卡同时开始读下一层，且短时间内都有未完成的读取，OD 给它们的长期保证份额相同。用连续均分作粗略估算：

```text
A 的读取时间 ≈ 28 × 176 KiB / 1.25 GiB/s = 3.760 ms
A 能把读取藏起来的计算时间只有 1.915 ms

B 的读取时间 ≈ 419 × 176 KiB / 1.25 GiB/s = 56.262 ms
B 能提供的计算时间有 93.155 ms
```

于是 A 可能等，B 仍来得及。B 读完后会让出份额，A 又可以借用更高带宽；可是之前已经损失的计算时间，不能通过之后“超过 100% 计算”补回来。

上面的读取时间只是连续均分估计，不是实际逐层测量，也不是硬下界。实际调度按整块仲裁，路径清空、重新入队、空闲借用都会改变服务。

## 4. 如何让每张卡都运行两类请求

把卡分成四组，每组 8 张。每张卡的队列都提前固定；运行时不延迟接纳、不改计算时间、不搬请求，也不加空闲。

| NPU 编号 | 队首先放 | 随后重复 6 次 |
|---|---|---|
| 0–7 | B、B、B | A 连续 35 个，再 B 连续 3 个 |
| 8–15 | B | A 连续 35 个，再 B 连续 3 个 |
| 16–23 | B、B | A 连续 35 个，再 B 连续 3 个 |
| 24–31 | B、B、B、B | A 连续 35 个，再 B 连续 3 个 |

这些初始 B 数量让四组轮流进入 A 段，希望保持“约 8 张 A 卡、24 张 B 卡”，并让 B 的大读取集中发生。**这是设计目标，不是强制规则。**如果等待改变了各组完成时间，实际 A 卡数会变化；最终仍要逐事件审计，越限就判该候选不满足约束。

本候选保留原生 Ring hash，但事先筛选不同请求 ID，使 SSU1 每层恰好收到 A 的 28 块、B 的 419 块，另外两盘不超过这个数。这是为了保持竞争相位的对抗性选址，不能称为普通随机地址。各请求 ID 都不同，没有把同一请求对象重复发送给 32 张卡。

## 5. 为什么不能把连续模型的预测当结果

连续模型把 1.25 GiB/s 看成持续流动的水。实际盘每次处理一个 176 KiB 块，短路径读空后再进入竞争，虚拟标签会重新设置。

在已审计的例子里，连续模型估计 A 读完需要约 3.76 ms，实际约 3.66 ms。差一点点，但 A 段有很多层，提前量会累积，让后续 B 的读取不再整齐同步。竞争变分散后，A 等待减少，利用率就回升。

因此，模型可帮助挑选输入，不能用来替代仿真；“warm 很低”也不能自动推出“长期很低”。详细证据见 [连续模型与原仿真的差异](ideal_search/proxy_native_gap.md)。

## 6. 实验怎么避免把统计口径当成效果

- 原仿真短试验先运行到 4 秒，只筛选 `[2,4)` 的利用率与欠载条件；它不提供完整请求 SLO。
- 晋级候选完整排空，OD 和 Once 使用逐字节相同的冻结输入。主窗口为 `[2,4)`，另看 `[2,6)`、`[4,8)`，新增候选再看 `[8,12)`、`[12,16)`。
- 每个窗口检查 32 张卡是否一直有活跃请求，以及是否都实际计算过 A 和 B。仅仅队列里有两类请求不算通过。
- 利用率用真实计算区间积分，分母是 `32 × 窗口长度`。同时分开统计请求内部层间等待、跨请求首层等待、启动等待和任务排空后的空闲。
- 末尾一些卡已经做完，会拉低全程平均；它不能作为“持续争用让利用率变差”的证据。
- SLO×1.5 沿用本项目的代理：`接纳后到 prefill 完成的时间 <= 1.5 × 8 × 本请求每层纯计算时间`。对窗口内接纳的请求跟到完成；不把未完成请求丢掉。它没有包含最初到达后的队列等待，也没有模拟真正的首 token 事件。
- Once 对照采用原始 Once 的类别 CIR 配置与逐层选路；因此差异来自这套完整策略，不是只改变选路的单变量实验。

## 7. 与 b / B 的关系

在**同一请求内部**，选择一个完整周期：本层开始计算，到下一层开始计算。两层画像相同，期间只预取下一层。

```text
周期长度 = 本层计算 C + 计算结束后等待 I
完整周期平均供给 b = 下一层读取量 V / (C + I)
参考需求 B = V / C

b / B = C / (C + I)
```

这时比值与该卡在这个完整周期内的计算占比一致。它不是瞬时利用率，也不等于单独 I/O 服务期间的读取速度。

整机窗口 U 要把各卡真实计算时间加起来再除以 `32 × T`，不能直接对长短不同的周期比值取算术平均。跨请求周期的前后 V、C 会变，窗口边缘还会截断周期，所以正式统计始终回到原始计算区间。
