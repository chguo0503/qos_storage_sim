          1 先说结论：能够扩展，但不能只把 40 改成 240 或 280

这里的 32 张 NPU 各自处理不同请求，不是 32 张卡共同计算一个请求。每张卡一时只计算一个请求，
每个请求 8 层，允许预取下一层，也开启已有下一请求的跨请求预取。KV 数据走 SSD→HBM，不经过
DRAM。

从一个 SSU 扩展到多个 SSU，至少增加了两个必须计算的因素：

    1. 每盘分别排队。总带宽没有用满，不代表每盘都有余量。某层只要有一个 SSU 的部分数据迟到，这
     层就不能开始计算。
    2. 多盘共用每张卡的一个接收口。 6 个盘各有 40 GiB/s，不代表一张卡可以接收 240 GiB/s；本项
     目每卡接收总上限仍然是 50 GiB/s。

因此，原来的 “前方工作时间＋自己的读取时间” 和多层反馈思想仍适用，但必须变成每个 SSU 的 FIFO，
加每张 NPU 的接收 FIFO。只有各盘总排队数，通常不能精确预测未来各层。

配套实现分工如下：

    • multi_ssu_stall_predictor.py：Baseline 的严格单层下界、独立多层预测、新请求影响比较。
    • multi_ssu_qos_controller.py：策略 A，固定 NPU 分配，动态选定专用 Path 的 CIR。
    • multi_ssu_npu_assignment.py：策略 B，在 A 之上，于实际到达时选择 NPU。

这三个结论不能混为一谈：公式下界成立，不等于在线预测一定精确；在线预测精确，也不等于某个调度策
略一定提升利用率。性能数字和验证误差应以配套实验报告及原始 JSON 为准。

2.1 一条 I/O 到底多大

本说明固定：



                          𝑏 = 176 KiB = 180224 byte.

这是 GLM 格式下 128 token 的一层 KV 数据，一条 I/O 就是一个完整 KV block。不是 128 个这
种 KV block，也不是 4 KiB。

用 GiB/s 输入带宽时，设 𝐵𝑠 是 SSU 𝑠 的带宽，𝐿𝑖 是 NPU 𝑖 的接收带宽。一条 I/O 的两个服务时间
分别为：


                          𝑏                        𝑏
                𝜏𝑠 =           1000 ms,   ℓ𝑖 =          1000 ms.
                        𝐵𝑠 230                   𝐿𝑖 230

本项目使用所有盘 𝐵𝑠 = 40、所有卡 𝐿𝑖 = 50，因此：



                          𝜏 = 0.0041961669921875 ms,
                           ℓ = 0.00335693359375 ms.

Python 多盘预测器目前接受统一的 disk_gib_s 和 link_gib_s；下面有下标的数学记法也便于说明
异构设备，但不能据此误认为所有现有接口都已支持逐盘不同带宽。

项目中的 request_id 只是全局唯一的请求编号。例如 1001 表示 “编号 1001 的那个请求”，不是长度、

的 L0 混成同一层。

跨请求预取还有一个限制：只有当前请求最后一层开始计算时已经到达的下一请求，才会被预取。之后才到
达的请求不能假装在过去已经读了数据。



                    3 通俗理解：多个仓库，一个卸货口

把每个 SSU 想成一个独立仓库；每个 NPU 的 HBM 接收链路是这个客户自己的卸货口。

一个客户要开始做下一道菜，必须收齐来自各仓库的全部材料。这里有两种完全不同的等待：

    • 仓库 A 的货车队很长。仓库 B、C 的材料已送到，也不能替代缺少的 A 的材料。
    • 各仓库同时送来很多货，但客户只有一个卸货口。即使所有仓库都没有别人排队，卸货本身也需要时
     间。

自然错开只是在改变 “什么时候加入哪些队列”。它不能增加仓库吞吐，也不能把一个卸货口变成六个。

5.1 每个盘的 FIFO 递推

先假定每盘 I/O 的服务顺序已经确定。设 𝑎𝑠,𝑗 是排在该盘第 𝑗 个服务位置的 I/O 的提交时刻，𝐹𝑠,𝑗 是它
离开 SSD 的时刻。完整等大小 I/O 的递推为：



                              𝐹𝑠,𝑗 = max(𝑎𝑠,𝑗 , 𝐹𝑠,𝑗−1 ) + 𝜏𝑠 .

含义是：“等这条命令到达，也等前一条服务完，再用一个服务时间。” 每个盘都要独立维护这个递推，不
能合成一个总盘队列。

正在服务的第一条若只剩 𝑟𝑠 byte，第一次加的是 (𝑟𝑠 /𝑏)𝜏𝑠 ，而不是完整 𝜏𝑠 。

这里给出一个充分条件，不是所有低利用率输入的完整分类。

在时刻 𝑎，某个长请求已经把一批 I/O 全部提交。盘 𝑠 至少还有 𝐻𝑠 ms 的已承诺 FIFO 工作。受影响的
短计算卡当前正在计算，每层计算 𝐶 ms，每层还需要从这个盘读 𝐾𝑠 条 I/O。

假设这张卡接下来两次切换都不 stall。当前计算最多再过 𝐶 ms 就结束，因此下一次计算最迟在 𝑎 + 𝐶
开始；那时发起再下一层读取，它的 deadline 最迟是 𝑎 + 2𝐶 。

但是这次新发的读取不能越过已排好的 FIFO 工作，数据到齐不早于：



                              𝑎 + 𝐻𝑠 + 𝐾𝑠 𝜏𝑠 + ℓ𝑖 .

因此，只要受影响卡确实使用的某个盘满足：



                        𝐻𝑠 + 𝐾𝑠 𝜏𝑠 + ℓ𝑖 > 2𝐶,

就能否定 “接下来两次都没有 stall”。无需提前知道这张卡正处于计算周期的哪个位置。

如果长批在 𝐽 ms 内向各盘共提交了 𝐾𝑏𝑢𝑟𝑠𝑡,𝑠 条 I/O，因为一个盘在此期间最多服务 𝐽 ms 的工作量，
可以使用：



                    𝐻𝑠𝐿𝐵 = max(0, 𝐾𝑏𝑢𝑟𝑠𝑡,𝑠 𝜏𝑠 − 𝐽 ).

配套函数是 fifo_burst_certificate。它返回的超出量是随后两次计算切换的累计 stall 下界，不是
保证某一层单独 stall 这么久。第一次迟到会移动后面的 deadline，不能重复扣这笔时间。

使用证明需要同时满足：

    • 每盘使用严格 FIFO Path0，没有后来请求越过这批工作。
    • 受影响 NPU 当时正在计算，且至少还有两次后续计算切换可考察。
    • 这两次切换涉及的读量和中间计算时间符合假定的固定 profile。
    • 只有一层前瞻预取，不能提前多层把后续数据都缓存好。

8 层请求接近结束时可能不满足这些条件。跨请求后 profile 改变时，也不能机械沿用同一个 𝐶 和 𝐾𝑠 。
一次有限长突发的证明，不是 “永远周期性 stall” 的证明。

自然错开能成功的情况并不矛盾：当这个条件不成立、盘和链路有足够余量，且各卡存在可行的相位间隔
时，一次等待可能把后续释放移到空闲段。本条件不成立只表示证明未判定，不能反推一定能错开。

7.2 NPUState 最容易填错的地方

NPUState 描述快照时刻的一张卡。函数把这一时刻当作 0，所有剩余时间都是相对于现在的 ms。

    • request：当前请求的已知 manifest；没有请求时为 None。
    • next_layer：下一层尚未开始计算的层号。正在算 L2 时应填 3，而不是 2。
    • compute_end_in_ms：当前计算还剩多久；负数表示前一个 deadline 已经过去，卡正在等数据。
    • queued_io_by_ssu：第一待计算层已提交、尚未离开各 SSD 的数量，包含在途 SSD I/O，不含
     link-only I/O。
    • unissued_by_ssu=None：这层读取还没激活；全 0 的元组表示已激活且全已提交，两者不同。
    • link_pending_io：第一待计算层尚在接收队列中的 I/O 数，包含正在接收的一条。
    • next_issue_in_ms、
                      emitter_ssu_order：本卡客户端下一次可以发射的时间、
                                                       尚未发完的 SSU
     轮转顺序。它们不是 SSD FIFO 顺序。
    • waiting_requests：已经到达、在本卡排队的后续请求。不要放入未来尚未到达的请求。

当前请求正在计算最后一层时，如果下一请求的 L0 已经被跨请求预取，这些 I/O 数量描述的是那个 L0；
原请求仍放在 request，下一请求放在 waiting_requests 的第一位。



7.3 同样的总队长为什么会有不同结果

假设盘的 Path0 总共还剩 4 条 I/O，NPU0 和 NPU1 各占 2 条：

    • 排列 A：NPU0、NPU0、NPU1、NPU1。
    • 排列 B：NPU1、NPU1、NPU0、NPU0。

总队长、每卡数量都一样，NPU0 到齐时间却不同。NPU0 的计算因此不同步，后续层的发射时刻也跟着
改变。

到了多盘，还会改变不同 SSD 的到达流如何在同一个 NPU 接收口合并。信息不足不是公式复杂度的问
题：不同真实状态映射成了同一个输入计数。任何只接收这些计数的确定函数，都不可能同时精确还原这两
种真实状态。

9.3 容量检查通过，也不等于无 stall

上述是必要条件，不是充分条件。还可能存在：

     • Path0 的长批次把短预算任务挡在后面。
     • 读取激活得太晚，整体吞吐够但 deadline 前的时间不够。
     • 多盘组成的同一层有一个慢分量；其他盘的提前完成不能抵消它。
     • 同刻完成造成 NPU 接收突发。
     • 后续请求 profile 变化，把原先可行的错开相位打破。

这些是调度有机会改善的部分，但改善多少仍需要同输入实验。

     • demand：根据剩余读量与计算时间构造需求，用联合 max-min 分配作为对照。
     • deadline：按当前数据 deadline 排序，再为某层各盘分量同步分配。

     • deadline_reserve：先尝试给每层保留 𝑊 /(𝐷 − 𝑡)，再分配剩余带宽。

10.3    CIR 不是实际瞬时速率，也不是 PIR

这一点是本实验最重要的实现边界之一：CIR 表里满足行上限，不代表实际流量绝不会把 HBM 接收口
打满。原生仲裁器保留历史虚拟完成标签；正在服务的命令不能抢占；CIR=0 的 Path 仍可能借用空闲带
宽。

因此，“CIR 偏向最早 deadline” 不是精确 EDF，也不是硬限速器，更不是无 stall 保证。当前 sim.py
明确拒绝有限 PIR，实验使用的是不限 PIR。虽然策略权限允许设置 PIR，本轮并未凭空补出一个未经验
证的有限 PIR 模型。

在线控制使用已到达 manifest、真实计算进度、HBM 完成通知，不读取 SSD FIFO。只有 HBM 回执
时，已经离开 SSD 但尚未进入 HBM 的字节还会保守计入剩余工作，这会产生一定过度预留。

控制在层开始、整层到齐、可选的某盘分量到齐以及原生请求边界触发。可使用最小更新间隔合并通知。实

                    13 最后整理成实际使用顺序

 1. 先确认完整 176 KiB 单位、每层计算时间、分盘 placement 和每卡接收上限。
 2. 对全未提交的目标层，用 screen_current_layer 排除那些最理想也赶不上的情况。
 3. 新请求到达时，读取已到达状态，用 predict_request_impact 比较加入前后；明确不知道 FIFO
     时只能作条件预测。
 4. A/B 用便宜、可获取的计数和 deadline 在线决策；不要每次到达都把全 I/O 多层展开成本当成免
     费。
 5. 用原仿真器的同输入对照验证收益、误差和失败案例，再判断是否值得增加真实遥测和控制开销。

核心判断是：共享的每个瓶颈资源都要单独计算，读取还必须赶上具体层的 deadline。总平均带宽够，只
是必要检查的一部分。
