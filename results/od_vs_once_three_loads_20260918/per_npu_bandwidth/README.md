## 两根线怎么看

- **橙色虚线：需求 B。** 当前已接纳请求每层读取量 V，除以该请求每层纯计算时间 C。它表示把读取藏进计算所需的参考速率；计算和 I/O 等待期间都保留这个需求。它不是磁盘此刻实际收到的流量。
- **蓝色实线：实际供给 b。** 在一个完整层周期内，三块 SSU 实际为这张卡读取的数据量，除以周期时长。蓝线统一线宽，不用粗细表示读取量。
- **灰色背景：这张卡正在 I/O 等待。** 查看需求与供给差距时，可同时看灰底是否出现。

```text
完整层周期 = 本层开始计算 → 下一层开始计算
周期时长 = 本层计算时间 + 下层开始前暴露出来的 I/O 等待

B = 当前请求每层读取量 / 该请求每层纯计算时间
b = 这个完整周期内 SSD 实际服务量 / 完整周期时长
```

蓝线按层周期平均，**不是只除以磁盘忙着读取的时间**。例如，读取提前完成后仍有计算，剩余时间也在分母中。

同一请求内部各层的读取量、计算时间相同，所以本实验的完整内部周期满足：

```text
b / B = C / (C + I/O 等待)
```

这时蓝线低于橙线，说明这个周期存在暴露出来的等待；这也是层周期利用率下降的原因。**该关系不应直接套到跨请求周期、瞬时利用率，或整窗两个均值的比值。**

## 两种容易误读的边界

**请求切换处：** 当前请求最后一层计算时，会预取下一请求首层。这个周期的蓝线对应下一请求读取量，橙线仍按当前已接纳请求定义；两条线可能短暂错位。即使欠载组利用率是100%，也可能出现蓝线高于橙线的尖峰，不能据此认定多读了数据或出现了等待。

**2秒、4秒边缘：** 先按完整周期算平均，再裁剪显示到 [2,4)。不把边缘小片段单独当成一个完整周期。右侧“供给均值”直接取真实SSD物理服务在这两秒内的统计；它可能与蓝线可见面积除以2秒略有不同。

每条蓝线对应其 NPU 自己的层周期，不同卡的平均区间不一致。不能把它们逐时刻相加后称作“该时刻磁盘实际供给”，也不能用单盘40 GiB/s限制三盘合计的每卡曲线。

同组的两种策略使用逐字节相同的请求输入。过载组两策略平均需求相差较大，是请求执行速度和驻留时间改变的结果，不能理解成给 OD 喂了更多请求。

## 数据来源与核验

未重新运行仿真，也未修改旧图。读取六份已完成实验及三份 OD 的逐块 SSD 服务采集记录。检查结果：

- 六份输入均为32卡、3盘、8层、batch=1；两策略同组 manifest 完全相同。
- 共检查46,912个完整层周期：下一层 I/O 提交时刻等于本层计算开始；下一层计算开始等于“本层计算结束”和“下一层 I/O 就绪”二者的较晚者。最大时序误差为0。
- 因为只预取下一层，完整周期内实际SSD服务量恰等于下一层实际读取量；跨请求时使用下一请求首层的量。与已有 OD 逐块服务记录对照，最大量误差小于 `1e-14 GiB`。
- 每卡利用率重新积分计算区间；真实供给均值核对逐盘服务统计；需求均值核对原实验逐事件需求积分。全部32卡在warm窗口持续活跃。

实际供给指 SSD 物理读取服务，原始记录以 `ssd_activation_time → link_enqueue_time` 统计。完整周期内可用守恒关系恢复其总量，不代表 SSD 服务和 NPU 链路传输的瞬时时序相同。
