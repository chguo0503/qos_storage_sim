## 局部图怎么读

放大的是 Ordered 运行中的 **3094–3105 ms**，即原暖窗内的一小段。先看上方长流，再看中间短流，最后看下方 SSU 4 的真实服务顺序。

1. NPU 一边计算第 2 层，一边预取第 3 层。程序中的 L0 是第 1 层，L1 是第 2 层，L2 是第 3 层。
2. **长流**上一层要算 25.612 ms，第 3 层的数据在 7.873 ms 后到齐，赶得上继续计算，因此没有 IO stall。长计算会延续到图外的 3121.203 ms，图上用箭头标出。
3. **短流**上一层只算 0.528 ms，第 3 层的数据却要 5.817 ms 才到齐。算完后只能停下来等，**IO stall = 5.817 − 0.528 = 5.289 ms**。
4. 为什么短流的数据这么晚？决定这一层何时到齐的最后一个短数据块，在 **SSU 4 的 Path 0 队列里等了 5.809 ms**。这段等待中，磁盘有 **5.704 ms（98.2%）在服务排在它前面的长请求块**，另有 0.105 ms 在服务其它短块，没有空闲。轮到这个短块后，真正盘读只要 **4.196 微秒**，链路传输再用 **3.357 微秒**，链路排队为零。

因此，这次停顿的直接原因是：**前方长请求的大量读块占着 FIFO 的服务次序，短请求剩余的计算时间又太短，无法把等待隐藏起来。** 其它卡计算得久，并不会直接占住这张短卡；共享磁盘上的先后服务关系才是这里的阻塞点。

## 标注中的时间各指什么

| 项目 | 长流示例：NPU 2 | 短流示例：NPU 8 |
|---|---:|---:|
| request ID | 2000304 | 8000307 |
| 当前预取层 | 第 3 层（L2） | 第 3 层（L2） |
| 上一层计算时间，可用于覆盖预取 | 25.612344 ms | 0.527909 ms |
| 整层读取跨度：发起 → 全部到达 HBM | 7.872949 ms | 5.817127 ms |
| 下一层开始前的 IO stall | 0 ms | 5.289218 ms |
| 这一层读取量 | 262.968750 MiB，1530 块 | 1.203125 MiB，7 块 |
| 这一层自身累计占用的盘服务时间 | 每盘 255 块，各 1.070023 ms | 一盘 2 块，其余每盘 1 块，各 0.004196–0.008392 ms |

**读取跨度包含提交、盘排队、盘服务、链路排队和传输，不能把它都叫作盘服务时间。** 六块盘可以并行，表中的各盘累计服务量不能直接相加当成整层读取延迟。IO stall 与关键块排队时间也不是同一个量：部分排队可以被上一层计算覆盖，数据到齐还包括盘读和传输。

橙色框内共与 1360 个长块和 25 个其它短块的盘服务重叠。第一个长块在短块入队前已经开始服务，所以服务量只统计其重叠的剩余时间，不能直接用 1360 乘完整单块服务时间。

阻塞长块来自 NPU 0、1、2、4、5、6，均为内部第 3 层（L2），入队都早于关键短块。长示例 NPU 2 确实属于这些阻塞者。本图窗口内没有长请求首层 L0 读取。

## 欠载与结论范围

Ordered 全程六盘中最大的名义需求为 **34.136730 GiB/s < 40 GiB/s**。名义需求按已约定的“当前请求每层读取量 / 每层计算时间”逐盘、逐事件核算；跨请求首层预取不另加一份需求。需求附图画的是这个量，**不是盘实际吞吐，也不表示任意时刻都没有突发排队**。局部图恰好展示了名义欠载时仍出现的 FIFO 突发积压。

这 11 ms 是为了看清一次具体等待而选取的片段，不能用它替代完整 2 秒的平均利用率，也不能由单个片段断言全部利用率损失都是同一来源。图中的 83.5963% 始终指原 [2,4) 秒窗口。
