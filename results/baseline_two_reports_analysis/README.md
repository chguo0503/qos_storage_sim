# baseline_two_reports：长短请求带宽与计算统计

本目录仅重新统计用户提供的 `baseline_two_reports`，没有运行新模拟，也没有修改原报告及输入。统计脚本与来源哈希见 [summarize_inputs.py](summarize_inputs.py)、[audit.json](audit.json)。

**统计口径。** 长序列是 >80K（LS/LL），短序列是 ≤80K（SS/SL）；NQL 划分类别第二位，并不直接代表计算时间。低利用率案例的 S/L 是画像族，L 同时包含 LS 和 LL。1K=1024 token，MiB=2²⁰ byte，GiB=2³⁰ byte。

带宽需求定义为 `B_need=1000×V_GiB/C_ms`，即每卡维持连续计算所需的数据速率。画像族使用完整输入的 `1000×ΣV/ΣC`，不使用各请求 V/C 的简单算术平均。固定分卡场景的整组需求为各卡此比值之和。它不是实测 SSD 交付带宽；I/O 发出至就绪也包含排队及链路，不能当盘独占服务时间。

每层 V 为跨全部 SSU 的读取量，每请求共8层，因此请求读取量为8V，纯计算时间为8C。各 SSU 容量40 GiB/s，每 NPU 接收链路50 GiB/s。

**1. 什么时候整机平均利用率低。** 本包实测是：少数长族卡发出大读取，多数短族卡连续处理计算窗口约0.53 ms的请求，共享每盘Path0 FIFO。短族等待占了大部分卡时间，拉低整机平均。32卡在各自warm窗口都全程有请求，idle=0。最热盘理想平均需求均小于40 GiB/s；因此并非已证明持续平均容量超载，但平均可行也不保证每一层都能及时取到数据。

|SSU盘数|长卡/短卡|整机U|短族U|长族U|最热盘理想GiB/s|
|---:|---:|---:|---:|---:|---:|
|4|6/26|64.0552%|55.7602%|100%|38.775901|
|5|9/23|60.2169%|44.6496%|100%|39.841274|
|6|11/21|67.3949%|50.3161%|100%|38.757173|

例如5盘：`(9×100%+23×44.6496%)/32=60.2169%`。三个点改变了盘数及卡数配额，不能当成同输入单独增加盘数的趋势。这是合成固定族输入，1K计算参数含外推，只有各自单seed的一个warm秒。

原始混排案例整机93.2605%时，LL占90.6628%的窗口卡时间，SS只占6.0010%；SS合并时间计算比虽仅25.1808%，也不足以大幅拉低整机平均。低例中的固定短卡则占65.625%–81.25%的卡时间。证据见原 [高利用率报告](../../baseline_two_reports/01_baseline_high_utilization_rebuttal.md) 与 [低利用率报告](../../baseline_two_reports/02_baseline_low_utilization_inputs.md)。

**2. 长请求也会明显等待，但要区分聚合范围。** 原混排案例中，NPU31的 request 31000009 为96K/NQL512（LL）；完整请求落在[1000,2000)ms，8层纯计算72.566734ms、等待48.728378ms、接纳至完成121.295112ms，计算比59.826594%。L2–L7均发生等待。该画像在所有出现卡上的条件U平均为86.922195%，合并时间比86.428466%；全部LL平均仍为98.710181%（合并98.733033%）。不能把这条长请求的低值冒充整个LL类平均。

三个低整机案例中，LS和LL在观测窗口均100%。因此本包没有“整个长类平均已降到50%–60%”的实测结果。机制上长类也可能差：取数历时超过可用于预取的计算窗口即可暴露等待；大量长卡同时取数还会遇到总容量限制。例如用原报告192K/NQL512画像估算，4盘、24长卡+8短卡时，长卡满算所需约360.396 GiB/s，而全盘只有160 GiB/s；即使全部供给长类，其持续运行平均U也不超过约44.40%。这个数是容量推导，非新模拟，也不是Baseline独有的调度缺陷证明。
