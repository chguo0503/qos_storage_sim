**这组实验为什么需求平均超过120，但SSU平均吞吐没有达到120？**

核查对象：`figures/ssu3/fleet_total_bandwidth_curves` 下的 Baseline Random、Ordered，32 NPU、3 SSU、seed 7、warm [2,4) 秒。2026-09-15重新积分已有逐块记录，没有运行新仿真。

结论：**需求并非每个时刻都超过容量。需求超过容量的片段，SSU确实基本满速；整窗平均吞吐较低，主要因为其他片段的已提交I/O队列会空掉。** 未来还有请求，不代表这些请求的所有层都已经交给SSU读取。

配置中的单位是GiB/s。三盘合计容量为120 GiB/s；吞吐除以120才是SSU利用率。

| warm [2,4) 的指标 | Baseline Random | Baseline Ordered |
|---|---:|---:|
| 原图需求曲线的时间平均，GiB/s | 189.795 | 318.750 |
| 需求大于120的时间占比 | 75.88% | 34.19% |
| 仅在需求大于120时，真实SSD吞吐，GiB/s | **119.912** | **120.000** |
| 在需求不大于120时，真实SSD吞吐，GiB/s | 83.525 | 47.531 |
| **整个窗口的真实SSD吞吐，GiB/s** | **111.136** | **72.308** |
| **整个窗口的SSU平均利用率** | **92.61%** | **60.26%** |
| 原图蓝线整窗平均，GiB/s | 111.146 | 72.252 |
| 三块盘同时空闲的累计时长 | 147.031 ms | 794.585 ms |
| NPU平均利用率 | 90.68% | 71.01% |

表格来自原始CSV的分段时长加权，以及trace中每块数据真实SSD服务区间的积分。没有用图片像素估计，也没有把CSV各行不等长的区间简单平均。机器可读结果与源文件SHA见[ssu3_bandwidth_audit.json](ssu3_bandwidth_audit.json)。

用Ordered代入就能看出平均值为什么低：

```text
整窗平均SSD吞吐
= 过载时长占比 × 过载时SSD吞吐
  + 其余时长占比 × 其余时段SSD吞吐

Ordered ≈ 34.19% × 120 + 65.81% × 47.531
        ≈ 72.308 GiB/s
```

**先区分图上两条线与磁盘实际工作。**

需求线是32张卡“当前请求的每层读取量 / 每层纯计算时间”之和。它表示维持理想计算节奏所需的参考带宽。在这版图里，请求从开始处理到完成，包括I/O等待期间，都会计入其需求；下一层已经读完后，这个参考值也不会立即变成零。跨请求首层的物理读取计入实际供给，需求线沿用当前请求画像，没有额外加算下一请求首层。

```text
B_i = 当前请求每层读取量 V_i / 每层纯计算时间 C_i
```

因此，需求线不是“此刻磁盘队列里待处理的字节数”，也不是“此刻每秒新提交到磁盘的字节数”。仅凭它大于120，不能推出磁盘队列时时非空。

蓝线则先把每张卡实际收到的数据摊到该卡的层周期，再把32张卡相加。各卡周期不对齐，所以蓝线局部甚至可以超过120；这不代表SSD瞬时超出物理容量。蓝线整窗面积严格等于NPU在窗内收到的数据量，所以**不能把整窗供给不足解释为平均画法造成的假象**。它与真实SSD吞吐的微小差异来自窗边界上SSD已读完、NPU尚未接收完的在途数据。计算口径见[绘图脚本](../render_fleet_total_bandwidth_curves_ssu3.py)。

**为什么还有请求，盘却会没活干？**

本实验的层间规则是：

```text
开始计算第k层
    -> 提交第k+1层读取
    -> 第k+1层数据可能很快读完
    -> 继续等第k层计算完成
    -> 开始计算第k+1层，才提交第k+2层读取
```

只提前一层预取。在当前层算完之前，不能因为盘闲了，就把所有更后面的层都读进来。最后一层计算期间可以预取下一请求的首层，依然不是无限提前读取。实际调用代码在[continuous_batch_sim.py](../../../continuous_batch_sim.py)，`_dispatch_compute` 中的 `layer + 1` 分支。

两类输入的真实参数如下，直接使用data中的计算时间和读取量：

| 类别 | 总输入 / miss | 每层读取量 | 每层纯计算时间 | B_i |
|---|---|---:|---:|---:|
| A：大读取、短计算 | 128K / 256 token | 175.656 MiB | 6.024 ms | 28.476 GiB/s |
| B：小读取、长计算 | 32K / 4096 token | 38.500 MiB | 28.593 ms | 1.315 GiB/s |

为了理解，假设32张卡同时开始计算某个B请求的内部层、同时预取下一层，没有此前积压。下面只估算SSD服务时间，暂不计NPU接收尾部和提交错位：

```text
32张卡下一层共需读取 = 32 × 0.03759765625 = 1.203125 GiB
三盘满速读取这些数据需要 = 1.203125 / 120 = 10.026 ms
本层计算需要 = 28.593 ms

读完之后，可能还有约18.567 ms计算时间。
如果没有其他卡提交新的读取，盘只能空闲。
```

此时32卡参考需求之和也只有42.078 GiB/s，远低于120。

反过来，32卡若一起进入A请求内部层，参考需求达到911.230 GiB/s。一起读取下一层需要约45.744 ms，但计算仅能提供6.024 ms的预取时间，很容易出现等待。Ordered更容易出现集中的A阶段和B阶段：A阶段读取赶不上计算节奏，B阶段下一层已读完而本层还没算完。Random更容易让不同卡的阶段互相补充，所以磁盘平均忙率更高。

这些同步算式是解释机制的简化例子，不假设真实32卡始终完全同步。下面是实际记录中的证据。

**找到的真实空闲片段。**

Ordered中，三块盘在 **2.026335–2.043650秒** 同时空闲，共17.315 ms。32张卡此时全在处理B请求，而且整个片段都在计算。最后一点NPU接收在2.026776秒结束，此后的16.874 ms内，所有卡都已拿到下一层数据，继续计算本层。

以NPU25的请求25000007为例，层号从0开始：

```text
2.015057秒：开始计算第2层，同时预取第3层
2.015814秒：第3层数据已到齐
2.043650秒：第2层计算结束；开始第3层计算，才提交第4层读取
```

这段等待计算完成的时间里，该卡没有更多已提交的SSD工作。窗口内32卡始终有请求在处理；磁盘空闲不是有限输入已经耗尽。

Random中也有极少量“参考需求大于120，但三盘同时空闲”的片段，总共1.102 ms，占2秒的0.0551%。例如2.973511–2.974235秒有3张A卡和29张B卡，参考需求123.561 GiB/s，但32卡都在计算，SSD已完成当前提交的工作，只有部分预取仍在NPU接收链路上。这也说明参考需求不能代替磁盘队列状态。

**这是不是Baseline故意限速或没有转移剩余带宽？**

这组记录不支持这个解释。每个SSD块实际执行时都使用40 GiB/s；逐盘吞吐如下：

| 顺序 | SSU0 | SSU1 | SSU2 |
|---|---:|---:|---:|
| Random，GiB/s | 37.041600 | 37.050513 | 37.044135 |
| Ordered，GiB/s | 24.100941 | 24.106058 | 24.100937 |

三盘非常均衡。检查盘上所有服务空隙，空隙后的首块均在它被提交的同一时刻开始服务；没有观察到“块已经在FIFO中排队，盘却闲着”的情形。[sim.py](../../../sim.py) 的 `_dispatch_one` 也明确设置 `flow.bw = self.disk_bw`。SSD完成后会继续调度，NPU接收阶段使用独立队列，不要求SSD等HBM接收确认才读下一块。

FIFO仍然可能让某些层的数据不能及时到齐，影响NPU利用率；这里区分的是“数据能否在计算结束前到齐”和“SSD有已提交工作时是否满速”两个问题。此次核查解释了盘为什么空闲，不能仅凭这个均值就把全部NPU损失归因于一个QoS path。预取深度、各卡阶段分布以及不同层的计算时限也参与了结果。

**为什么Ordered的平均需求反而更高？**

两种顺序每卡都是40个A、80个B。如果按照完整请求数量和纯计算时间计算，维持无等待节奏所需的总带宽相同：

```text
32 × (V_A + 2 × V_B) / (C_A + 2 × C_B)
= 124.910 GiB/s
```

它表示完整输入工作量对应的理想平均需求，约比容量高4.09%；它不是外部持续到达速率，也不是所选窗口的需求曲线均值。

图上的189.795和318.750按“当前各卡正停留在哪类请求”统计。A等待越久，高需求的A画像就会在时间轴上被计入越久。因此，Ordered较高的平均参考需求，部分是等待加重造成的结果，不能理解成Ordered额外输入了更多数据。

同样不能用“整窗总供给 / 整窗总需求”计算NPU利用率。要研究层上的 `b_i / B_i`，应匹配该层的数据、计算时长和读取/计算周期，处理跨请求与窗口边界；本次总量图主要说明工作量和供给，无法保留每卡每层的时限信息。

核查使用的原始文件位于 `validation20s/runs/ssu3_{random,ordered}_k1_sync_seed7/baseline/`，包括 `manifest.json.gz`、`result.json.gz`、`trace.json.gz`、`command.json`。源文件SHA、核心仿真文件SHA、完整记录标记、Path0路由及物理传输时长均通过检查。所有带宽数字仅针对这些图的[2,4)秒窗口，不外推为任意窗口或其他随机种子的结论。
