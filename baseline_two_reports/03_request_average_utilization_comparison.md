**请求平均计算利用率：公式与原 Baseline 报告的对比**

日期：2026-09-08。数据来自 [01_baseline_high_utilization_rebuttal.md](01_baseline_high_utilization_rebuttal.md) 的同一次实验：**32 NPU、6 SSU，每请求 8 层，batch=1**。本次只重新聚合已保存事件，没有重跑仿真。

在原报告的同一个 **[1000, 2000) ms** 窗口，原整体 NPU 利用率为 **93.2605%**，改用请求等权平均后为 **82.4403%**，低 **10.8202 个百分点**。变化来自统计权重，不代表设备实际计算时间减少。

**公式：先算每个请求的计算比例，再平均**

$$
\boxed{
U_{\mathrm{request}}
=\frac{1}{N}\sum_{i=1}^{N}\frac{C_i}{C_i+W_i}\times100\%
}
$$

- $N$：参与统计的请求数。
- $C_i$：请求的计算时间。
- $W_i$：请求已接纳后，因 I/O 未就绪产生的等待时间。
- 每个请求权重相同；计算时间长的 LL 不会仅因持续时间长而获得更大权重。

对完整请求，$C_i$ 是全部 8 层的计算时间，$C_i+W_i=completion_i-admission_i$。该公式衡量接纳后的计算效率，不包含接纳前排队。

**与原报告比较时，必须统一观察窗口。** 本文主表使用与 [原报告第 3、4 节](01_baseline_high_utilization_rebuttal.md) 完全相同的窗口：对每条与窗口重叠的请求，分别裁剪计算时间和 I/O 等待时间，再代入上式。具体为：

$$
U_{\mathrm{request}}^{H}
=\frac{1}{|R_H|}\sum_{i\in R_H}
\frac{C_i^{H}}{C_i^{H}+W_i^{H}}\times100\%,
\qquad H=[1000,2000)\ \mathrm{ms}
$$

$R_H$ 是接纳后执行区间与窗口有正时长重叠的请求集合。该窗口共有 **183 条重叠请求**，使用这 183 条在窗口内的执行片段，每条等权；不是只取窗口内完成的 151 条，也不是使用全部输入的 704 条。跨左边界和右边界的请求各 32 条，完全位于窗口内的请求 119 条。

**同一窗口：整体及每个类别的对比**

| 范围 | 窗口内重叠请求数 | 原报告：先逐卡算再平均 | 原报告：合并时间计算比 | 新指标：先逐请求算再平均 | 新指标减原逐卡平均（百分点） |
|---|---:|---:|---:|---:|---:|
| **整体** | **183** | **93.2605%** | **93.2605%** | **82.4403%** | **−10.8202** |
| SS | 42 | 35.0646% | 25.1808% | **39.4282%** | +4.3636 |
| SL | 14 | 73.0651% | 66.9992% | **73.5287%** | +0.4636 |
| LS | 0 | — | — | — | — |
| LL | 127 | 98.7102% | 98.7330% | **97.6471%** | −1.0631 |

原报告的整体指标是每卡计算时间除以 1000 ms，再对 32 卡平均；类别指标则先算每张卡处理该类时的计算比例，再对出现该类的卡平均。SS、SL、LL 分别有 24、11、32 张卡参与类别平均。

“合并时间计算比”是 $\sum C/\sum(C+W)$，仍按执行时长加权。本窗口全部 NPU 全程有已接纳请求，空闲时间为 0，因此整体的合并时间计算比与原整体 NPU 利用率相同。LS 没有请求，记为“—”，不按 0% 参与平均。

**为什么整体降低，而 SS 的类别结果反而升高？**

整体降低，是因为 LL 在新整体平均中的权重从占用时间份额变为请求数量份额：

| 类别 | 原整体指标中的占用时间权重 | 新整体指标中的请求数量权重 |
|---|---:|---:|
| SS | 6.0010% | 42/183 = **22.9508%** |
| SL | 3.3363% | 14/183 = **7.6503%** |
| LL | 90.6628% | 127/183 = **69.3989%** |

原整体值由“时间权重 × 各类合并时间计算比”求和得到；新整体值由“请求数量权重 × 各类请求平均计算利用率”求和得到。利用率较低的 SS 在新平均中获得了更大权重。

SS 从 35.0646% 变为 39.4282%，是因为原来每张出现 SS 的卡权重相同，现在每条 SS 请求权重相同。不同卡上的 SS 请求数量和执行效率不同，结果可以上升或下降。**新公式消除的是单条长请求的持续时间权重，不保证每个类别的结果都比原公式低。**

新指标仍按请求数量加权，LL 在该窗口有 127 条，仍占 69.3989% 的权重；它不是对 SS、SL、LL 三个类别各赋予三分之一权重。

**与上一轮回答的 82.31% 区分**

上一轮的 82.3127% 使用的是全部 **704 个完整请求**，计算每条请求从接纳到完成的完整 8 层效率；本文主表的 82.4403% 使用的是 **183 个窗口内请求片段**。两者是同一平均方法在不同统计范围上的结果。

| 范围 | 全部输入请求数 | 完整请求平均计算利用率 | 同 1 秒窗口的请求平均计算利用率 |
|---|---:|---:|---:|
| 整体 | 704 | **82.3127%** | **82.4403%** |
| SS | 192 | 45.9501% | 39.4282% |
| SL | 64 | 85.4101% | 73.5287% |
| LS | 0 | — | — |
| LL | 448 | 97.4542% | 97.6471% |

与原报告的 93.2605% 做同窗口对比，应使用 **82.4403%**。评估固定输入批次中“每条完整请求的一票”，则使用完整请求口径，等待该批请求全部完成后统计。窗口片段口径会受边界裁剪影响，不能当作请求完整生命周期的效率。

**数据来源与复核**

- [逐请求窗口账](data/high/warm_requests.csv)：183 条请求的 `warm_compute_ms`、`warm_stall_ms`、`warm_active_ms`。
- [逐层事件](data/high/warm_layers.csv.gz)：独立裁剪计算事件，复核全部 183 条请求的窗口计算时间。
- [逐卡类别表](data/high/per_npu_category.csv) 与 [原统计结果](data/high/statistics.json)：复核原逐卡均值及合并时间计算比。
- [全部输入与完成时间](data/high/all_inputs_and_times.csv.gz)：复核全部 704 个完整请求的结果。

复核得到窗口计算合计 29843.348635 NPU-ms，I/O 等待合计 2156.651365 NPU-ms，两者合计 32000 NPU-ms，与原报告一致。所有新均值均直接从逐请求数据计算，未对原报告已经四舍五入的百分比再次求平均。

在本文件所在目录运行以下代码，可复算主表中的新指标：

```python
import csv
from math import fsum

with open("data/high/warm_requests.csv", encoding="utf-8-sig") as f:
    requests = list(csv.DictReader(f))

for category in ("整体", "SS", "SL", "LS", "LL"):
    group = requests if category == "整体" else [
        r for r in requests if r["category"] == category
    ]
    if not group:
        print(category, 0, "—")
        continue
    utilization = fsum(
        float(r["warm_compute_ms"])
        / (float(r["warm_compute_ms"]) + float(r["warm_stall_ms"]))
        for r in group
    ) / len(group)
    print(category, len(group), f"{utilization:.4%}")
```
