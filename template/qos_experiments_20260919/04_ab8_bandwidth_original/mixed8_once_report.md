# 同一 8 NPU 混合输入：补充原始 Once per layer

2026-09-14；8 NPU、1 SSU（40 GiB/s）、ring hash、seed=7、窗口 [2,4)s。

本次补跑参考实验的 **原始 Once per layer，5 ms 状态采集**。上一轮的“短读取优先”仅是验证 FIFO 阻塞机制的诊断对照，两者不是同一策略。本次不改变输入、请求执行顺序、NPU 绑定、盘映射、计算时间或盘/链路容量。

Once 整机利用率为 **97.16%**，相对 FIFO 的 92.52% **变化 +4.63 个百分点**；短流利用率为 **97.54%**；TTFT SLO×1.5 为 **100.00%**。

## 输入与公平性

每张 NPU 都是 6 个 L+66 个 S，独立随机打乱，合计 576 条请求；每张卡的 `(总长度,NQL)` 组合均不重复。L 为 199.9873–200K、NQL1651–1664，每层计算57.0524–57.5039ms，读取0.266372681GiB；S 为20–20.0801K、NQL1024–1106，每层计算5.2440–5.6668ms，读取0.025512695GiB。K=1024 tokens。

类内固定 KV 命中前缀，小幅变化 NQL 和总长度，计算时间从原始 `data` 插值；20K 低于实测32K下界，使用32K/48K长度外推。这是构造输入，不能称为新硬件实测。所有请求t=0到达，batch1、8层，沿各自NPU队列串行接纳；这不是低到达率的泊松场景。

盘侧原生 ring hash 使用 `(request_id,block_index)`，不含layer，同一block全部层在同一盘。1 SSU下全部block映射到唯一盘。任意8卡当前请求组合的名义需求上界 **38.916459<40 GiB/s**，因此是轻度存储欠载；名义需求不重复计入跨请求L0预取，不等价于瞬时突发IO速率或零等待保证。Once全程名义需求峰值为 **38.050129 GiB/s**。

启动前已验证生成输入指纹与封存baseline一致，运行后独立对比完整requests、placements及核心文件SHA256。逐层区间独立复算利用率和等待，使用完整结果判断窗口内admission cohort的SLO。

## Once 实际做了什么

使用 `run_case(strategy='once', assignment='fixed')`，进入原始 `shared_path_adapter`。参考实验记录的29个核心/策略SHA256均与当前源文件一致。此次没有使用`once_native`入口；后者的TTL=0，与参考5ms版不同。

1. 盘状态在0、5、10…ms采集，客户端使用最近快照。
2. 每个“请求、层、SSU”只规划一次整层IO的Path，按类别允许的Path、快照排队量和QoS服务估计完成时间，并加入本层的局部影子负载。
3. 规划好的IO仍每NPU每0.1μs下发一条176KiB IO。每条Path内部FIFO；盘每次仲裁一条非抢占IO。
4. 不调整请求先后顺序，不改变NPU绑定，不在运行中修改CIR；一次规划后不按每个IO重新读取实时盘状态，也不使用new_once的全局未发预留量。

256 Paths分成8组，沿用FINAL_STATIC表。SS/SL/LS/LL各类总CIR为20/6/8/6GiB/s，Path数量为96/32/96/32，PIR无限，可共享空闲容量。此次自定义的短类 **S在QoS分类里是SL**，长类L是LL，因为两者NQL均≥512；两类各32条Path、总CIR6GiB/s。S/L是本实验的总长度标签，不能把S误写成QoS的SS。

## 指标与每卡混合验证

整机U=8卡在[2,4)s内计算时间之和/16000card-ms。分类U=该类在窗口内计算时间/该类在窗口内从admission至completion的活动时间，不是该类占整机时间的比例。

TTFT从NPU接纳请求开始计时，阈值为每请求`1.5×8×自身每层计算时间`，不包含t=0到admission的上游排队。各策略执行进度不同，窗口内admission请求集合和数量可不同；完整冻结输入相同，但表中SLO不是同一cohort逐条配对。

## 剩余等待在哪里

| Once 等待位置 | card-ms | 占整机窗口百分点 |
|---|---:|---:|
| 长流 L0 | 287.993424 | 1.799959 |
| 短流 L0 | 21.094429 | 0.131840 |
| 短流 L1–L7 | 145.993322 | 0.912458 |
| 长流 L1–L7 | 0 | 0 |
| 合计 | 455.081176 | 2.844257 |

Once相对FIFO减少短流等待970.241535 card-ms，同时增加长流等待229.159055 card-ms，净节省741.082480 card-ms，对应整机提升4.631765个百分点。

长流L0占Once剩余等待的63.284%。长请求一层无竞争盘读取下界为6.659317ms，而前一短请求末层计算仅约5.244–5.667ms。窗口内19次S→L的物理等待下界合计23.111012 card-ms（0.144444个百分点），明显小于实际长L0等待287.993424。因此不能把剩余2.84个百分点全说成不可避免的L0物理下限。

短流仍有167.087752 card-ms等待，其中145.993322在后7层。Once比短读取优先诊断低0.994094个百分点：短等待多167.087752，长等待少8.032727，净多159.055024 card-ms。这说明Once尚未消除所有短层读取延迟，但此次没有TTL/分组消融，不能将差距定量归因于5ms旧状态或CIR限制。

实际运行记录：4608次规划=576请求×8层，快照最大年龄4.998550ms，CIR写入、请求重排、NPU重分配均为0。

## 图与复现

`mixed8_once_bandwidth.png` 为逐卡需求/供给图；`mixed8_once_timeline.png` 为绿色计算、蓝色端到端读取（含排队）、黄色暴露stall、黑色请求完成标记。蓝色读取可与计算重叠，不能将整个读取时长当作stall。8卡均显示L/S混合。

带宽图紫线为当前请求V/C，蓝线为完整内部层周期收到的下一层字节量/周期时长，灰色是跨请求或窗口截断周期，不表示零IO。右侧实际供给精确统计本次仿真窗口内收到的字节量，两个整窗带宽均值之比不等于NPU利用率。数据来自本次运行只读观察，未为作图重放仿真。

