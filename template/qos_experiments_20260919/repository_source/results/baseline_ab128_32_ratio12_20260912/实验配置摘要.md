# A/B 混合请求实验配置摘要

本表对应当前两张总带宽曲线：32 NPU、3 SSU、seed 7、Random / Ordered。此前整个实验还测试了4、6 SSU；不同盘数需要分别列组。

| 项目 | 当前实验配置 |
|---|---|
| NPU | 32 张；每卡接收链路 50 GiB/s |
| SSU | 3 块；每块 40 GiB/s，总容量 120 GiB/s |
| A 请求 | 总输入 128K token，新增 256 token；每层读取 175.65625 MiB，计算约 6.024 ms；大读取、短计算 |
| B 请求 | 总输入 32K token，新增 4096 token；每层读取 38.5 MiB，计算约 28.593 ms；小读取、长计算 |
| 请求数据与模型 | A、B 均直接取自根目录 `data`；每请求 8 层，batch=1；没有缩放读取量或计算时间 |
| L1：请求分配给哪张卡 | 固定分卡，无卡间迁移；每卡 40 个 A＋80 个 B，请求数量比 A:B=1:2；32 卡共 3840 个请求 |
| L2：卡内请求顺序 | Random：每卡独立打乱自己的 40A＋80B；Ordered：每卡均按 `A→B→B` 重复 40 轮，初始同时开始，随后独立推进，没有运行时同步屏障 |
| L3：存储 I/O 调度 | 本批已测策略只有 Baseline：每块 SSU 各自使用 Path0 FIFO；并非所有 SSU 共用一个全局 FIFO |
| 外部请求输入 | 有限批次一次性输入：3840 个请求全部在 t=0 到达，之后不新增请求 |
| 内部执行方式 | Layerwise 计算与预取：当前层计算时预取下一层；数据未就绪则等待。下一请求首层可在当前请求最后一层计算时预取 |
| 主统计窗口 | 跳过前 2 秒，统计固定 warm 窗口 `[2,4)` 秒，窗口长度 T=2 秒；不是整个运行过程的正中间，也不等于已证明进入稳态 |
| 窗口内活动条件 | 当前两张图中，32 张卡全程都有任务，且每卡均计算过 A 和 B；有任务包含 I/O 等待，不代表一直在计算 |
| NPU 平均利用率 | 窗口内全部 NPU 的实际计算时间之和 / `(32 × 2 秒)`；I/O 等待计入分母，不计入分子 |
| 随机种子 | 当前图使用 seed 7；报告中的 Random 多种子均值使用 seed 7、19、43 |

## 表述中需要注意的地方

1. **L1 不只是数量比，而是请求到卡的分配规则。** `A:B=1:2` 是每卡完整输入队列的请求数比例，不是某个时刻的 A/B 卡数比例，也不保证任意 2 秒窗口内执行或完成的请求数仍为 1:2。
2. **“Baseline / 流量分配”不能写成这批实验已经完成的策略对照。** “流量分配”是机制的泛称，Baseline 本身也决定 I/O 如何获得服务。本批没有 Once 或其他分配算法的对照结果。若用于未来实验设计，可写 `Baseline / 待测算法名称（尚未测试）`，并明确具体分配规则。
3. **“开环有限输入”需要注明观察层面。** 外部请求到达时间预先固定，不因请求完成而生成新到达，按这一意义可称开环有限输入。更直白的名称是“有限批次，全部 t=0 到达”。内部层计算和 I/O 提交仍相互依赖；外部输入开环不代表内部没有反馈，也不代表 L3 无法改变利用率。
4. **取 2 秒窗口只决定怎么统计，不决定开环或闭环。** 本次也不是严格逐盘、逐时刻欠载实验；名义带宽需求曾超过容量，不能把低利用率全归因于 FIFO 而忽略容量和请求集中出现的影响。
