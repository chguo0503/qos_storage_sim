# 2–4 秒逐 NPU 等待原因核查

对象：semi / Baseline / seed 7，32 NPU、3 SSD。每盘 40 GiB/s，每 NPU 接收上限 50 GiB/s。
原始输入、请求顺序和策略不变，重放到 4.05 秒；核对 2,888 个层计算开始时间，最大差异为 0。

## 结论

橙色等待表示：NPU 已经可以开始算下一层，但这一层的数据还没有全部进入 NPU。不能把所有等待都称为“短请求等长请求”。

- 共享 Path 0 FIFO 上，长读取量请求的 IO 可以排在短请求前面；也存在短请求之间以及长请求之间的竞争。所有单条 IO 都是 176 KiB，“长请求”指其 IO 数量多，而不是某一条 IO 特别长。
- 盘侧排队会推迟数据进入接收链路。某些停算片段内，SSD 已经完成相应读取，NPU 仍在以 50 GiB/s 接收剩余数据；不能因此把上游排队的影响忽略，也不能把整段停算都记成 SSD 排队。
- 跨请求首层只能利用前一请求最后一层的计算时间预读。如果这个窗口比新请求自身的读取时间短，即使没有其他请求竞争，也会有等待。
- 同一 NPU 上“后面的短请求排在前面的长请求后面执行”会增加该短请求的 TTFT；前一个请求正在计算时，NPU 仍然繁忙，这段时间并不是图中的橙色停算。

全部等待 560.91 卡·ms：首层 100.42 卡·ms（17.90%），后续层 460.48 卡·ms（82.10%）。83.69% 的等待发生在 SS/LS（NQL=256，计算窗口较短）上。按读取量区分，53.03% 发生在短读取请求，46.97% 发生在长读取请求本身。

## 三个具体例子

### NPU 17：确有短请求被长请求 IO 拖住

请求为 64K/256（SS），第 4 层（代码 layer=3）：2.427075 秒发起读取，2.430415 秒前一层计算结束，2.441843 秒数据到齐。读取历时 14.768 ms，只能用前一层的 3.340 ms 计算掩盖，因此停算 11.428 ms。
实际服务依赖链中，前方包含 NPU 21、NPU 16 的 200K/256，以及 NPU 4、28、15、11 等卡的长请求 IO，也包含 NPU 30、31、13、25 的短请求 IO。该层独立读取只需约 1.716 ms，本来可以在 3.340 ms 计算窗口内读完。

### NPU 15：长请求也会等待

请求为 200K/2048（LL），首层从 3.483753 秒开始预读，3.493938 秒数据到齐；前一请求在 3.491010 秒结束，因此停算 2.928 ms。读取过程受到了前方 NPU 13（200K/2048）、NPU 21（160K/4096）、NPU 12（128K/256）的 IO 影响。
这 2.928 ms 暴露等待期间，实际服务依赖落在 NPU 接收链路上；更早的盘侧排队推迟了它开始接收数据。该例不能描述成“短请求等待长请求”。

### NPU 26：预读窗口本身也可能不够

前一请求 32K/256 的最后一层计算仅 1.997 ms；下一请求 200K/256 的首层，在没有其他卡竞争时也需要约 5.369 ms 读入。因此至少 3.371 ms 等待来自预读窗口不足。这次实际首层等待为 6.548 ms，另有竞争带来的延迟。
